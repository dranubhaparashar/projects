Tool Use & Function Calling

The model writes the request; your code does the work

A language model can only produce text. It cannot look up today’s exchange rate, measure a distance or add up a column of figures. What it can do is write a small, structured request: “call convert_currency with these arguments”. Your program checks the request, runs a real function and hands the result back, and the model answers from it. On the right, six real tools over real data (European Central Bank exchange rates, 1,172 airports, more than 170 years of Met Office weather records) sit behind a router. The idea

Why a model needs tools

Everything a language model knows was frozen into its weights when training stopped. Ask it for an exchange rate and the best it can do is recall one it saw then, which may be months or years old. It also predicts digits as text, so long arithmetic is unreliable, and it cannot act at all: it cannot send an email or read a database. Tool use, also called function calling, fixes all three in the same way. The application gives the model a list of functions it may request. When a question needs one, the model writes a structured call instead of guessing. The application runs the function and passes the result back.

The cleanest case is a fact that changes. Below is the real euro reference rate published by the European Central Bank on each of 7,129 working days since January 1999. Suppose a model memorised the rate on its training cutoff and is asked about a later day. Move the cutoff and the gap and see how far the remembered fact has drifted from what a tool returns.

\[ \begin{aligned} e &= \frac{\lvert\, r_q - r_c \,\rvert}{r_q} \\ \tilde e(h) &= \operatorname*{median}_{t_c}\; e\big(t_c,\, t_c{+}h\big) \end{aligned} \]
Read it as: tc is the day the model’s knowledge stopped and tq the day the question is about; rc and rq are the rates on those days. The relative error e is how far off the remembered rate is, as a share of the true one. The second formula repeats this for every possible cutoff day and takes the median: the typical error after a gap of h months. A tool call has error 0, because it reads rq itself.
Say it“e is the absolute value of r-q minus r-c, over r-q; e-tilde of h is its median over all cutoffs t-c.”

Step 1 · the contract

Describing a tool with JSON Schema

A model can only call a tool it has been told about. Each tool is described by three things: a name, a description in plain words, which is what the model reads to decide when the tool fits, and an input schema that says exactly what the arguments must look like. The schema is written in JSON Schema, a standard vocabulary of keywords: type, required, enum (one of a fixed list), minimum/maximum, pattern (a regular expression), format and additionalProperties. Whatever the model writes, the host validates it against the schema before running anything. A model is a text predictor, and sooner or later it will write "month": 13. Pick a tool and break its arguments: edit the JSON or try the presets.

\[ \begin{aligned} \text{valid}(v, S) \iff\; & \textstyle\bigwedge_{\kappa \in S} \text{ok}_\kappa(v) \\ \wedge\; & \textstyle\bigwedge_{p \in P} \text{valid}(v_p, S_p) \end{aligned} \]
Read it as: an argument object v is valid against schema S only if every keyword κ of S holds for v (∧ means “and”) and every property p in P, the properties of S that v actually supplies, is itself valid against its sub-schema Sp. One failed keyword anywhere makes the whole call invalid. Keywords that do not apply to a value are skipped: minimum says nothing about a string.
Say it“v is valid against S if and only if every keyword of S is satisfied and every supplied property is valid against its own schema.”

Step 2 · the conversation

    
The function-calling loop

    
The model never runs a tool. It is a function from a conversation to the next message, and the API is stateless: every request carries the whole conversation so far, plus the tool definitions. When the model wants a tool, its reply ends with a request to call one (the Anthropic API marks it stop_reason: "tool_use", the OpenAI API finish_reason: "tool_calls"). The host, your program, runs the call, appends the result to the conversation and asks the model again. The loop stops when the model replies with plain text. Each call carries an id, and its result must quote the same id, so results cannot be mixed up. Step through a conversation and read every message exactly as it travels, in either API’s format. The model here is a transparent stand-in (section 4), not an LLM.

    
\[ \begin{aligned} a_t &= M(h_t,\, \mathcal T) \\ h_{t+1} &= h_t \oplus a_t \oplus \text{run}(a_t) \end{aligned} \]
Read it as: ht is the conversation history after t rounds and 𝒯 the tool definitions. The model M reads both and writes a reply at. If the reply contains tool calls, the host runs them; the reply and the results are appended (⊕) to the history and the model is called again; this repeats for as long as at contains a call. When at is plain text, it is the answer. A question that needs k rounds of tools costs k + 1 model calls.
Say it“a-t is M of h-t and the tools; h-t-plus-one is h-t, then a-t, then the result of running a-t.”

Step 3 · decisions

    
Choosing a tool and filling in its arguments

    
Given a request and a list of tools, the model makes two decisions: which tool, if any, and what arguments. A real LLM makes both implicitly, by reading the descriptions. This page cannot run one, so it uses a transparent stand-in that copies the idea. It scores each tool by the words its definition shares with the request, weighting rare words more, much as the tool-retrieval systems behind very large tool sets do. It turns the scores into probabilities and then fills the arguments with a few dozen hand-written patterns (amounts, currencies, dates, airport names, months). An “answer directly” option with a fixed score θ competes with the tools. The API’s tool_choice setting can override the decision: auto lets the model decide, any forces some tool, tool forces one named tool and none forbids tools. Type a request, then switch to names only to see why descriptions matter.

    
\[ \begin{aligned} s_j &= \sum_{w \,\in\, x \,\cap\, d_j} \text{idf}(w) \\ s_0 &= \theta \\ p(j \mid x) &= \frac{e^{\,s_j/\tau}}{\sum_{k \in A} e^{\,s_k/\tau}} \end{aligned} \]
Read it as: x is the set of normalised words in the request and dj those in tool j’s name, description and schema. A word found in only one of the six definitions has a high idf, so it is strong evidence; one found in all six is worth little. Option 0 is “answer without a tool”, with a fixed score θ = 1.2. The softmax over the allowed options A (set by tool_choice) gives probabilities; the stand-in picks the most probable. The temperature τ sets how decisive those probabilities look.
Say it“The score of tool j is the sum of idf over the words shared by the request and its description; the probability of j is e to the s-j over tau, normalised over the allowed options.”

Step 4 · what comes back

    
Handling results: every byte is re-read

    
A tool result is not shown to the user; it is pasted into the conversation as a tool_result block, and the model reads it on every later turn. Because the API is stateless, each new model call re-sends the whole history, so a 5,000-character result is paid for again in every round that follows. Good tools therefore return only what is needed: a limit argument, the fields that matter, a compact format, and a hard cap with an honest "truncated": true rather than silently dropping data. Two more rules. Results are data, not instructions: text inside a result that says “ignore your instructions” must not be obeyed (chapter 5.6). And errors are results too: return them, marked as errors, so the model can react. Raise the limit and the number of rounds on a real query, the hottest months in Oxford’s record, which goes back to 1853.

    
\[ \begin{aligned} C_i &= C_0 + i\,\Delta \\ \text{read} &= \textstyle\sum_{i=0}^{R} C_i \\ &= (R+1)\,C_0 + \Delta\,\tfrac{R(R+1)}{2} \end{aligned} \]
Read it as: C0 is the size of the first request (tool definitions plus the question) and Δ what each round adds (the model’s call plus the tool’s result). The i-th model call reads Ci. Over R rounds of tools there are R + 1 calls, so the total read grows with the square of the number of rounds. Sizes here are in characters; providers bill in tokens, roughly one per four characters of English (a rule of thumb, not a tokenizer).
Say it“The total read is R plus one times C-nought, plus delta times R times R plus one over two.”

Latency

    
Several calls at once

    
“Convert €100 into dollars, pounds, yen and rupees” needs four independent lookups. A model can ask for them one per turn, waiting for each result before writing the next call. That means five model calls. Or it can emit all four tool_use blocks in a single reply. The host can then run them one after another, or all at the same time, and return all the results together in one message. Both APIs allow this (parallel_tool_calls in OpenAI’s, disable_parallel_tool_use to turn it off in Anthropic’s). Calls can run in parallel only when they are independent. “How far is it, and how long at 900 km/h?” needs the distance before the division. Compare the three strategies; the latencies are simulated (the real tools here answer in microseconds), but the arithmetic is the point.

    
\[ \begin{aligned} T_{\text{one per turn}} &= (n+1)\,t_M + \textstyle\sum_j t_j \\ T_{\text{batched, serial}} &= 2\,t_M + \textstyle\sum_j t_j \\ T_{\text{batched, parallel}} &= 2\,t_M + \max_j t_j \end{aligned} \]
Read it as: n tool calls with latencies tj, and tM for each model call (assumed equal, for simplicity). One call per turn pays for n + 1 model calls. Batching all the calls into one reply pays for just two, the call and the answer. Running the batch concurrently replaces the sum of the tool latencies with the slowest one.
Say it“One per turn costs n plus one model calls plus the sum of the tool times; batched costs two model calls plus the sum; batched and parallel costs two model calls plus the maximum.”

Robustness

    
When tools fail: bad arguments, timeouts, retries

    
Tools fail in three ways, and each needs a different response. Bad arguments are the model’s mistake. Retrying the same call cannot help, so the host returns the validation error as the result, marked as an error, and the model usually corrects itself on the next turn. Transient failures (a 503, a dropped connection) are worth retrying, but with exponential backoff: wait b, then 2b, then 4b, with random jitter so that a thousand clients don’t all retry at the same instant. Slowness needs a timeout: give up on an attempt after τ seconds, because a call that hangs for ever stalls the whole agent. Retries are safe only for idempotent tools, ones where doing it twice equals doing it once. A lookup is idempotent; a payment is not, unless it carries an idempotency key. Simulate 2,000 calls to a flaky, slow tool and tune the policy.

    
\[ \begin{aligned} p_s &= (1-p)\;\Phi\big(\ln(\tau/m)/\sigma\big) \\ P_n &= 1-(1-p_s)^{n} \\ w_k &= b\,2^{k-1}\,(\tfrac12 + \tfrac12 U_k) \end{aligned} \]
Read it as: one attempt fails outright with probability p. Its latency is log-normal with median m = 0.6 s and spread σ = 0.5, so the chance that it finishes before the timeout τ is Φ(ln(τ/m)/σ), where Φ is the normal distribution’s cumulative probability. An attempt succeeds with probability ps. With n independent attempts, the call fails only if all n do, so it succeeds with probability Pn. Before attempt k + 1 the host waits wk: the base b doubled each time, scaled by a random Uk between 0 and 1 (“equal jitter”).
Say it“p-s is one minus p times Phi of log tau over m, over sigma; P-n is one minus one-minus-p-s to the n.”

Standards

    
MCP: one protocol for every tool

    
Everything so far lives inside one program. In practice the tools belong to other people: a calendar service, a code repository, a company database. Without a standard, each AI application must write its own connector for each tool service. The Model Context Protocol (MCP), introduced by Anthropic in November 2024 and now an open specification, defines a single connector. An application (the host) runs one MCP client per server. A server advertises its tools with tools/list and runs them with tools/call; it can also offer read-only resources and reusable prompts. Messages are JSON-RPC 2.0: a request has a jsonrpc, an id, a method and params; a response has the same id and either a result or an error; a notification has no id and gets no reply. They travel over standard input/output for a local server, or over HTTP for a remote one. Count the connectors, then talk to a real MCP server running in this page.

    
\[ N_{\text{bespoke}} = n \cdot m \qquad N_{\text{MCP}} = n + m \]
Read it as: n applications and m tool services. With bespoke integrations every pair needs its own connector, n × m of them. With a shared protocol each application implements a client once and each service implements a server once: n + m pieces of work, and any client then works with any server. It is the same idea that let any USB device work with any computer, or any browser with any website over HTTP.
Say it“Bespoke needs n times m connectors; MCP needs n plus m.”

    Real-world project
    
    
    Project: a tool router over real data
    
    
    
      
    The pieces of this chapter, assembled. Six tools run real code over real data embedded in this page. convert_currency uses the European Central Bank’s euro reference rates for every working day from 4 January 1999 to 4 November 2026 (US dollar, pound, yen, Swiss franc, yuan from 2005, rupee from 2009). get_airport and flight_distance use the 1,172 large airports with an IATA code in OurAirports (public domain), with the haversine great-circle formula. station_climate and climate_extremes use the Met Office’s historic monthly records for five UK stations, 7,548 station-months back to 1853 (Open Government Licence). calculate is a recursive-descent arithmetic parser that never calls eval. All data was downloaded on 5 November 2026. A router sits in front of the tools: it looks the tool up, validates the arguments against the schema, applies defaults, runs the call with a timeout and retries, and wraps the outcome in the exact message shape of the chosen API. The “model” is the stand-in from section 4: a policy you can read, not an LLM.

The Python reference below does the same job independently: it validates with the jsonschema library (draft 2020-12, with format checking switched on) and reimplements every tool from the raw downloaded files. For each test, the two must give the same errors at the same places, the same outcome and the same numbers.

    import csv, json, math, ast, operator, calendar, statistics, datetime as dt
from jsonschema import Draft202012Validator

tools = {t["name"]: t["input_schema"] for t in json.load(open("tu-tools.json", encoding="utf8"))}
tests = json.load(open("tu-tests.json", encoding="utf8"))

# ECB euro reference rates, read straight from the published CSV
with open("tu_dl/eurofxref-hist.csv", encoding="utf8") as f:
    rows = sorted(csv.DictReader(f), key=lambda r: r["Date"])
dates = [r["Date"] for r in rows]
def eur(c, r): return 1.0 if c == "EUR" else (None if r[c] in ("N/A", "") else float(r[c]))

def convert_currency(amount, frm, to, date=None):
    date = date or dates[-1]
    if date > dates[-1]: raise ValueError("no ECB rates yet for " + date)
    i = max(k for k, d in enumerate(dates) if d <= date)
    rf, rt = eur(frm, rows[i]), eur(to, rows[i])
    if rf is None or rt is None: raise ValueError("no ECB rate for that currency on " + dates[i])
    return dict(rate_date=dates[i], converted=round(amount * (rt / rf), 2), exact=amount * (rt / rf))

# OurAirports: large airports with an IATA code
with open("tu_dl/airports.csv", encoding="utf8", newline="") as f:
    ap = {r["iata_code"]: r for r in csv.DictReader(f) if r["type"] == "large_airport" and len(r["iata_code"]) == 3 and r["iata_code"].isupper()}
def gc_km(a, b):
    p1, p2 = math.radians(float(a["latitude_deg"])), math.radians(float(b["latitude_deg"]))
    dp = math.radians(float(b["latitude_deg"]) - float(a["latitude_deg"])); dl = math.radians(float(b["longitude_deg"]) - float(a["longitude_deg"]))
    h = math.sin(dp / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dl / 2) ** 2
    return 2 * 6371.0088 * math.asin(min(1.0, math.sqrt(h)))
def get_airport(code):
    if code not in ap: raise ValueError("no large airport " + code)
    return dict(name=ap[code]["name"], elevation_ft=int(ap[code]["elevation_ft"]))
def flight_distance(frm, to, unit="km"):
    for c in (frm, to):
        if c not in ap: raise ValueError("no large airport " + c)
    km = gc_km(ap[frm], ap[to])
    return dict(exact=km / {"km": 1, "mi": 1.609344, "nmi": 1.852}[unit])

# Met Office historic station data, parsed from the text files
def station(name):
    out = {}
    for line in open(f"tu_dl/{name}data.txt", encoding="utf8"):
        t = line.split()
        if len(t) >= 7 and t[0].isdigit() and len(t[0]) == 4 and t[1].isdigit():
            vals = [None if set(v) == {"-"} else float(v.rstrip("*#")) for v in t[2:7]]
            out[(int(t[0]), int(t[1]))] = vals
    return out
ST = {s: station(s) for s in ("oxford", "heathrow", "armagh", "stornoway", "cardiff")}
COLS = ["tmax", "tmin", "af", "rain", "sun"]
def station_climate(station, year, month):
    if (year, month) not in ST[station]: raise ValueError("no record for that month")
    return dict(zip(["tmax_c", "tmin_c", "air_frost_days", "rain_mm", "sun_hours"], ST[station][(year, month)]))
def climate_extremes(station, metric, order="highest", month=None, limit=5):
    c = COLS.index(metric)
    items = [(k, v[c]) for k, v in sorted(ST[station].items()) if v[c] is not None and (month is None or k[1] == month)]
    items.sort(key=lambda kv: -kv[1] if order == "highest" else kv[1])          # stable: ties stay in date order
    return dict(considered=len(items), top=[f"{y}-{m:02d}={v}" for (y, m), v in items[:limit]])

OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg, ast.UAdd: operator.pos}
def calculate(expression):
    def ev(n):
        if isinstance(n, ast.Constant) and type(n.value) in (int, float): return float(n.value)
        if isinstance(n, ast.BinOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.operand))
        raise ValueError("unsupported")
    try: return dict(value=ev(ast.parse(expression.replace("^", "**"), mode="eval").body))
    except (SyntaxError, ZeroDivisionError) as e: raise ValueError(type(e).__name__)

IMPL = dict(convert_currency=lambda a: convert_currency(a["amount"], a["from"], a["to"], a.get("date")), get_airport=lambda a: get_airport(a["code"]),
            flight_distance=lambda a: flight_distance(a["from"], a["to"], a.get("unit", "km")), station_climate=lambda a: station_climate(**a),
            climate_extremes=lambda a: climate_extremes(**a), calculate=lambda a: calculate(a["expression"]))

out = []
for k, (name, args, note) in enumerate(tests, 1):
    v = Draft202012Validator(tools[name], format_checker=Draft202012Validator.FORMAT_CHECKER)
    errs = sorted(("/" + "/".join(str(p) for p in e.absolute_path) if e.absolute_path else "", e.validator) for e in v.iter_errors(args))
    res, terr = None, None
    if not errs:
        try: res = IMPL[name](args)
        except ValueError as e: terr = str(e)
    out.append(dict(errs=errs, res=res, terr=terr))
    verdict = "valid" if not errs else "invalid: " + ", ".join(f"{p or '(root)'} {kw}" for p, kw in errs)
    shown = "" if res is None else " -> " + ", ".join(f"{a}={round(b, 6) if isinstance(b, float) else b}" for a, b in res.items() if a != "exact")
    if res and "exact" in res and name == "flight_distance": shown = f" -> {res['exact']:.6f}"
    print(f"{k:2d} {name:16s} {verdict}{' -> tool error' if terr else ''}{shown}")

def add_months(d, h):
    y, m = divmod(d.month - 1 + h, 12); y += d.year; m += 1
    return dt.date(y, m, min(d.day, calendar.monthrange(y, m)[1]))
stale = {}
for c in ("USD", "GBP", "JPY"):
    idx = [(dt.date.fromisoformat(d), eur(c, r)) for d, r in zip(dates, rows)]
    errs, j = [], 0
    for i, (d, r) in enumerate(idx):
        t = add_months(d, 12)
        if t > idx[-1][0]: break
        while j + 1 < len(idx) and idx[j + 1][0] <= t: j += 1
        errs.append(abs(idx[j][1] - r) / idx[j][1])
    stale[c] = statistics.median(errs)
print("valid", sum(1 for o in out if not o["errs"]), "of", len(out), "| tool errors", sum(1 for o in out if o["terr"]))
print("median relative error of a 12-month-old euro rate:", ", ".join(f"{c} {v:.6f}" for c, v in stale.items()))
json.dump(dict(tests=out, stale=stale), open("tu-py.json", "w", encoding="utf8"))

    The two implementations share only the schemas and the test list. The browser reads compact copies of the data that were prepared once in Node, and Python reads the original CSV and text files. They agree on all 46 verdicts, on every error location and keyword, and on every number exactly, including the median staleness errors of section 1 (USD 6.47%, GBP 3.74%, JPY 7.37% after 12 months). Three honest caveats. First, the “model” is a pattern-matching stand-in: it routes the example questions correctly, but it will misread phrasings it was not written for, where a real LLM would not. Second, the latencies, failures and timeouts are simulated on a virtual clock, because the real tools answer in microseconds. Third, format is only an annotation by default in JSON Schema 2020-12; this router, like Python’s jsonschema with a format checker, treats it as a rule. Without that, "2020-02-31" would pass.
    
  
    

    



    
  
    
    
    Wrap-up
    
    
    Five lines to remember
    
    
      
      
    • A model never runs tools. It writes a structured request; your code validates it, runs a real function and returns the result, and the loop repeats until the model answers in text.
      • 
      
    • A tool is a name, a description the model reads to decide when to use it, and a JSON Schema for its arguments. Validate every call before running it.
      • 
      
    • Results are pasted into a conversation that is re-sent on every turn, so keep them small: limit, select, cap and say when you truncated. Treat them as data, not instructions.
      • 
      
    • Independent calls can go in one turn and run in parallel. Retry only transient failures, with timeouts and exponential backoff with jitter, and only for idempotent tools; return bad-argument errors to the model.
      • 
      
    • MCP standardises the connection: JSON-RPC messages (initialize, tools/list, tools/call) turn n × m bespoke integrations into n + m.
      • 
    
    
    
    Check your understanding
    
    
    
      
    The model returns a tool call with "month": 13. What should the host do?
    Not run it, and not retry it unchanged. Return a tool result marked as an error that says what was wrong (“/month: 13 is greater than the maximum of 12”). The model reads it on its next turn and can correct the call or ask the user.
    
      
    Why does every request to the API include the tool definitions and the whole conversation again?
    Because the model is stateless: each call is an independent computation over the text it is given. The host keeps the state. That is also why large tool results are expensive: they are re-read on every later turn.
    
      
    A question needs three independent lookups, each taking 0.4 s, and a model call takes 1.5 s. How long does each strategy take?
    One per turn: 4 × 1.5 + 3 × 0.4 = 7.2 s. Batched in one reply but run serially: 2 × 1.5 + 1.2 = 4.2 s. Batched and parallel: 2 × 1.5 + 0.4 = 3.4 s.
    
      
    Why is it dangerous to retry a transfer_money tool after a timeout?
    A timeout means you don’t know whether the transfer happened; the reply may simply have been slow. Retrying a non-idempotent action can do it twice. Use an idempotency key so that the server can recognise the repeat, or check the state before retrying.
    
      
    In MCP, what is the difference between a JSON-RPC error and a result with isError: true?
    A JSON-RPC error is a protocol-level failure: malformed JSON (−32700), an unknown method (−32601), an unknown tool or invalid parameters (−32602). A result with isError: true means the tool ran but failed, for example “no large airport with code QQQ”. That text goes to the model so it can adapt.

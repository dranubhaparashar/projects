Precision, Memory Maths & Quantisation

Every weight is a handful of bits. Which bits can you throw away?

A 7-billion-parameter model is 28 GB of numbers in FP32, 14 GB in BF16, 3.5 GB in INT4. The model did not change; only the way each number is written down did. This chapter is about that writing: how a floating-point number spends its bits on range and on precision, why training wants one kind of format and inference another, how to count the bytes a model needs before you buy the GPU, and how to squeeze a trained network into 8, 4 or even 2 bits per weight without it noticing too much. Numerical representations

Bits of a float: sign, exponent, mantissa

A computer has a fixed number of bits for each number, so it cannot store most real numbers; it stores the nearest member of a finite set. A floating-point format spends its bits in three fields. One sign bit says positive or negative. An exponent field of \(E\) bits says roughly how big the number is: which power of two it sits between. A mantissa (also called the significand or fraction) of \(M\) bits says where exactly it sits inside that power-of-two interval. The standard that fixes the rules, IEEE 754 (revised in 2019), stores the exponent with a bias so that the field is an unsigned integer, and it does not store the leading 1 of the mantissa at all, because for a normalised binary number the leading digit is always 1. That free bit is the implicit one.

Two special exponent codes are reserved. All zeros means a subnormal number: the implicit one is switched off and the number is \(0.\text{mantissa}\times 2^{1-\text{bias}}\), which fills the gap between zero and the smallest normal number with evenly spaced values. All ones means infinity (mantissa zero) or not a number, NaN (mantissa non-zero). Everything else is a normal number. When a real value falls between two representable numbers, the default rule is round to nearest, ties to even: pick the closer neighbour, and if it is exactly half-way, pick the one whose last mantissa bit is 0. The gap between neighbours at a given magnitude is the unit in the last place, the ulp; the largest rounding error is half an ulp, and because the gap doubles with each power of two the relative error stays roughly constant at about \(2^{-(M+1)}\). That is the whole point of floating point: the same relative precision at \(10^{-6}\) as at \(10^{6}\).

\[ x = (-1)^{s}\,\times\,\big(1 + \tfrac{m}{2^{M}}\big)\,\times\,2^{\,e - \text{bias}}, \qquad \text{bias} = 2^{E-1}-1, \qquad \text{ulp}(x) = 2^{\lfloor \log_2 |x| \rfloor - M} \]
Read it as: \(s\) is the sign bit, \(e\) the exponent field read as an unsigned integer, \(m\) the mantissa field read as an unsigned integer. The bias centres the exponent so that \(e = \text{bias}\) means \(2^{0}\). For FP32, \(E = 8\), \(M = 23\), bias 127; for FP16, \(E = 5\), \(M = 10\), bias 15; for BF16, \(E = 8\), \(M = 7\), bias 127. The ulp is the spacing between neighbours at the magnitude of \(x\): \(2^{M}\) evenly spaced values in every interval \([2^{k}, 2^{k+1})\).

Two conversions by hand

Converting by hand is the fastest way to make the fields real. Take a number that happens to be a short binary fraction, and one that is not.

how exactly?
Write it in binary: 0.15625 = 1/8 + 1/32 = 0.00101₂. Shift the point until one digit sits before it: 1.01₂ × 2−3. The mantissa bits are what follows the point, 01, padded with zeros to the field width; the leading 1 is implicit and not stored.
FP16 exponent: −3 + bias 15 = 12 = 01100₂. Mantissa: 01 padded to ten bits: 0100000000. Assemble sign 0, exponent, mantissa: 0 01100 0100000000 = 0011 0001 0000 0000 = 0x3100.
BF16 exponent: −3 + bias 127 = 124 = 01111100₂. Mantissa: 01 padded to seven bits: 0100000. Assemble: 0 01111100 0100000 = 0011 1110 0010 0000 = 0x3E20. Decode either: (1 + 1/4) × 2−3 = 1.25/8 = 0.15625. Nothing was lost because the number needs only two mantissa bits.

0.1, not representable in binary

0.1 = 1.100110011001100…₂ × 2−4
FP16: 0 01011 1001100110 = 0x2E66 → 0.0999755859375 (−2.44×10−5)
BF16: 0 01111011 1001101 = 0x3DCD → 0.10009765625 (+9.77×10−5)
FP32: 0x3DCCCCCD → 0.100000001490116 (+1.49×10−9)
how exactly?
0.1 lies between 2−4 = 0.0625 and 2−3 = 0.125, so the exponent is −4 and the mantissa is 0.1/0.0625 = 1.6 = 1.1001 1001 1001…₂, a repeating pattern that never ends. The stored value is the nearest multiple of the ulp, 2−4−M.
FP16 (M = 10): ulp = 2−14. Count ulps: 0.1 × 214 = 1638.4 → rounds to 1638. Stored value 1638/16384 = 0.0999755859375, error −2.44×10−5, which is 0.4 ulp. The mantissa field is 1638 − 1024 = 614 = 1001100110₂ (the implicit 1 is the 1024). Exponent −4 + 15 = 11 = 01011₂. Bits 0 01011 1001100110 = 0x2E66.
BF16 (M = 7): ulp = 2−11. 0.1 × 211 = 204.8 → rounds to 205. Stored value 205/2048 = 0.10009765625, error +9.77×10−5 (0.2 ulp, but the ulp is 8× larger than FP16’s). Mantissa 205 − 128 = 77 = 1001101₂; exponent −4 + 127 = 123 = 01111011₂. Bits 0 01111011 1001101 = 0x3DCD.
Check against FP32. 0.1 in FP32 is 0x3DCCCCCD. BF16 is FP32 with the low 16 mantissa bits removed, so round 0x3DCC|CCCD to 16 bits: the dropped half, 0xCCCD, is more than 0x8000, so round up: 0x3DCD. The same answer from the other direction.
Why this matters. Add 0.1 to itself ten times in FP16 and you get 0.99976, not 1. Multiply a learning rate of 0.1 by a gradient and the product carries a relative error of 2.4×10−4 before any other arithmetic happens. Formats do not store decimals; they store the nearest binary fraction.
Tensor data types

FP32, FP16, BF16, FP8: range against precision

With 32 bits there is room for everything: 8 exponent bits give a range from \(10^{-38}\) to \(10^{38}\), and 23 mantissa bits give seven significant decimal digits. Halve the budget and you must choose. FP16 (IEEE “binary16”) keeps 10 mantissa bits, about three decimal digits, but only 5 exponent bits: the largest number is 65,504 and the smallest normal number is \(2^{-14} \approx 6.1\times10^{-5}\), with subnormals reaching down to \(2^{-24} \approx 6\times10^{-8}\). BF16, the brain floating point format proposed by Google and analysed by Kalamkar et al. (2019), makes the opposite choice: keep all 8 exponent bits of FP32 so that the range is the same, and keep only 7 mantissa bits, about two decimal digits. A BF16 number is literally the top half of an FP32 number, which makes conversion a truncation and lets a BF16 accumulator overflow exactly where FP32 would, which is to say almost never.

Why does that trade pay off for neural networks? Because weights, activations and especially gradients span many orders of magnitude within one tensor, and the relative error of a few parts in a thousand is swallowed by the noise of stochastic gradient descent, while a value that underflows to zero or overflows to infinity is a catastrophe. BF16 trains almost everything out of the box; FP16 needs the loss-scaling machinery of the next section. The price is visible in the inspector above: in BF16 the number 1000 is stored to the nearest 4, in FP16 to the nearest 0.5.

FP8 goes one step further. Micikevicius et al. (2022) proposed two 8-bit formats, since adopted in hardware: E4M3 (4 exponent bits, 3 mantissa bits, range ±448, no infinities, a single NaN code) for weights and activations in the forward pass, where range matters less and resolution more; and E5M2 (5 exponent bits, 2 mantissa bits, range ±57,344, with infinities and NaNs like a shortened FP16) for gradients, which need the range. With only 3 mantissa bits the relative error is around 6%, so FP8 is always used with a per-tensor scaling factor that is chosen from the recent history of the tensor’s maximum, which is exactly the trick integer quantisation uses. INT8, for contrast, has no exponent at all: 256 evenly spaced values, so a fixed absolute spacing, chosen by a scale that someone has to supply. A dot product adds thousands of products, and the sum grows while the terms do not. Once the running total is large, its spacing exceeds the size of the next term, and adding the term changes nothing. Mixed precision and loss scaling

Half-precision arithmetic is two to sixteen times faster on modern accelerators and halves the memory traffic, so everyone wants to train in it. The trouble is that a weight update is a small number added to a large one. A typical update, learning rate times gradient, might be \(10^{-3}\) of the weight’s magnitude; in a format with 10 mantissa bits (relative spacing \(10^{-3}\)) that update rounds away to nothing, and in BF16 (relative spacing \(8\times10^{-3}\)) it is gone entirely. The recipe that made half precision work, Micikevicius et al. (2018), has three parts and the diagram shows all three.

  1. FP32 master weights. Keep one copy of every weight in FP32 and apply the optimiser update there, where it will not be rounded away. Cast a half-precision copy for the forward and backward passes. The optimiser’s own state (Adam’s two moments) stays in FP32 too.
  2. Loss scaling. Activation gradients are small: in the authors’ measurements a large share of them fell below FP16’s smallest normal number and many below its smallest subnormal, so they flushed to zero. Multiply the loss by a scale \(S\) before backpropagation; every gradient is then \(S\) times larger and moves into the representable range. Divide the weight gradients by \(S\) before the update. The gradient is exactly the same mathematically; only its encoding moved.
  3. FP32 accumulation. Dot products sum thousands of half-precision products; let the hardware accumulate them in FP32 and round once at the end. Tensor cores do exactly this: FP16 or BF16 inputs, FP32 accumulate.

Memory bottlenecks

Memory maths for training and inference

Before any model runs, someone has to count its bytes. The count has five parts, and each is a parameter count multiplied by a bytes-per-element. Weights: \(N\) parameters at 4 bytes (FP32), 2 (BF16/FP16), 1 (INT8) or ½ (INT4). Gradients: one per trainable parameter, same width as the working weights. Optimiser state: Adam keeps two FP32 moments per trainable parameter, and mixed precision adds the FP32 master copy, so training costs 16 bytes per trainable parameter in total, as the diagram above showed. Activations: backpropagation needs every intermediate value of the forward pass, so their memory grows with batch size times sequence length times depth, and for long sequences the attention scores add a term in the square of the sequence length. The KV cache: at inference a decoder stores the key and value vectors of every past token in every layer, so that generating the next token does not recompute them; its size grows with context length and batch and is often the thing that limits how many users a server can hold.

The parameter count itself follows from the model’s shape. A transformer layer with hidden size \(h\) has four \(h\times h\) projections in attention (\(4h^2\)) and a feed-forward block with an intermediate width of \(4h\) (\(8h^2\)), so about \(12h^2\) per layer. Embeddings add \(Vh\), twice if the output head is not tied to the input embedding. Models with grouped-query attention (fewer key/value heads than query heads) shrink the K and V projections and, more importantly, the KV cache in proportion. The calculator below does all of this live; the previous chapter explains how the result gets split across GPUs when it does not fit on one.

\[ N \approx 12\,L\,h^{2} + 2\,V\,h, \qquad \text{train} \approx 16\,N + \text{activations}, \qquad \text{KV cache} = 2\,L\,n_{kv}\,d_{\text{head}}\cdot b_{kv}\ \text{bytes per token} \]
Read it as: \(L\) layers, hidden size \(h\), vocabulary \(V\); \(n_{kv}\) key/value heads each of width \(d_{\text{head}} = h/n_{\text{heads}}\); \(b_{kv}\) bytes per cached element (2 for FP16, 1 for INT8/FP8). The 2 in the KV term is one key and one value vector per layer. When \(n_{kv} = n_{\text{heads}}\) the KV cache is simply \(2\,L\,h\,b_{kv}\) bytes per token. For activations the calculator uses the estimate of Korthikanti et al. (2022) for a standard transformer layer in 16-bit precision, \(T\,B\,h\,(34 + 5\,n_{\text{heads}}T/h)\) bytes per layer, where the second term is the attention scores; with activation recomputation (checkpointing) only the layer inputs, about \(2\,T\,B\,h\) bytes per layer, are kept and the rest is recomputed during the backward pass.

FP32. The update is too small to survive 16-bit rounding; 12 of the 16 bytes per parameter live here, which is what ZeRO shards across data-parallel ranks.

BF16 by default; FP16 with a loss scaler on older hardware; FP8 with per-tensor scaling for the matmuls on the newest. Norms, softmax and reductions stay FP32.

Stored activations

16-bit, and as few as possible: activation checkpointing recomputes them, FlashAttention never materialises the T×T scores, so the quadratic term disappears.

serving

Weights

INT8 or INT4 (per-group, GPTQ/AWQ-style) for memory-bound decoding; FP8 or INT8 with quantised activations (W8A8) when the batch is large enough to be compute-bound.

Where the bottleneck sits. For training, the 16 bytes per trainable parameter and the activations dominate; that is why parameter-efficient fine-tuning (LoRA) helps so much: with 1% of the parameters trainable, the gradient and optimiser terms shrink a hundredfold and the frozen weights can sit in 4 bits (that is QLoRA, Dettmers et al. 2023, which also introduced the NF4 format of §9). For inference, the weights and the KV cache are read from memory for every generated token, so they decide both how much fits and how fast it runs: §8 makes that argument quantitative.

Quantisation

Integer quantisation: scale, zero-point, granularity

Floating-point formats put the exponent inside every number. Quantisation takes it out and shares it: a whole block of weights is stored as small integers \(q\) plus one floating-point scale \(s\) (and, optionally, an integer zero-point \(z\)) for the block. The weight is recovered as \(\hat w = s\,(q - z)\). With \(b\) bits the integers run over \(2^{b}\) levels, so the block’s range is cut into \(2^{b}-1\) equal steps of width \(s\), and every weight moves to the nearest step: the worst-case error is \(s/2\), and if the weights are spread evenly within a step the root-mean-square error is \(s/\sqrt{12}\).

Two conventions are common. Symmetric quantisation sets \(z = 0\) and \(s = \max|w| / (2^{b-1}-1)\), so the grid is centred on zero and the integer matmul needs no zero-point corrections; it wastes levels if the block is lopsided. Asymmetric (affine) quantisation maps \([\min w, \max w]\) onto \([0, 2^{b}-1]\) exactly, with \(z\) marking where zero lands; it uses every level but each block carries an extra integer. Jacob et al. (2018) showed how to run a whole network in integer arithmetic this way: multiply INT8 weights by INT8 activations, accumulate in INT32, and fold the two scales into one fixed-point multiplier at the output.

The crucial design choice is how big a block shares one scale. Per-tensor: one scale for the whole matrix; smallest overhead, but a single large weight stretches the grid for millions of others. Per-channel: one scale per output row, which is free inside a matmul because each output is scaled independently. Per-group: one scale for every \(g\) consecutive weights along the input dimension (\(g = 32\) to 128 in practice); the overhead is a 16-bit scale per group, \(16/g\) bits per weight, 0.125 bit for \(g = 128\), and the damage an outlier can do is confined to its own group. Dettmers et al. (2022) found that from about 6.7 billion parameters upward, transformers develop a few hidden dimensions with activations tens of times larger than the rest, emergent outlier features, which is why per-tensor INT8 for activations breaks at that size and why their LLM.int8() keeps those few dimensions in 16 bits. Plant an outlier in the matrix below and watch the three granularities respond.

\[ \text{symmetric: } s = \frac{\max|w|}{2^{b-1}-1},\ q = \operatorname{clip}\!\Big(\operatorname{round}\frac{w}{s},\, -2^{b-1}+1,\, 2^{b-1}-1\Big),\ \hat w = s\,q \qquad \text{asymmetric: } s = \frac{\max w - \min w}{2^{b}-1},\ z = \operatorname{round}\frac{-\min w}{s},\ q = \operatorname{clip}\!\Big(\operatorname{round}\frac{w}{s}+z,\,0,\,2^{b}-1\Big),\ \hat w = s\,(q-z) \]
Read it as: divide by the scale to measure the weight in steps, round to a whole number of steps, clip to the available integers, and multiply back to decode. The zero-point \(z\) is the integer that decodes to exactly 0, which matters because padding and ReLU outputs must stay exactly zero. All of this happens per block: per tensor, per row, or per group of \(g\) weights.

Post-training quantisation

Rounding cleverly: RTN, GPTQ, AWQ and SmoothQuant

Post-training quantisation (PTQ) takes a finished model and compresses it without retraining, usually with a few hundred calibration sequences to look at activations. The baseline is round-to-nearest (RTN): choose a scale per block and round every weight independently, exactly as the last section did. At 8 bits RTN is essentially free for large models. At 4 bits and below it starts to hurt, and three families of ideas recover most of the loss. They differ in what they look at while rounding: the other weights, the activations, or both.

Error-compensating rounding (GPTQ). Rounding one weight changes the layer’s output; the other weights in the same row can move slightly to cancel most of that change, because the inputs they multiply are correlated. The optimal brain surgeon line of work made that precise: for a layer with input covariance \(H = 2XX^{\top}\), the output error from perturbing a row of weights by \(\delta\) is \(\delta^{\top} H\,\delta\), a quadratic bowl whose shape depends on the data. Frantar et al. (2023) quantise one column of the weight matrix at a time, in a fixed order, and after each one update all remaining unquantised weights by the step that minimises the quadratic error, \(\delta = -\frac{w_q - w}{[H^{-1}]_{qq}}\,[H^{-1}]_{:,q}\); with lazy batching and a Cholesky factorisation this runs over a 175-billion-parameter model in a few GPU-hours. The two-weight picture below is the whole idea: rounding the first weight moves you off the valley floor; re-optimising the second weight before rounding it puts you back on it.

\[ \mathcal L(\hat{\mathbf w}) = \|X^{\top}\hat{\mathbf w} - X^{\top}\mathbf w\|^2 = (\hat{\mathbf w}-\mathbf w)^{\top} H\,(\hat{\mathbf w}-\mathbf w),\quad H = XX^{\top} \qquad w_2 \leftarrow w_2 - \frac{H_{12}}{H_{11}}\,(\hat w_1 - w_1) \]
Read it as: the damage done by a change of weights is measured at the layer’s output, not at the weights themselves, and the matrix \(H\) built from the calibration inputs says which directions of weight change are cheap (along the valley) and which are expensive (across it). After quantising \(w_1\), the correction to \(w_2\) is the regression coefficient of input 1 on input 2, times the rounding error just committed; for two inputs of unit variance that coefficient is the correlation \(\rho\). GPTQ does this for every column in turn using \(H^{-1}\), so that the correction is exact for the remaining free weights.
Say it“Round one weight, then move the others to cancel the damage; measure damage at the output.”

Activation-aware scaling (AWQ). Lin et al. (2024) observed that not all weights matter equally: the weights that multiply the input channels with the largest activations carry most of the output, and protecting the 1% most salient of them in 16 bits almost eliminates the quantisation loss. Keeping mixed formats is awkward, so instead they scale: multiply the salient input channels of \(W\) by a factor \(s_j > 1\) before quantising and divide the corresponding activations by \(s_j\), which leaves the product \(WX\) unchanged but gives the important weights a larger share of the grid. The factor is searched per layer as \(s_j = \overline{|x_j|}^{\,\alpha}\) over a small grid of \(\alpha\), using calibration activations and no gradients at all.

Migrating difficulty (SmoothQuant). Weight-only methods keep activations in 16 bits. To use INT8 tensor cores you need INT8 activations too (“W8A8”), and activations are the hard part because of the outlier channels: a per-tensor scale for \(X\) is stretched by a few channels that are 30 to 100 times larger than the rest. Xiao et al. (2023) notice that the same algebraic trick works in reverse. Divide each activation channel by \(s_j\) and multiply the matching weight column by \(s_j\): \(Y = (X\,\text{diag}(s)^{-1})(\text{diag}(s)\,W)\). Choose \(s_j = \max|x_j|^{\alpha} / \max|w_j|^{1-\alpha}\): with \(\alpha = 0.5\) the two sides share the difficulty equally; \(\alpha = 1\) pushes all of it into the weights, which can take it badly; \(\alpha = 0\) leaves it all in the activations. Training for low precision

Quantisation-aware training and the straight-through estimator

When post-training tricks are not enough, at 2 or 3 bits, or for small models that have no redundancy to spare, you can teach the network to live with the rounding. Quantisation-aware training (QAT) inserts a fake quantisation step in the forward pass: the weights (and often the activations) are quantised and immediately dequantised, \(\hat w = s\cdot\operatorname{round}(w/s)\), so that the rest of the network sees exactly the values the deployed model will see. Training then adjusts the underlying full-precision weights so that their rounded versions do the job.

There is an obstacle. The rounding function is a staircase: its derivative is zero everywhere except at the jumps, where it is undefined. Backpropagation through it would deliver no gradient at all. The straight-through estimator (STE), named by Bengio, Léonard and Courville (2013) and traced by them to Hinton’s lectures, simply pretends in the backward pass that the staircase was the identity: \(\partial\hat w/\partial w := 1\) inside the clipping range and 0 outside. The gradient computed for \(\hat w\) is applied to \(w\). It is biased, it is not the gradient of anything, and it works remarkably well: the full-precision weight drifts under the accumulated gradient until it crosses a rounding boundary, at which point the deployed weight flips to the next level. Refinements learn the scale \(s\) too (treating it as a parameter with its own STE gradient) and anneal from soft to hard rounding. The cost is a training run, with data and compute, which is why QAT is used for small on-device models and for the last bits of large ones, while PTQ handles the first.

\[ \hat w = s\cdot\operatorname{round}\!\big(\operatorname{clip}(w/s,\,q_{\min},\,q_{\max})\big), \qquad \frac{\partial \mathcal L}{\partial w} \;\overset{\text{STE}}{:=}\; \frac{\partial \mathcal L}{\partial \hat w}\cdot \mathbf 1\big[q_{\min} \le w/s \le q_{\max}\big] \]
Read it as: forward with the staircase, backward as if it were a straight line of slope 1 inside the representable range, and no gradient for weights that are clipped (they are stuck at the end of the grid, so pushing them further changes nothing). The indicator is the only place the quantiser shows up in the gradient.

Inference

Weight-only, W8A8, and the KV cache

Why does quantising weights make a model faster, and when does it not? The answer is arithmetic intensity: the number of floating-point operations a kernel performs per byte it moves from memory. A matrix multiply of a weight matrix with a batch of \(B\) tokens performs \(2B\) operations per weight and reads each weight once, so its intensity is \(2B / \text{bytes per weight}\) FLOP per byte. An accelerator has a fixed peak compute and a fixed memory bandwidth, and the ratio of the two, its ridge point, is the intensity at which the two limits meet: about 156 FLOP per byte for an A100 (312 TFLOP/s of BF16 tensor-core compute, 2.0 TB/s of memory bandwidth). Below the ridge the kernel is memory-bound: it finishes when the bytes have been read, however fast the arithmetic is. Above it, the kernel is compute-bound.

Generating text one token at a time for one user means \(B = 1\): two operations per weight, two bytes per weight in BF16, an intensity of 1. That is 150 times below the ridge. Decoding a 7B model therefore takes about as long as reading 13.4 GB from memory, 6.7 ms on an A100, no matter how fast the tensor cores are; they sit idle 99% of the time. Weight-only INT4 cuts the bytes by four and so cuts the decode time by nearly four, even though the weights have to be dequantised to 16 bits on the fly before the multiply, because that extra arithmetic is free in a memory-bound regime. W8A8, with both operands in INT8, halves the bytes and doubles the peak compute, so it helps most in the compute-bound regime: prefill (processing the prompt, where \(B\) is the prompt length) and large-batch serving. Pick a batch size and a weight format below and watch the point cross the ridge; the inference chapter builds the whole serving stack on this picture.

\[ \text{intensity} = \frac{2\,B\,N}{N\,b_w + \text{KV bytes}} , \qquad t_{\text{step}} \approx \max\!\Big(\frac{\text{bytes}}{\text{bandwidth}},\ \frac{2\,B\,N}{\text{peak FLOP/s}}\Big) \]
Read it as: one decode step for \(B\) sequences multiplies every one of the \(N\) weights by \(B\) activations (two operations each) and must read every weight (\(b_w\) bytes each) plus the KV cache of all \(B\) sequences. The step takes as long as the slower of the two resources. The roofline plot draws the two limits as lines; where your configuration lands tells you which resource to buy, or which bytes to shrink.
Say it“Two B flops per weight, b bytes per weight; below the ridge, bytes decide the time.”

The KV cache is a tensor too. Every decode step reads the whole cache of every active sequence, and §4 showed it reaching 17 GB for one 32k-token sequence of a 7B model. So the cache is quantised as well, usually to INT8 or FP8 and increasingly to 4 bits, with a scale per head and per token (for values) or per channel (for keys, whose outliers live in a few fixed channels, the same emergent dimensions that trouble activations). The cache is written once per token and read thousands of times, so the cost of quantising it is paid once; and because attention softmaxes over scores, small errors in keys are forgiven more readily than the same relative error in weights. Grouped-query attention, which shares each K/V head across several query heads, cuts the cache by the same factor before any quantisation, and the two are routinely combined.

What quantisation does not fix. Below the ridge, bytes are the cost, so weight-only quantisation is nearly a free speed-up; above it, compute is the cost and INT4 weights that must be dequantised to BF16 give no speed-up at all (the kernel is doing the same BF16 multiplies plus extra unpacking). INT8 or FP8 compute helps there only if the hardware has integer or FP8 tensor cores, and then only if the activations are quantised too, which is where SmoothQuant earns its keep. Batching moves you right along the intensity axis; longer contexts move you left, because the KV bytes grow while the FLOPs per token do not.

Bits against quality

Bits versus perplexity, and the NF4 codebook

How many bits does a language model need? The honest answer is an experiment: quantise at several widths and measure perplexity on held-out text, the exponential of the average negative log-probability per token, which is the standard yardstick for language models and the one every quantisation paper reports. Perplexity is a geometric-mean inverse probability: a model with perplexity 14 is, on average, as unsure as if it were choosing uniformly among 14 options at every step. Large models all show the same shape of curve: flat from 16 bits down to about 4, a knee between 4 and 3, and a cliff at 2. Where exactly the knee falls depends on the method (per-group scales and GPTQ-style rounding push it left) and on the model’s size (bigger models are more tolerant), and the very small toy below is not a large model: it is here so that you can see the curve come out of a real computation in your browser, not to stand in for published results.

NF4: a grid shaped like the weights

Uniform grids spend their levels evenly, but weights are not spread evenly: in a trained network they cluster around zero in a roughly bell-shaped distribution, so most of the outer levels of a 16-level grid are rarely used while the crowded middle is coarsely resolved. Dettmers et al. (2023) proposed NormalFloat4 (NF4) for QLoRA. Normalise each block of 64 weights by its largest magnitude so that values lie in \([-1, 1]\); then, instead of 16 equally spaced levels, use 16 levels placed at the quantiles of a standard normal distribution, so that each level is expected to receive the same number of weights. The levels are fixed constants (one of them is exactly 0, so that zeros stay zero) and every block is read with the same codebook, so the only per-block cost is the scale. Because weights really are close to normal after absmax normalisation, this is close to the information-theoretically optimal 4-bit code for them, and QLoRA showed it matching 16-bit fine-tuning quality. Read it as: \(\Phi^{-1}\) is the inverse cumulative distribution of the standard normal, so the \(q_i\) are midpoints of equal-probability bins; QLoRA builds the negative and positive halves separately (8 and 9 levels) so that a level lands exactly on zero, then merges them and divides by the largest level to span \([-1, 1]\). Build it yourself in Python

The listing is complete and needs only numpy. It uses the same 32-bit generator as the page (mulberry32), the same Box–Muller draws, the same initialisation and the same full-batch Adam, so its numbers are the page’s numbers; the output block is what it printed.

quantise_mlp.py
# quantise_mlp.py -- train a tiny MLP on a synthetic three-spiral task,
# then quantise its weights to 8, 4, 3 and 2 bits with per-tensor and
# per-group scales. Needs only numpy. The random generator is mulberry32
# (the same one the web page uses), so the page and this script see the
# same data and the same initial weights.
import math
import numpy as np

def mulberry32(a):                       # 32-bit generator, same as the page
    a &= 0xFFFFFFFF
    def r():
        nonlocal a
        a = (a + 0x6D2B79F5) & 0xFFFFFFFF
        t = ((a ^ (a >> 15)) * (1 | a)) & 0xFFFFFFFF
        t = ((t + (((t ^ (t >> 7)) * (61 | t)) & 0xFFFFFFFF)) ^ t) & 0xFFFFFFFF
        return ((t ^ (t >> 14)) & 0xFFFFFFFF) / 4294967296
    return r

def gauss(r):                            # Box-Muller, one draw
    u = 0.0
    while u == 0.0:
        u = r()
    return math.sqrt(-2 * math.log(u)) * math.cos(2 * math.pi * r())

def spirals(seed, n_per_class=100, noise=0.1):
    r = mulberry32(seed); X, y = [], []
    for k in range(3):
        for _ in range(n_per_class):
            t = r()                                  # position along the arm
            ang = 4.5 * t + k * 2 * math.pi / 3      # three arms, 120 deg apart
            rad = 0.25 + 1.0 * t
            X.append([rad * math.cos(ang) + noise * gauss(r),
                      rad * math.sin(ang) + noise * gauss(r)])
            y.append(k)
    return np.array(X), np.array(y)

def init(seed, sizes=(2, 32, 32, 3)):
    r = mulberry32(seed); P = []
    for a, b in zip(sizes[:-1], sizes[1:]):          # W is (out, in), He init
        W = np.array([[gauss(r) * math.sqrt(2.0 / a) for _ in range(a)] for _ in range(b)])
        P += [W, np.zeros(b)]
    return P

def forward(P, X):                                   # ReLU MLP, returns logits + cache
    h, cache = X, []
    for i in range(0, len(P), 2):
        z = h @ P[i].T + P[i + 1]
        cache.append((h, z))
        h = np.maximum(z, 0) if i + 2 < len(P) else z
    return h, cache

def loss_grads(P, X, y):
    logits, cache = forward(P, X)
    logits = logits - logits.max(1, keepdims=True)
    p = np.exp(logits); p /= p.sum(1, keepdims=True)
    n = len(y); loss = -np.log(p[np.arange(n), y]).mean()
    d = p; d[np.arange(n), y] -= 1; d /= n              # dL/dlogits
    grads = [None] * len(P)
    for i in range(len(P) - 2, -1, -2):
        h = cache[i // 2][0]                          # input of this layer
        grads[i] = d.T @ h; grads[i + 1] = d.sum(0)
        if i > 0:                                     # back through the previous ReLU
            d = (d @ P[i]) * (cache[i // 2 - 1][1] > 0)
    return loss, grads

def adam(P, X, y, epochs, lr, fake=None):
    m = [np.zeros_like(p) for p in P]; v = [np.zeros_like(p) for p in P]
    b1, b2, eps = 0.9, 0.999, 1e-8
    for t in range(1, epochs + 1):
        Q = [fake(p) if (fake and p.ndim == 2) else p for p in P]   # QAT: quantise on the forward pass
        loss, g = loss_grads(Q, X, y)                                # ... and let gradients straight through
        for i in range(len(P)):
            m[i] = b1 * m[i] + (1 - b1) * g[i]; v[i] = b2 * v[i] + (1 - b2) * g[i] ** 2
            P[i] -= lr * (m[i] / (1 - b1 ** t)) / (np.sqrt(v[i] / (1 - b2 ** t)) + eps)
    return loss

def rnd(x):                                           # round half up, like Math.round
    return np.floor(x + 0.5)

def quantise(W, bits, mode, g=16):
    """Asymmetric (min/max) uniform quantiser. mode: 'tensor' | 'channel' | 'group'."""
    out_dim, in_dim = W.shape
    if mode == 'tensor':
        blocks = W.reshape(1, -1)
    elif mode == 'channel':
        blocks = W.reshape(out_dim, in_dim)
    else:
        gg = min(g, in_dim); blocks = W.reshape(out_dim * in_dim // gg, gg)
    qmax = 2 ** bits - 1
    lo, hi = blocks.min(1, keepdims=True), blocks.max(1, keepdims=True)
    s = (hi - lo) / qmax; s[s == 0] = 1.0
    z = rnd(-lo / s)
    q = np.clip(rnd(blocks / s) + z, 0, qmax)
    deq = ((q - z) * s).reshape(out_dim, in_dim)
    n_blocks = blocks.shape[0]
    bits_total = bits * W.size + n_blocks * (16 + bits)   # fp16 scale + b-bit zero point per block
    return deq, bits_total

def accuracy(P, X, y):
    return (forward(P, X)[0].argmax(1) == y).mean()

Wrap-up

Five lines to remember

  • A float is sign, exponent and mantissa: the exponent buys range, the mantissa buys precision, and a 16-bit budget forces a choice. FP16 takes precision (10 bits, range to 65,504); BF16 takes range (FP32’s 8 exponent bits, 7 mantissa bits), which is why it trains without loss scaling.
  • Mixed precision computes in 16 bits but updates FP32 master weights with FP32 Adam moments: 16 bytes per trainable parameter. A loss scale moves small FP16 gradients into range; the gradient is unchanged, only its encoding.
  • Count before you buy: \(N \approx 12Lh^2 + 2Vh\) parameters; weights cost 4, 2, 1 or ½ bytes each; training costs 16 bytes per parameter plus activations; the KV cache costs \(2Lh\) bytes per token in FP16 and can outgrow the weights at long context.
  • Quantisation stores integers plus a shared scale (and zero-point). The block that shares a scale is the key design choice: per-group scales confine outliers; GPTQ compensates rounding error through the input covariance; AWQ and SmoothQuant rescale channels so that the hard parts land where there is room; QAT with the straight-through estimator trains the network to tolerate the grid.
  • Decode is memory-bound at small batch, so weight-only INT4 speeds it up almost fourfold for free; prefill and large batches are compute-bound and want INT8/FP8 on both operands. The quality cost is flat to about 4 bits, kinks at 3 and collapses at 2, and shaped codebooks such as NF4 fit bell-shaped weights better than a uniform grid.

Common mistakes

Mixing up GB, GiB and “bits”

  • A 7B model in BF16 is 13.4 GB (109) or 12.5 GiB (230); an “80 GB” GPU holds about that much minus the framework’s own buffers. Leave 10–20% slack.
  • “4-bit” never means 4.0 bits per weight once scales are counted: 4.16 for g = 128, 5.25 for g = 16. Quote the effective figure.
  • Biases, norms and embeddings are usually left in 16 bits; for small models they are a noticeable share.

Expecting speed where there is none

  • Weight-only INT4 speeds up memory-bound decode. It does nothing for prefill, and it can slow a compute-bound kernel by adding dequantisation work.
  • Quantising the weights does not shrink the KV cache; at long context the cache dominates and needs its own treatment.
  • Per-tensor INT8 activations fail for large transformers because of outlier channels; use per-token scales, smoothing, or keep the outlier columns in 16 bits.
  • FP16 training without loss scaling “works” until a layer’s gradients underflow and the loss plateaus; check the fraction of zero gradients, not just the loss.

Check your understanding

BF16 and FP16 both use 16 bits. Why can BF16 represent 10−20 while FP16 cannot, and what does BF16 give up?

BF16 keeps FP32’s 8 exponent bits, so its range runs from about 10−38 to 1038; FP16 has 5 exponent bits and bottoms out at 6×10−8 (subnormal). BF16 pays with a 7-bit mantissa: its relative spacing is 2−7 ≈ 0.8%, eight times coarser than FP16’s 2−10 ≈ 0.1%. The number 1000 is stored to the nearest 4 in BF16 and to the nearest 0.5 in FP16.

Why do mixed-precision recipes keep an FP32 master copy of the weights even when the forward and backward passes run in BF16?

The update η·g is typically a thousandth of the weight or less. Added to a BF16 weight whose relative spacing is 0.8%, it rounds away to nothing and training stalls. In FP32 the spacing is 1.2×10−7, so the update survives; the BF16 copy is re-cast from the master after each step. The cost is 4 extra bytes per parameter.

A 13B model is served in INT8 with a 16k-token context and FP16 KV cache (L = 40, h = 5120, no GQA). Which is larger, the weights or one sequence’s cache?

Weights: 13×109 bytes = 13 GB. KV cache per token: 2 × 40 × 5120 × 2 B = 819,200 B; times 16,384 tokens = 13.4 GB. The cache of a single long sequence already matches the INT8 weights, which is why GQA and KV-cache quantisation matter as much as weight quantisation for long-context serving.

Per-group INT4 with g = 128 and 16-bit scales costs how many bits per weight? And with g = 16, as in the project?

4 + 16/128 = 4.125 bits per weight (plus 4/128 = 0.03 for an asymmetric zero-point). With g = 16 the overhead is 16/16 = 1 bit for the scale and 4/16 = 0.25 for the zero-point, so 5.25 bits: that is why the project’s per-group rows are so much heavier than their nominal width, and why real deployments use groups of 32 to 128.

Why does weight-only INT4 speed up decoding at batch 1 but not prefill of a 2,000-token prompt?

At batch 1 the decode step performs 2 FLOPs per weight and reads 2 bytes per weight in BF16: an intensity of 1, deep in the memory-bound regime, so time is bytes divided by bandwidth and INT4 cuts the bytes fourfold. Prefill performs 4,000 FLOPs per weight, far above the ridge; it is compute-bound, and INT4 weights still have to be dequantised to BF16 for the tensor cores, so the arithmetic is unchanged and nothing speeds up. For prefill you need INT8 or FP8 compute on both operands.

The derivative of the rounding function is zero almost everywhere. How does QAT train anything?

The straight-through estimator replaces the staircase with the identity in the backward pass: the gradient with respect to the dequantised weight is applied directly to the underlying full-precision weight. That weight accumulates gradient steps until it crosses a rounding boundary, at which point the deployed weight jumps a level. The gradient is biased, but it points the right way often enough; weights outside the clipping range receive zero gradient, since moving them changes nothing.

Inference Optimisation

Prefill, decode, batching & speculation: why generating text is a memory problem, and how serving systems get around it

Training a language model is a compute problem; running one is mostly a memory problem. Every generated token needs the whole model’s weights read from memory once, and a modern accelerator can do hundreds of arithmetic operations in the time it takes to fetch one byte. So the card that trained the model sits almost idle while it writes your answer, unless the server finds other work to do with each byte it fetches. This chapter is about that search: the two phases of a request, the cache that grows under it, the schedulers that keep a batch full, the kernels that avoid touching memory, and the trick of guessing several tokens and checking them at once. Drag the batch slider and watch eight requests cost barely more than one.

The setting

Two phases: prefill, then decode

A decoder-only transformer (chapter 4.3) answers a prompt by predicting one token, appending it, and predicting again; chapter 4.5 covered how the next token is chosen from the model’s distribution. Here we care about what the hardware is doing while that happens. The same network runs at every step, but the work it does falls into two phases with completely different characters, and almost everything in this chapter follows from the difference.

Prefill handles the prompt. All \(S\) prompt tokens enter the network together as an \(S \times d\) matrix, and every layer processes all of them in one pass: the big weight matrices multiply \(S\) rows at once, so each weight is fetched from memory once and used \(S\) times. Prefill also computes the key and value vectors of every prompt token at every layer and stores them (the KV cache, next section). Its output is the first generated token. The cost is set by arithmetic: roughly \(2P\) floating-point operations per token for a model with \(P\) parameters, so \(2PS\) in total, plus the attention scores, which grow with \(S^2\).

Decode produces every later token, one per step. Now the network processes a single new row per request. Every weight matrix must still be read in full from the accelerator’s high-bandwidth memory (HBM), but it multiplies one vector instead of \(S\) rows. The arithmetic is tiny, about \(2P\) operations, while the traffic is the whole model: \(P\) weights times the bytes per weight. For 16-bit weights that is one operation per byte moved, and an H100 can perform roughly 300 operations in the time it moves one byte. The arithmetic units idle while memory streams the weights past them: decode is memory-bound. Then the step repeats, for every output token, with attention over a cache that has grown by one entry.

The first consequence is a hard floor on single-stream speed. A 7-billion-parameter model in bf16 is about 13.5 GB of weights; at 3.35 TB/s that is 4 ms per step even with perfect efficiency, so one request cannot run faster than roughly 250 tokens per second no matter how much compute the card has. The second consequence is the hero figure: because the step time is set by reading the weights, a second request in the same step is nearly free. It adds one more row to each matrix multiplication and a few more bytes of cache, but the weights are read once for everyone. Move the sliders below to see the anatomy of each step of a single request: a tall prefill step full of arithmetic, then a row of decode steps each dominated by the same block of weight bytes.

\[ \begin{aligned} \text{FLOPs}_{\text{prefill}} &\approx 2PS + 2\,L\,d\,S^{2} \\ \text{FLOPs}_{\text{decode step}} &\approx 2P + 4\,L\,d\,c \\ \text{bytes}_{\text{decode step}} &\approx P\,b_w + c\cdot \text{KV}_{\text{tok}} \\ t_{\text{step}} &\approx \max\!\left(\frac{\text{FLOPs}}{F},\; \frac{\text{bytes}}{\text{BW}}\right) \end{aligned} \]
Read it as: \(P\) is the parameter count, \(S\) the prompt length, \(L\) the number of layers, \(d\) the model width (query heads × head dimension), \(c\) the current context length, \(b_w\) the bytes per weight, \(\text{KV}_{\text{tok}}\) the cache bytes per token, \(F\) the peak arithmetic rate and \(\text{BW}\) the memory bandwidth. The factor 2 in \(2P\) is one multiply and one add per weight per token. The attention terms are the \(QK^{\top}\) and \(PV\) products: \(2 L d\, S^2\) for a causal prefill, \(4 L d\, c\) for one new token against \(c\) stored ones. The last line is the simplest timing model: arithmetic and memory traffic overlap, so whichever pipeline is slower sets the pace. That is the roofline of section 3, and the whole chapter uses it.

The memory

The KV cache: what it stores and what it costs

Self-attention at position \(t\) compares the new token’s query with the keys of every earlier position and blends their values (chapter 2.6). The keys and values of the earlier tokens do not change when a new token arrives, because a causal model never lets an early position look at a later one. Recomputing them at every step would mean running the whole prompt through every layer again for each generated token: quadratic work per token, cubic for the reply. So the server keeps them. The KV cache holds, for every layer and every processed token, that token’s key vector and value vector. A decode step then computes keys and values for the one new token, appends them, and attends over the stored ones.

Its size is easy to count. A layer with \(n_{kv}\) key-value heads of dimension \(d_{\text{head}}\) stores \(n_{kv} d_{\text{head}}\) numbers for the key and the same for the value: \(2 n_{kv} d_{\text{head}}\) numbers per layer per token, times \(L\) layers, times the bytes per number. For a 7B model with 32 layers, 32 heads of dimension 128 and 16-bit numbers that is exactly half a mebibyte per token. Half a mebibyte sounds small until you multiply by a context: a 4,096-token conversation holds 2 GiB of cache, one seventh of the model’s own weights, and it is per request. The cache grows by one token’s worth at every decode step, so a long reply inflates it even if the prompt was short.

This is what limits the batch. Everything on the card must fit in HBM: the weights, a little scratch space for activations, and the cache of every request currently being served. Decode is memory-bound, so the batch is the main lever on throughput, and the batch is capped by how many caches fit. Pope et al. (2022) made this trade explicit for very large models: at long contexts the cache, not the weights, is what the memory system spends its time reading, and it is what decides how many users share one accelerator. Two remedies live in the model’s design. Multi-query attention (Shazeer, 2019) gives all query heads one shared key head and one shared value head, so \(n_{kv} = 1\); grouped-query attention (Ainslie et al., 2023) is the compromise in between, with groups of query heads sharing a key-value head, so \(n_{kv}\) is 8 where the query heads number 32 or 64. Either divides the cache, and the bytes read per step, by \(n_q / n_{kv}\) with little loss in quality; an existing multi-head checkpoint can be converted by averaging each group’s key and value projections and training briefly (“uptraining”). The third remedy is fewer bytes per number, which is the subject of chapter 4.4c. Try the controls: change the KV heads and watch both the wiring diagram and the number of conversations that fit.

\[ \text{KV}_{\text{tok}} = 2 \cdot L \cdot n_{kv} \cdot d_{\text{head}} \cdot b_{kv}, \qquad \text{Memory}_{\text{KV}}(B, c) = B \cdot c \cdot \text{KV}_{\text{tok}}, \qquad B_{\max} \approx \frac{\text{HBM} - P\,b_w - \text{scratch}}{c \cdot \text{KV}_{\text{tok}}} \]
Read it as: the 2 is one key and one value; \(L\) layers, \(n_{kv}\) key-value heads of dimension \(d_{\text{head}}\), \(b_{kv}\) bytes per stored number (2 for bf16, 1 for an 8-bit cache). \(B\) requests at context \(c\) hold \(B c\) tokens of cache. The largest batch that fits is what is left of HBM after the weights (\(P b_w\) bytes) and some scratch, divided by one request’s cache. Multi-head attention has \(n_{kv} = n_q\); grouped-query attention has \(n_{kv} = n_q / g\) for a group size \(g\); multi-query has \(n_{kv} = 1\).
Say it“Two, times layers, times KV heads, times head dimension, times bytes: that is the cache per token. Batch times context times that must fit in what the weights leave free.”

  1. 1 · Numbers per layer per token
    \( 2 \times n_{kv} d_{\text{head}} = 2 \times 32 \times 128 = 8{,}192 \)
    how exactly?
    The key vector of one token in one layer has one slice of 128 numbers per head: 32 × 128 = 4,096 numbers. The value vector is the same size. Key plus value: 2 × 4,096 = 8,192 numbers for one layer.
  2. 2 · Bytes per token
    \( 8{,}192 \times 32 \text{ layers} \times 2 \text{ bytes} = 524{,}288 \text{ bytes} = 512\ \text{KiB} = 0.5\ \text{MiB} \)
    how exactly?
    8,192 × 32 = 262,144 numbers per token across all layers. In bf16 each number is 2 bytes: 262,144 × 2 = 524,288 bytes. 524,288 / 1,024 = 512 KiB, exactly half a MiB. (With 8-bit cache entries it would be 256 KiB.)
  3. 3 · One conversation at 4,096 tokens
    \( 4{,}096 \times 0.5\ \text{MiB} = 2{,}048\ \text{MiB} = 2\ \text{GiB} \approx 2.15\ \text{GB} \)
    how exactly?
    4,096 tokens × 0.5 MiB = 2,048 MiB = 2 GiB. In decimal gigabytes: 2 × 1,073,741,824 bytes = 2,147,483,648 bytes ≈ 2.15 GB. A single 4,096-token request holds about one seventh of the weights’ 13.5 GB.
  4. 4 · What the weights leave free on an 80 GB card
    \( 80 - 13.5 - 4 = 62.5\ \text{GB} \)
    how exactly?
    Weights: 6.74 × 109 parameters × 2 bytes = 13.5 GB. Scratch for activations and workspace: say 5% of the card, 4 GB. Left for caches: 80 − 13.5 − 4 = 62.5 GB.
  5. 5 · Conversations that fit
    \( B_{\max} = \left\lfloor \frac{62.5}{2.15} \right\rfloor = 29 \quad (\text{GQA with } n_{kv}=8:\ 116;\ \text{plus 8-bit cache: } 232) \)
    how exactly?
    62.5 / 2.147 = 29.1 → 29 full-length conversations in multi-head attention with a 16-bit cache. Grouped-query attention with 8 KV heads divides the cache by 32/8 = 4: 0.125 MiB per token, 0.54 GB per conversation → 116. Storing the cache in 8 bits halves it again → 232. Same card, same weights, eight times as many users, which at a memory-bound step is nearly eight times the throughput.

The performance model

Decode on the roofline: intensity grows with the batch

The roofline model (Williams, Waterman & Patterson, 2009) puts the two phases on one picture. A piece of work has an arithmetic intensity \(I\): the operations it performs per byte it moves to or from memory. A device has a peak arithmetic rate \(F\) and a memory bandwidth \(\text{BW}\). The work cannot run faster than \(F\), and it cannot run faster than \(\text{BW} \cdot I\), because every byte it needs must come through the memory pipe. On log axes those two limits are a slanted line and a flat line, meeting at the ridge point \(I^* = F / \text{BW}\). Left of the ridge the work is memory-bound and the flat roof is out of reach; right of it, compute-bound. Chapter 4.4b builds the roofline up from the hardware; here we only need to place decode on it.

A decode step at batch \(B\) does about \(2PB\) operations and moves \(P b_w\) bytes of weights, so its weights-only intensity is \(2B / b_w\): with 16-bit weights, simply \(B\) operations per byte. One request has intensity 1. The ridge of an H100 is near 295, of an A100 near 156. So a single stream uses a third of a percent of the card’s arithmetic, and every doubling of the batch doubles the intensity at nearly the same step time, until the batch reaches \(B^* = b_w F / (2\,\text{BW})\), about 300 for bf16 on an H100. After that the step is compute-bound: time grows with \(B\) and the throughput curve goes flat. Quantising the weights to 8 or 4 bits moves the bytes down and the knee to the left; it makes small batches faster, not large ones.

The cache spoils the clean picture. Each step also reads every running request’s KV entries, \(B c\, \text{KV}_{\text{tok}}\) bytes, and those grow with the batch exactly as the arithmetic does. The intensity therefore saturates: as \(B\) grows it approaches \(2P / (c\,\text{KV}_{\text{tok}})\), which for the 7B model at a 4,096-token context is about 6 operations per byte, far below any ridge. At long contexts decode is memory-bound at every batch size, and the memory it is bound by is the cache. That is the second reason GQA, MQA and 8-bit caches matter: they raise the ceiling on intensity as well as on capacity. Prefill sits on the other side of the ridge: a prompt of \(S\) tokens has intensity about \(S\), so anything beyond a few hundred tokens is compute-bound, which is why prefill time scales with the prompt and decode time does not. Slide the batch and context and watch the point travel along the memory roof and stall below it.

\[ \text{attainable rate} = \min\big(F,\ \text{BW}\cdot I\big), \qquad I_{\text{decode}}(B) = \frac{2PB}{P\,b_w + B\,c\,\text{KV}_{\text{tok}}} \;\xrightarrow[\;c \to 0\;]{}\; \frac{2B}{b_w}, \qquad B^{*} = \frac{b_w\,F}{2\,\text{BW}} \]
Read it as: performance is capped by the compute roof \(F\) and the memory roof \(\text{BW} \cdot I\). The decode intensity is the step’s operations over its bytes: the weights are read once for the whole batch, the cache once per request. With no cache the intensity is proportional to the batch and the knee sits at \(B^*\), where \(2B^*/b_w = F/\text{BW}\). With a cache the denominator grows with \(B\) too and the intensity levels off at \(2P/(c\,\text{KV}_{\text{tok}})\).

What to measure

Latency, throughput and cost

A user watching a reply stream in sees two different delays. The time to first token (TTFT) is how long the screen stays blank: the wait in the queue, then the prefill of the prompt, then whatever scheduling gap comes before the first decode step. The inter-token latency (ITL) is the gap between one streamed token and the next, which is the decode step time plus any stall. Averaged over a reply it is usually called the time per output token (TPOT): the time from the first token to the last, divided by the number of gaps. A person reads at perhaps five to ten tokens a second, so an ITL below 100 ms already streams faster than it can be read; a code assistant that completes lines as you type wants much less, and an agent that chains many model calls cares about the whole reply time, \(\text{TTFT} + (n-1)\,\text{ITL}\), more than about either part.

The operator sees different numbers: throughput, in output tokens per second or requests per second over all users, and cost, which is the price of the hardware per hour divided by the tokens it produced in that hour. From the cost model the two sides are joined by one curve. The step time \(t_{\text{step}}(B)\) barely rises with the batch while decode is memory-bound, so throughput \(B / t_{\text{step}}(B)\) rises almost linearly and ITL stays flat; past the knee the step time grows in proportion to \(B\), throughput levels off and ITL climbs. Plot throughput against ITL with \(B\) as the parameter and you have the latency–throughput trade-off curve of a serving system. Every stack has one; the engineering in this chapter moves it up and to the left. An operator then chooses a point on it by fixing a target, a service-level objective such as “p95 ITL under 50 ms”, and running the largest batch that keeps it. The throughput of requests that meet their targets is sometimes called goodput, and it is the honest objective: raw tokens per second can always be raised by making everyone wait.

Two cautions. First, report percentiles, not means. Queues create tails: the p50 TTFT may be 20 ms while the p95 is a second because a burst of arrivals piled up, and it is the p95 that users complain about. Second, the two phases interfere. In a continuous batch (next section) a newly admitted request’s prefill runs in the same forward pass as everyone else’s decode step, so one 4,000-token prompt stretches that step from 6 ms to the best part of 100 ms and every other user sees a hiccup in their stream: one person’s TTFT is bought with everyone’s ITL. Serving systems answer with chunked prefill, splitting long prompts into pieces spread across several steps (Agrawal et al., 2024), or by disaggregating the phases onto different accelerators and shipping the finished KV cache from the prefill pool to the decode pool (Zhong et al., 2024; Patel et al., 2024). Set a latency target below and read off the batch, throughput and cost it allows.

\[ \text{reply time}(n) = \text{TTFT} + (n-1)\,\text{ITL}, \qquad \text{throughput}(B) = \frac{B}{t_{\text{step}}(B)}, \qquad \text{cost per million tokens} = \frac{\text{price per hour}}{3600 \cdot \text{throughput}} \times 10^{6} \]
Read it as: a reply of \(n\) tokens takes the first-token time plus \(n-1\) gaps. Throughput at batch \(B\) is \(B\) tokens per step divided by the step time, which the roofline gives as \(\max(\text{compute time}, \text{memory time})\) plus a fixed overhead for launching kernels and running the scheduler. Price per hour over tokens per hour is the cost of a token; the \(10^6\) turns it into the usual “dollars per million tokens”. All three quantities below come from the same cost model as the rest of the chapter, with achieved efficiencies of 70% of peak compute and 85% of peak bandwidth and a 0.3 ms per-step overhead.

The scheduler

Static versus continuous batching

Since a decode step costs nearly the same for one request as for thirty, the server’s first job is to keep the batch full. The obvious way, inherited from training, is static batching: wait until \(B\) requests have arrived (or a short timer runs out), prefill them together, then decode them together, step after step, until the last of them is finished; then collect the next \(B\). Three things go wrong. Requests want different numbers of tokens, and a slot whose request finished after 20 tokens stays allocated and padded, doing useless work, until its longest neighbour finishes after 900. Anyone who arrives just after a batch starts waits for the whole batch to end, so the time to first token is set by other people’s reply lengths. And prompts of different lengths are padded to the longest, so the prefill wastes arithmetic too. With realistic spreads of output lengths the share of slot-steps that produce a real token can be well under a half.

Orca (Yu et al., 2022) changed the unit of scheduling from the batch to the iteration: the scheduler runs before every forward pass. A request that emitted its end-of-sequence token leaves the batch immediately and frees its slot; a waiting request takes the slot and has its prompt prefilled in that same pass while the others take their decode step. The trick that makes mixing possible is that most of a transformer layer, the projections and the feed-forward network, treats tokens independently, so tokens from different requests at different positions can be stacked into one matrix multiplication; only attention has to be run per request, against each request’s own cache, and the KV cache replaces padding. This continuous batching (also called iteration-level or in-flight batching) is now what every serving engine does. The Orca paper reports throughput an order of magnitude higher than a static-batching baseline at the same latency; the gain is largest exactly when reply lengths vary most.

Continuous batching has its own costs: the scheduler runs every few milliseconds, a new request’s prefill lengthens that step for everyone (the interference of the previous section), and because the batch changes shape at every step the cache can no longer be a fixed block per slot, which is the problem the next section solves.

\[ \text{slot utilisation} = \frac{\sum_{i} n_i}{B \cdot T}, \qquad \text{wait}_i = s_i - a_i, \qquad T_{\text{static}} = \sum_{\text{batches } j} \max_{i \in j} n_i \]
Read it as: \(n_i\) is the number of tokens request \(i\) needs, \(B\) the number of slots and \(T\) the total number of iterations until everything is done, so the numerator is useful work and the denominator is paid-for capacity. A request that arrives at iteration \(a_i\) and starts at \(s_i\) waited \(s_i - a_i\) iterations. Under static batching every batch runs for as long as its longest member, so the total time is the sum of batch maxima; under continuous batching slots are refilled as soon as they free up, so \(T\) approaches the ideal \(\lceil \sum_i n_i / B \rceil\).

Memory management

Paged KV cache, prefix sharing and the serving stack

Continuous batching admits and retires requests at every step, so the cache must be allocated and freed just as often, and nobody knows in advance how long a reply will be. The first serving systems handled this the way a static framework would: each request got one contiguous tensor sized for the longest possible sequence, prompt plus maximum output, because the attention kernels expected contiguous memory. Kwon et al. (2023) catalogued the waste. Slots reserved for tokens that have not been generated yet sit empty; slots reserved for tokens that will never be generated, because the reply stopped early, are never used; and the gaps between reservations are too small to hold anyone else (external fragmentation). Measuring real systems they found only 20% to 38% of the KV memory holding live token states. Since the batch is capped by cache memory, that is a direct loss of throughput.

Their answer, PagedAttention in the vLLM engine, borrows virtual memory from operating systems. The cache is cut into fixed-size blocks of, say, 16 tokens. A request’s cache is a list of blocks that can live anywhere in memory, and a per-request block table maps logical block \(j\) to its physical address. A block is allocated only when the previous one is full, so the only waste is the unfilled tail of each request’s last block, under one block per request, and freed blocks go straight back to a shared pool. The attention kernel reads the table and gathers keys and values block by block. When the pool runs dry, the scheduler preempts a request, either swapping its blocks to host memory or simply dropping them and recomputing the prefill later. The result in the paper was two to four times the throughput of the best previous systems at the same latency, entirely from fitting more requests into the same memory.

Blocks also make sharing trivial. Two requests whose token sequences agree on a prefix have identical keys and values for it, so their block tables can point at the same physical blocks with a reference count, and a block is copied only when one of them writes into it (copy-on-write). Parallel samples from one prompt, beam search, a system prompt shared by every user, few-shot examples, the earlier turns of a long conversation: all of these are prefixes. Carried across requests, the idea becomes prefix caching (RadixAttention in SGLang, Zheng et al., 2024, and the automatic prefix caching of vLLM): finished requests’ blocks are kept in a tree keyed by token content and evicted least-recently-used, and a new request’s prefill skips every block it finds there. The hosted-API feature sold as “prompt caching” is this mechanism: the first request with a long shared preamble pays its prefill; later ones pay only for the suffix, so their time to first token and their input cost fall together. Grow the four requests below under each allocator and watch the waste; then share the system prompt.

\[ \text{physical}(t) = \text{table}_r\!\left[\left\lfloor t / b \right\rfloor\right], \quad \text{offset}(t) = t \bmod b, \qquad \text{waste}_{\text{paged}} \le B\,(b - 1) \text{ tokens}, \qquad \text{prefill saved} = \frac{\text{shared prefix}}{\text{prompt length}} \]
Read it as: token \(t\) of request \(r\) lives in the block the table lists at position \(\lfloor t/b \rfloor\) (for block size \(b\)), at offset \(t \bmod b\) inside it. Each request wastes at most \(b-1\) slots, in its last block. With a shared prefix of \(s\) tokens out of a prompt of \(S\), the prefill only has to process the remaining \(S - s\), so the fraction saved is \(s/S\); the shared blocks are stored once, whatever the number of requests pointing at them.

The serving stack, and what to measure

Put the pieces together and a serving engine has a recognisable shape. A front end tokenises requests and streams tokens back; a scheduler runs before every iteration, admits requests from the queue while slots and cache blocks allow, decides which running requests to preempt, and builds the batch; a block manager owns the KV pool, the block tables, the reference counts and the prefix tree; the model runner executes one forward pass over the mixed prefill-and-decode batch with kernels written for paged caches and for attention that never touches HBM more than it must (next section); and a sampler turns logits into tokens with the rules of chapter 4.5, possibly with a speculative draft (section 9). Around it sit the things an operator watches, and the project at the end of this chapter measures all of them on a simulated card.

The kernel

FlashAttention: tiles and the online softmax

Written the textbook way, attention for one head computes the score matrix \(S = QK^{\top}\) (\(N \times N\) for a sequence of \(N\) tokens), applies a softmax to every row, and multiplies by \(V\). On a GPU that is three kernels and a lot of traffic: the scores are written to HBM, read back for the softmax, the probabilities written again, read again for the product with \(V\). For a 4,096-token prefill with 32 heads the score matrix is 32 million numbers per layer, and each of those passes moves it through the same memory pipe that the weights compete for. Dao et al. (2022) pointed out what this means: the attention step is memory-bound not because of its arithmetic, which is modest, but because of an intermediate result that no one needs to keep.

A GPU has a second, much smaller memory: a few hundred kilobytes of on-chip SRAM per streaming multiprocessor, with an order of magnitude more bandwidth than HBM. FlashAttention is the observation that the whole computation can be organised so that the score matrix never leaves it. Split \(Q\) into tiles of rows and \(K\), \(V\) into tiles of columns; load one tile of \(K\) and \(V\) into SRAM, compute the slice of scores for a tile of queries, and fold the result straight into a running output. The obstacle is the softmax, which needs the maximum and the sum of the whole row before any probability can be normalised. The online softmax (Milakov & Gimelshein, 2018) removes it: keep a running maximum \(m\), a running denominator \(l\) and an unnormalised running output \(o\); when a new tile raises the maximum, rescale the old \(l\) and \(o\) by \(e^{m_{\text{old}} - m_{\text{new}}}\) before adding the tile’s terms. At the end divide \(o\) by \(l\). The answer is exactly the softmax-weighted sum, computed one tile at a time with constant extra memory per row. For training, the backward pass recomputes the tile’s scores from \(Q\) and \(K\) instead of storing \(N^2\) probabilities, trading cheap arithmetic for expensive memory, which is the chapter’s theme in miniature.

The payoff is twofold. The \(N^2\) footprint disappears, so a 32k-token prompt no longer needs gigabytes of scratch per layer. And the HBM traffic drops from several passes over an \(N \times N\) matrix to one pass over \(Q\) and the output plus one pass over \(K\) and \(V\) for each tile of queries, which is why FlashAttention is two to four times faster than the naive kernels at typical lengths and the gap widens with \(N\). FlashAttention-2 (Dao, 2023) reorganised the loops and the work split between threads to cut non-matrix-multiply arithmetic and reached half to three quarters of the A100’s peak. During decode the problem is different, a single query row against a long paged cache, and its kernels (“flash-decoding”) split the cache across the chip’s multiprocessors and combine their partial \((m, l, o)\) triples with the same rescaling rule. Step through the tiles below and watch the three running numbers converge on the exact answer.

\[ \begin{aligned} m' &= \max\!\big(m,\ \max_{j \in \text{tile}} s_j\big) \\ l' &= l\, e^{\,m - m'} + \sum_{j \in \text{tile}} e^{\,s_j - m'} \\ o' &= o\, e^{\,m - m'} + \sum_{j \in \text{tile}} e^{\,s_j - m'}\, v_j \end{aligned} \qquad\qquad \text{output} = \frac{o}{l} = \sum_j \frac{e^{s_j}}{\sum_i e^{s_i}}\, v_j \]
Read it as: \(s_j\) is the score of key \(j\) for the current query row and \(v_j\) its value; \(m\), \(l\), \(o\) are the running maximum, running sum of exponentials and running weighted sum, started at \(-\infty\), 0 and 0. Every exponential is taken relative to the current maximum so that nothing overflows, and when the maximum moves, the factor \(e^{m - m'} \le 1\) re-expresses everything already accumulated relative to the new one. After the last tile, \(o/l\) equals the ordinary softmax average, exactly, because \(e^{s_j - m'}/l'\) is just \(e^{s_j}/\sum_i e^{s_i}\) with the common factor \(e^{-m'}\) cancelled.

Model optimisation

Make the model smaller: pruning, distillation, dynamic structure

Everything so far left the model alone and changed how it is run. The other family changes the model. Since decode time is bytes of weights over bandwidth, the most direct lever is fewer bytes per weight: quantising weights and cache to 8 or 4 bits, which has its own chapter (4.4c) and which the sliders throughout this one have already shown moving the knee. The remaining levers are fewer weights, a smaller model trained to imitate a larger one, and models that spend less work on easy inputs.

Pruning removes weights. Magnitude pruning zeroes the smallest ones; better criteria estimate each weight’s effect on the loss, and SparseGPT (Frantar & Alistarh, 2023) prunes a large model to half its weights in one pass by solving a small reconstruction problem per layer. The catch is hardware. A matrix with half its entries zeroed at random is still stored, read and multiplied as a dense matrix unless the format stores indices, and tensor cores work on dense tiles; unstructured sparsity therefore saves almost no time at inference. Speed needs structure: either whole heads, columns or layers removed, which shrinks the matrices themselves at a real cost in quality, or the 2:4 pattern, exactly two zeros in every group of four, which NVIDIA’s tensor cores since Ampere execute at up to twice the dense rate while storing the weights at half the bytes plus a small index. For a memory-bound decode step, the halved bytes are what matter.

Distillation (Hinton, Vinyals & Dean, 2015) trains a small student to match a large teacher’s outputs: its full softmax distributions, softened with a temperature so that the “dark knowledge” in the unlikely tokens is visible, or simply the text the teacher generates (sequence-level distillation; chapter 4.7a is about the data side). The student then runs at its own, smaller cost, and it is also the usual source of the draft models in the next section. Dynamic structure makes the amount of work depend on the input. Early exit (Schuster et al., 2022) attaches a confidence estimate to intermediate layers and stops a token’s forward pass as soon as the prediction looks settled; its awkward detail is that later tokens expect this token’s keys and values in every layer, so the skipped layers’ entries are filled by copying the last computed hidden state upward (state propagation) or recomputed later. Mixture-of-experts layers route each token to a few of many feed-forward blocks, cutting the arithmetic per token several-fold, but every expert still lives in memory and, in a batch, nearly all of them are read every step: a compute saving, not a bandwidth saving, which is why the roofline, not the FLOP count, predicts their serving cost. Try both figures: prune the matrix and read what the hardware would actually gain; then set an exit threshold and see how many layers a toy model skips, and how often it changes its mind.

\[ \text{dense time} \propto \frac{P\,b_w}{\text{BW}}, \qquad \text{2:4 time} \approx \frac{\tfrac{1}{2} P\,b_w + \text{indices}}{\text{BW}}, \qquad \text{early-exit cost} = \frac{1}{n}\sum_{i} \frac{\ell_i}{L} \]
Read it as: for a memory-bound step, time is proportional to the bytes of weights read. Random sparsity does not reduce those bytes; the 2:4 pattern halves them (the index costs two bits per kept weight) and lets the matrix units skip the zeros. Early exit replaces the fixed depth \(L\) by a per-token depth \(\ell_i\), and its saving is the average fraction of layers skipped; what it risks is a token whose answer would have changed in the layers it skipped.
Say it“Only structure the hardware can skip turns zeros into speed; only tokens that are already settled can leave early.”
Guess, then check

Speculative decoding: draft \(k\) tokens, verify them in one pass

Below the knee, a decode step on five tokens costs the same as a step on one: the weights are read either way. Autoregression seems to forbid using that slack, because token five cannot be computed before token four exists. Speculative decoding (Leviathan, Kalman & Matias, 2023; independently Chen et al., 2023) gets around the dependency with a guess. A small draft model \(q\), perhaps a few percent of the target’s size, writes \(k\) tokens autoregressively at its own small cost. The target model \(p\) then runs once on the prefix plus all \(k\) drafted tokens, which gives its distribution at every one of those positions in a single forward pass. The drafted tokens are then checked from left to right; up to the first one the target disagrees with, they are kept. When the draft is good, several tokens arrive for the price of one target step.

The check has to be done carefully or the output distribution changes. The rule is a modified rejection sampling. At position \(i\) the draft proposed \(x_i\) with probability \(q(x_i)\); accept it with probability \(\min(1, p(x_i)/q(x_i))\). If it is rejected, draw a replacement from the residual distribution, \(p\) minus \(q\) where that is positive, renormalised, and discard the rest of the draft. If all \(k\) are accepted, the target’s distribution at position \(k+1\) is already computed, so a bonus token is sampled from it for free. The equation box proves the key fact: whatever the draft, every emitted token is distributed exactly as \(p\) would have produced it. Nothing is approximated; the draft only decides how fast the target’s own distribution is sampled. For greedy decoding the rule collapses to “keep while the draft’s token is the target’s argmax”.

How much it helps depends on the acceptance rate \(\alpha\), which for one position equals \(\sum_x \min(p(x), q(x))\), one minus the total variation distance between the two distributions, and on the draft’s cost \(c\) relative to a target step. If each drafted token is accepted independently with probability \(\alpha\), the expected number of tokens per step is \((1-\alpha^{k+1})/(1-\alpha)\), rising towards \(1/(1-\alpha)\) as \(k\) grows; the speed-up divides that by \(1 + kc\), so there is a best \(k\) beyond which drafting costs more than it gains. The method helps most where the chapter’s problem is worst: at small batch, where verification is free. At large batch the \(k+1\) tokens per request push the step past the knee and verification is no longer free; speculation then cuts latency but not throughput, and can cost some. The draft can also come from cheaper places than a second model: extra prediction heads on the target itself (Medusa), a tiny network fed the target’s hidden state (EAGLE), or simply n-grams copied from the prompt, which works surprisingly well for summarisation and code editing. Set up the two toy distributions below, simulate twenty thousand steps, and check that the output histogram matches the target even when the draft is poor.

\[ \text{accept } x \text{ with probability } \min\!\left(1, \frac{p(x)}{q(x)}\right), \qquad \text{else draw } x \sim p'(x) = \frac{\max\big(0,\, p(x) - q(x)\big)}{\sum_y \max\big(0,\, p(y) - q(y)\big)} \]
Read it as: the draft drew \(x\) from \(q\). Where the target likes \(x\) at least as much as the draft did, keep it; where the draft over-proposed \(x\), keep it only a fraction \(p/q\) of the time. The replacement, when needed, comes from exactly the places where the target wanted more mass than the draft gave: the positive part of \(p - q\), scaled to sum to one.
Say it“Keep the draft’s token with probability p over q, capped at one; otherwise sample from the target’s surplus.”
\[ \Pr[X = x] = q(x)\,\min\!\left(1, \frac{p(x)}{q(x)}\right) + (1 - \beta)\, p'(x) = \min\big(p(x), q(x)\big) + \max\big(0, p(x) - q(x)\big) = p(x), \qquad \beta = \sum_y \min\big(p(y), q(y)\big) \]
Read it as: \(X\) is the token finally emitted at this position. The first term is “drafted and accepted”: \(q(x)\) times the acceptance probability, which simplifies to \(\min(p, q)\). \(\beta\) is the total probability of accepting, so \(1 - \beta\) is the probability of a rejection, and \(1 - \beta = \sum_y \max(0, p(y) - q(y))\) is also the normaliser of \(p'\), so the second term is just the positive part of \(p - q\). Minimum plus positive part of the difference is \(p(x)\). The acceptance probability \(\beta\) is the \(\alpha\) of the next box, and it equals one minus the total variation distance between \(p\) and \(q\).
Say it“Accepted mass plus rejected-and-resampled mass equals the target, token by token.”
\[ \mathbb E[\text{tokens per step}] = \sum_{i=0}^{k} \alpha^{i} = \frac{1 - \alpha^{k+1}}{1 - \alpha}, \qquad \text{speed-up} \approx \frac{1 - \alpha^{k+1}}{(1 - \alpha)\,(1 + k\,c)} \]
Read it as: the step emits at least one token (the \(i = 0\) term: either the first draft is accepted or its replacement is emitted); it emits a second if the first was accepted (probability \(\alpha\)), a third if the first two were (\(\alpha^2\)), and so on up to the bonus token after \(k\) acceptances (\(\alpha^k\)). The sum of the geometric series is the closed form. The step costs \(k\) draft steps at \(c\) each plus one target step, so dividing gives the speed-up when verification is as cheap as a single-token step.
Say it“One plus alpha plus alpha squared, up to alpha to the k: that many tokens per step, for one target pass and k draft passes.”

Project · a serving system in the browser

Project: an inference simulator

Nothing in this chapter can be run on a real accelerator from a web page, so we build the next best thing: a discrete-event simulator of one card serving one model. It is driven entirely by the cost model of sections 1 to 4, iteration by iteration, exactly as a continuous-batching engine is: requests arrive at random times with random prompt and reply lengths; a scheduler admits them while slots and KV blocks allow; each forward pass processes the newcomers’ prompts and the running requests’ next tokens and takes as long as the roofline says; the cache grows, blocks are allocated and freed, requests finish and leave. One minute of serving takes a few milliseconds to simulate, so every control re-runs it live. What the simulator leaves out

It is a teaching model, and it is honest about what it is. Step time is the roofline maximum with fixed achieved efficiencies, so it does not know that small, oddly shaped matrix multiplications run below peak or that attention kernels have their own efficiency; kernel launches, sampling and the Python-side scheduler are one constant 0.3 ms. Prefill is not chunked, so a long prompt stalls the step it joins, which is realistic for a plain continuous batcher and pessimistic for a modern one. Preempted requests are recomputed, never swapped. The 70B model does not fit on one 80 GB card in bf16 and the page says so rather than inventing a second card; tensor parallelism is chapter 4.4b’s business. Quantised weights are assumed to be dequantised for free into bf16 arithmetic. And speculative acceptance is a coin with a fixed \(\alpha\) per drafted token, which is the standard simplification and the one the closed form assumes; real acceptance rates vary with position and content.

# inference_sim.py -- one GPU serving an LLM, simulated one forward pass at a time.
# Needs only numpy. Same cost model and same seeded generator as the chapter page.
import math
import numpy as np

# ---------- 1. hardware and model (public spec-sheet numbers, rounded) ----------
DEVICES = {
    "H100": dict(F=989e12, BW=3.35e12, mem=80e9),   # bf16 dense FLOP/s, HBM bytes/s, HBM bytes
    "A100": dict(F=312e12, BW=2.0e12, mem=80e9),
    "L4":   dict(F=121e12, BW=300e9, mem=24e9),
}
MODELS = {  # params, layers, query heads, KV heads, head dim
    "7B-MHA": dict(P=6.74e9, L=32, nq=32, nkv=32, dh=128),
    "8B-GQA": dict(P=8.03e9, L=32, nq=32, nkv=8, dh=128),
    "70B-GQA": dict(P=68.9e9, L=80, nq=64, nkv=8, dh=128),
}
EFF_C, EFF_M, T0 = 0.70, 0.85, 0.0003   # achieved fraction of peak compute / bandwidth, fixed per-step overhead (s)
BLOCK = 16                               # KV-cache block size in tokens (paged attention)

def kv_per_token(M, bytes_kv):
    return 2 * M["L"] * M["nkv"] * M["dh"] * bytes_kv

def step_cost(D, M, bytes_w, bytes_kv, prefill, decode):
    """prefill: list of prompt lengths processed this step.
       decode: list of (context length, tokens processed) per running request.
       Returns (step time, compute time, memory time)."""
    d, kv = M["nq"] * M["dh"], kv_per_token(M, bytes_kv)
    flops, byts = 0.0, M["P"] * bytes_w            # every step reads all the weights once
    for S in prefill:
        flops += 2 * M["P"] * S + 2 * M["L"] * d * S * S   # linear layers + causal attention
        byts += S * kv                                      # KV written
    for c, n in decode:
        flops += 2 * M["P"] * n + 4 * M["L"] * d * c * n
        byts += c * kv + n * kv                             # KV read + KV written
    tc, tm = flops / (D["F"] * EFF_C), byts / (D["BW"] * EFF_M)
    return max(tc, tm) + T0, tc, tm

# ---------- 2. the seeded generator (mulberry32, identical to the page) ----------
def mulberry32(seed):
    a = seed & 0xFFFFFFFF
    def rnd():
        nonlocal a
        a = (a + 0x6D2B79F5) & 0xFFFFFFFF
        t = ((a ^ (a >> 15)) * (1 | a)) & 0xFFFFFFFF
        t = ((t + (((t ^ (t >> 7)) * (61 | t)) & 0xFFFFFFFF)) ^ t) & 0xFFFFFFFF
        return ((t ^ (t >> 14)) & 0xFFFFFFFF) / 4294967296
    return rnd

def gauss(rnd):
    u = 0.0
    while u == 0.0:
        u = rnd()
    return math.sqrt(-2 * math.log(u)) * math.cos(2 * math.pi * rnd())

def lognormal_len(rnd, mean, sigma, lo, hi):
    z = gauss(rnd)
    return int(min(hi, max(lo, round(math.exp(math.log(mean) - sigma * sigma / 2 + sigma * z)))))

def make_requests(seed, rate, horizon, prompt_mean, out_mean, out_max):
    """Poisson arrivals over [0, horizon); lognormal prompt and output lengths."""
    rnd, t, reqs = mulberry32(seed), 0.0, []
    while True:
        t += -math.log(1 - rnd()) / rate
        if t >= horizon:
            break
        S = lognormal_len(rnd, prompt_mean, 0.6, 8, 8192)
        O = lognormal_len(rnd, out_mean, 0.6, 2, out_max)
        reqs.append(dict(arr=t, S=S, O=O, gen=0, first=None, done=None, blocks=0))
    return reqs

# ---------- 3. the simulator ----------
def simulate(reqs, D, M, bytes_w=2, bytes_kv=2, sched="continuous", B=32, horizon=60.0,
             spec=False, alpha=0.75, k=4, draft_frac=0.05, wait=0.1, out_max=1024, seed=1):
    reqs = [dict(r) for r in reqs]
    rnd = mulberry32(seed + 1000)
    kv = kv_per_token(M, bytes_kv)
    cap_blocks = int((D["mem"] - M["P"] * bytes_w - 0.05 * D["mem"]) // (BLOCK * kv))  # 5% kept for activations
    free = cap_blocks
    blocks_for = lambda n: -(-n // BLOCK)
    Md = dict(M, P=M["P"] * draft_frac)
    t, nxt, queue, running, newly = 0.0, 0, [], [], []
    ttft, busy, busy_c, peak, steps, dec_tok = [], 0.0, 0.0, 0, 0, 0
    while t < horizon:
        while nxt < len(reqs) and reqs[nxt]["arr"] <= t:          # a. arrivals join the queue
            queue.append(reqs[nxt]); nxt += 1
        if sched == "static" and not running:                      # b. static: form a whole batch, or wait
            ready = len(queue) >= B or (queue and t >= queue[0]["arr"] + wait)
            if not ready:
                cands = []
                if nxt < len(reqs): cands.append(reqs[nxt]["arr"])
                if queue: cands.append(queue[0]["arr"] + wait)
                if not cands: break
                t = max(t, min(cands)); continue
            while queue and len(running) < B:
                need = blocks_for(queue[0]["S"] + out_max)         # static serving reserves the maximum length
                if need > free: break
                r = queue.pop(0); r["blocks"] = need; free -= need; running.append(r); newly.append(r)
            if not running:
                t = max(t, reqs[nxt]["arr"]) if nxt < len(reqs) else horizon; continue
        if sched == "continuous":
            decoding = [r for r in running if r not in newly]
            plan = []                                              # b. decide this step's tokens, make room
            for r in decoding:
                n = 1
                if spec:
                    for _ in range(k):
                        if rnd() < alpha: n += 1
                        else: break
                n = min(n, r["O"] - r["gen"])
                plan.append([r, n])
            while True:                                            # preempt the youngest if the cache is full
                extra = sum(blocks_for(r["S"] + r["gen"] + n) - r["blocks"] for r, n in plan)
                if extra <= free or not plan: break
                r, n = plan.pop()
                running.remove(r); free += r["blocks"]; r["blocks"] = 0; queue.insert(0, r)
            while queue and len(running) < B:                      # c. admit newcomers (prompt + 1 token of room)
                need = blocks_for(queue[0]["S"] + queue[0]["gen"] + 1)
                if need > free: break
                r = queue.pop(0); r["blocks"] = need; free -= need; running.append(r); newly.append(r)
            if not running:
                if nxt >= len(reqs): break
                t = max(t, reqs[nxt]["arr"]); continue
        else:
            plan = []
            for r in running:
                if r in newly: continue
                n = 1
                if spec:
                    for _ in range(k):
                        if rnd() < alpha: n += 1
                        else: break
                plan.append([r, min(n, r["O"] - r["gen"])])
        # d. cost of this forward pass
        prefill = [r["S"] + r["gen"] for r in newly]
        if sched == "static" and newly:
            prefill = [max(prefill)] * B                           # padded to the longest prompt, B slots
        if sched == "static":
            decode = [(r["S"] + r["gen"], (k + 1 if spec else 1)) for r, n in plan]
            if decode:                                             # finished or empty slots are padding: they cost too
                cmax = max(c for c, n in decode)
                decode += [(cmax, decode[0][1])] * (B - len(decode))
        else:
            decode = [(r["S"] + r["gen"], (k + 1 if spec else 1)) for r, n in plan]
        dt, tc, tm = step_cost(D, M, bytes_w, bytes_kv, prefill, decode)
        if spec and decode:
            nB = len(decode)

Wrap-up

Five lines to remember

  • Inference has two phases. Prefill processes the whole prompt in one pass and is compute-bound; decode produces one token per pass, reads every weight each time, and is memory-bound: its floor is weight bytes over bandwidth, and a second request in the step is nearly free.
  • The KV cache holds \(2 \cdot L \cdot n_{kv} \cdot d_{\text{head}} \cdot b\) bytes per token, grows with every generated token, and is what caps the batch; grouped-query attention and 8-bit caches shrink it, and at long contexts reading it, not the weights, is what the step waits for.
  • On the roofline a decode step’s intensity is about \(2B/b_w\): batch is the lever on throughput until the knee at \(B^* = b_w F/(2\,\text{BW})\). Report TTFT and ITL as percentiles, tokens per second and cost per token, and choose the batch from a latency target.
  • Continuous batching schedules every iteration so finished requests leave and new ones join at once; paged KV blocks make that allocation cheap and nearly waste-free and let shared prefixes be stored once; FlashAttention keeps the score matrix in on-chip memory with an online softmax.
  • Speculative decoding drafts \(k\) tokens with a small model and verifies them in one target pass; accepting with probability \(\min(1, p/q)\) and resampling from \((p - q)^+\) keeps the target distribution exact, and yields \((1 - \alpha^{k+1})/(1 - \alpha)\) tokens per step.

Check your understanding

A 13B model in bf16 runs on a card with 2 TB/s of bandwidth. What is the fastest a single stream can possibly decode, and why does the card’s FLOP rating not enter?

13 × 109 weights × 2 bytes = 26 GB must be read per step; at 2 TB/s that is 13 ms, so at most about 77 tokens per second for one request. The arithmetic for one token is 26 GFLOP, which any modern accelerator finishes in well under a millisecond, so the step waits for memory and the FLOP rating only matters once the batch is large enough to reach the ridge point.

Why does grouped-query attention improve throughput and not just the number of conversations that fit?

Each decode step reads the whole cache of every running request. With fewer KV heads the cache per token is smaller, so the bytes per step fall and the step is shorter at the same batch; and because the intensity ceiling \(2P/(c\,\text{KV}_{\text{tok}})\) rises, a larger batch can be served before the cache dominates the traffic. Both effects raise tokens per second; the capacity gain is the third benefit.

Under static batching, a batch of eight has replies of 20, 30, 40, 50, 60, 70, 80 and 900 tokens. What is the slot utilisation of that batch?

The batch runs for 900 iterations on 8 slots: 7,200 slot-steps. Useful tokens: 20 + 30 + 40 + 50 + 60 + 70 + 80 + 900 = 1,250. Utilisation 1,250 / 7,200 ≈ 17%. Continuous batching would refill the seven short slots as they freed, and the 900-token reply would share its steps with about 60 other requests over its lifetime.

In the speculative acceptance rule, why is the replacement sampled from \((p - q)^+\) rather than from \(p\) itself?

Accepted drafts already contribute \(\min(p, q)\) of probability to every token. Sampling the replacement from \(p\) would add \((1 - \beta)\,p(x)\) on top, over-representing tokens the draft already proposed often. Sampling from the positive part of \(p - q\), normalised by \(1 - \beta\), adds exactly the mass that acceptance left out, \(\max(0, p - q)\), so the total is \(p(x)\) for every token.

Speculative decoding gave a 2.5× speed-up for a single user. The operator turns it on for a card serving 200 concurrent requests and throughput falls. Why?

At batch 200 the card is near or past its knee, so each step is close to compute-bound. Verification then processes \((k+1) \times 200\) tokens instead of 200, which costs real time rather than riding on the memory bound, and the drafting steps are added on top. Rejected drafts are wasted compute. The method converts spare arithmetic into latency; when there is no spare arithmetic, it has nothing to convert.

A long prompt joins a continuous batch. What does each other user see, and which two system designs address it?

The newcomer’s prefill runs inside the shared step, so that one step takes tens of milliseconds instead of a few, and every streaming user sees a stall of that length in their inter-token latency. Chunked prefill splits the prompt across several steps to bound the stall; disaggregated serving runs prefill on separate accelerators and ships the finished KV cache to the decode pool.

The online softmax processes scores 2.0, 5.0 in the first tile and 3.0 in the second. Write the running \(m\) and \(l\) after each tile.

Tile 1: \(m = 5\), \(l = e^{2-5} + e^{0} = 0.0498 + 1 = 1.0498\). Tile 2: the maximum stays 5, so the rescale factor is \(e^{0} = 1\) and \(l = 1.0498 + e^{3-5} = 1.0498 + 0.1353 = 1.1851\). This equals \(e^{-5}(e^2 + e^5 + e^3)\), the full denominator with the common factor \(e^{-5}\) pulled out, so dividing \(o\) by \(l\) gives the exact softmax average.

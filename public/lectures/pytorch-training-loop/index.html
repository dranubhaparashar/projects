PyTorch: Tensors, Autograd & the Training Loop

Five lines of code, repeated a few thousand times, are how every network learns

The last chapter built automatic differentiation by hand. PyTorch packages that idea with two more: arrays that know their shape and number type, and ready-made layers, losses, optimisers and data loaders. Put together, every training run is the same small loop: clear the old gradients, run the model forward, measure the loss, send the gradient backward, take a step. The figure runs that loop on real Fashion-MNIST photos, in your browser, with a network whose numbers match PyTorch’s to 16 digits. Press Train, or step one batch at a time, and watch each stage of the loop light up with its real numbers.

The big picture

Three libraries in one

PyTorch (Paszke et al., 2019) is easiest to understand as three libraries sharing one name. The first is a tensor library: multi-dimensional arrays, much like NumPy’s, that can also live on a GPU. The second is an autograd engine: it watches the operations you run on tensors and can work out the gradient of any result with respect to any input. The third is a deep-learning toolkit: ready-made layers and losses in torch.nn, optimisers in torch.optim, and data plumbing in torch.utils.data. None of them is magic: the last chapter wrote the second one in about a hundred lines.

Below, the smallest possible model, a straight line ŷ = w·x + b, is fitted to six points by gradient descent. Each step uses all three parts, and the ledger shows which part did what, with the real numbers. Drag the points, then step; push the learning rate past the limit shown and watch the fit blow up.

\[ \begin{aligned} L(w,b) &= \frac1n\sum_{i=1}^{n}\big(w x_i + b - y_i\big)^2 \\ \frac{\partial L}{\partial w} &= \frac2n\sum_{i}(\hat y_i - y_i)\,x_i \\ \frac{\partial L}{\partial b} &= \frac2n\sum_{i}(\hat y_i - y_i) \\ w &\leftarrow w - \eta\,\frac{\partial L}{\partial w} \\ b &\leftarrow b - \eta\,\frac{\partial L}{\partial b} \end{aligned} \]
Read it as: the first line is the mean squared error (the tensor library computes it). The next two are its gradient (the autograd engine works them out; you never type them). The last two are one step of gradient descent with learning rate η (the optimiser applies it).
Say it“L is the mean of the squared errors; each parameter moves by minus eta times its partial derivative.”

    loss = ((w * x + b - y) ** 2).mean()           # tensor library
    opt.zero_grad(); loss.backward()               # autograd fills w.grad and b.grad
    opt.step()                                     # w -= lr * w.grad, b -= lr * b.grad
Part 1 · the tensor library

Tensors: shape, strides and dtype

A tensor is a block of numbers with a shape. A single number is a rank-0 tensor (a scalar), a list is rank 1 (a vector), a table is rank 2 (a matrix), and a stack of tables is rank 3. A batch of 32 colour images is rank 4: 32 × 3 × height × width. Underneath, every tensor is one flat run of memory plus a recipe for finding element (i, j, k) in it: the strides, how many slots to jump per step along each axis. That is why x.T is free: transposing just swaps the strides, no number moves. The price is that the result is no longer contiguous, so .view() refuses it and .reshape() quietly makes a copy.

Each tensor also has a dtype. Floats default to float32 and integers to int64; NumPy arrays arrive as float64. Large models are trained in 16-bit types to halve memory: float16 keeps more digits but overflows above 65,504, while bfloat16 keeps float32’s range with only about two to three significant digits. Change the shape, click any element, then try the dtypes.

\[ \begin{aligned} \text{offset}(i_0,\dots,i_{r-1}) &= \sum_{k=0}^{r-1} i_k\, s_k \\ s_{r-1} = 1, \quad s_k &= s_{k+1}\, d_{k+1} \end{aligned} \]
Read it as: a tensor of shape (d0, …, dr−1) stored row by row has strides s: the last axis moves one slot, each earlier axis jumps over a whole block of the later ones. Element (i0, …) lives at the dot product of its index with the strides.
Say it“The offset is the sum over axes of the index times the stride.”
\[ \begin{aligned} \text{fl}(x) &= x\,(1+\delta), \quad |\delta| \le \tfrac{\varepsilon}{2} \\ \text{bytes} &= \text{numel} \times \text{itemsize} \end{aligned} \]
Read it as: storing x in a floating-point dtype rounds it to the nearest number the dtype can hold; the relative error is at most half the machine epsilon ε (2−23 for float32, 2−7 for bfloat16), as long as x is inside the dtype’s normal range. Memory is simply the number of elements times the bytes per element.
Say it“Stored x is x times one plus delta, with delta at most half epsilon; bytes are elements times item size.”

Part 1 · doing things with tensors

Tensor operations and broadcasting

Most of a network is a handful of operations. Element-wise ones (+, *, torch.relu) act on matching positions. Reductions (x.sum(dim=0), x.mean(), x.argmax(dim=1)) collapse an axis. Matrix multiplication, written A @ B, is where nearly all the arithmetic goes. And reshaping (.reshape, .view, .T, .flatten) changes how the same numbers are indexed.

When two shapes differ, PyTorch broadcasts: it lines the shapes up from the right, and an axis of size 1 (or a missing axis) is stretched to match the other, without copying. That is how a bias of shape (64,) is added to a batch of shape (32, 64). @ broadcasts too, over every axis except the last two, which is how one weight matrix is applied to a whole stack of matrices at once. Pick two shapes and an operation; A is filled with 0, 1, 2, … and B with 1, 2, 3, …, so you can check every result by hand. The engine on this page was compared with PyTorch on all 1,521 pairs of shapes up to rank 3 with sides 1 to 3, for all three operations.

\[ \begin{aligned} d^{\text{out}}_k &= \max(a_k, b_k) \\ \text{only if } & a_k = b_k \ \text{ or } \min(a_k,b_k) = 1 \end{aligned} \]
Read it as: right-align the two shapes and pad the shorter one with 1s on the left. Axis by axis, equal sizes stay, a 1 stretches to the other size, and any other mismatch is an error.
Say it“Each output size is the larger of the two, allowed only when they match or one of them is one.”
\[ \begin{aligned} (AB)_{ij} &= \sum_{q=1}^{k} A_{iq}\,B_{qj} \\ (n\times k)\,@\,(k\times m) &\to (n\times m) \end{aligned} \]
Read it as: entry (i, j) of the product is row i of A dotted with column j of B, so the inner sizes must agree. Extra leading axes are batch axes and broadcast by the rule on the left; a 1-D operand is treated as a row (on the left) or a column (on the right) and that axis is dropped again afterwards.
Say it“Entry i j of A B is the sum over q of A i q times B q j.”

Part 2 · the autograd engine

Models as computation graphs

Every model is a chain of tensor operations, and any chain of operations is a computation graph: inputs and parameters at the leaves, each operation a node, the loss at the root. PyTorch builds this graph while your code runs (“define by run”). Whenever an operation touches a tensor created with requires_grad=True, the result remembers which operation made it in its grad_fn, and that is the graph. Because it is rebuilt on every forward pass, ordinary Python ifs and loops can change the model from one batch to the next.

Here is the smallest classifier there is: logistic regression on one example, with a weight w and a bias b. The labels in the boxes are the real grad_fn names PyTorch gives these operations. Move the sliders, then switch off requires_grad or switch on no_grad, and see which parts of the graph stop being recorded.

\[ \begin{aligned} u &= w\,x, \qquad z = u + b \\ a &= \sigma(z) = \frac{1}{1+e^{-z}} \\ L &= -\big[\,y \ln a + (1-y)\ln(1-a)\,\big] \end{aligned} \]
Read it as: multiply the input by the weight, add the bias to get the logit z, squash it into a probability a, and score that probability against the true label y (0 or 1) with the binary cross-entropy L. Each equals sign is one node of the graph.
Say it“z is w x plus b, a is the sigmoid of z, and L is minus y log a minus one-minus-y log one-minus-a.”

Part 2 · gradients on demand

Autograd in practice

loss.backward() walks the recorded graph from the loss back to the leaves, multiplying local derivatives along the way (the chain rule, in reverse mode), and leaves the result in the .grad of every leaf that requires a gradient. Three habits follow from how it does that. Gradients are added into .grad, never overwritten, so each step must start with optimizer.zero_grad(); the adding is deliberate, because it lets you sum the gradients of several small batches before one step (gradient accumulation). The graph is freed after backward, so calling backward twice on the same loss is an error unless you ask for retain_graph=True. And when a tensor feeds two places, its gradients from both paths are summed.

The model now adds a weight-decay penalty λw², so w feeds the graph twice. Press backward a few times without zeroing, then zero and press again.

\[ \begin{aligned} L &= \text{BCE}\big(\sigma(wx+b),\, y\big) + \lambda w^2 \\ \frac{\partial L}{\partial w} &= \underbrace{(a-y)\,x}_{\text{through }z} + \underbrace{2\lambda w}_{\text{through } w^2} \\ \frac{\partial L}{\partial b} &= a - y \end{aligned} \]
Read it as: the sigmoid and the cross-entropy combine into the neat local gradient a − y at the logit. From there the chain rule multiplies by x to reach w, and by 1 to reach b. The penalty adds a second path into w, and autograd adds the two contributions. Every call to backward then adds this whole gradient to what .grad already holds.
Say it“dL by dw is a minus y times x, plus two lambda w; dL by db is a minus y.”

Part 3 · the toolkit

nn.Module: layers that own their parameters

Writing w and b by hand stops scaling at about two parameters. torch.nn wraps them in modules: nn.Linear(196, 64) creates a 64 × 196 weight and a 64-long bias, registers both as parameters that require gradients, and computes x WT + b when called. A model is a module made of modules: subclass nn.Module, create the layers in __init__, say how data flows in forward, or simply chain them with nn.Sequential. Then model.parameters() hands every weight to the optimiser, and model.train() / model.eval() switch layers such as dropout and batch norm between their training and inference behaviour.

The network in this chapter maps a 14 × 14 photo (196 pixels) through two hidden layers with ReLU to 10 logits, one per class. There is no softmax at the end: F.cross_entropy takes logits and applies a numerically safe log-softmax itself. Fresh layers start from PyTorch’s default, uniform weights in ±1/√fan_in, so an untrained network is roughly equally unsure of all ten classes. Resize the hidden layers and compare the starting loss with ln 10.

\[ P = \sum_{l=1}^{L} \big(n_{l-1} + 1\big)\, n_l \]
Read it as: a linear layer from nl−1 inputs to nl outputs has an nl × nl−1 weight matrix plus nl biases. ReLU layers have none. Add them up over the layers.
Say it“The parameter count is the sum over layers of inputs-plus-one times outputs.”
\[ \begin{aligned} W_{ji},\ b_j &\sim \mathcal U\!\Big(\!-\tfrac{1}{\sqrt{n_{l-1}}},\ \tfrac{1}{\sqrt{n_{l-1}}}\Big) \\ L_0 &\approx \ln K \end{aligned} \]
Read it as: nn.Linear’s default draws every weight and bias uniformly within one over the square root of the fan-in. That keeps the logits small, so the softmax is close to uniform over the K = 10 classes and the first loss is close to ln 10 ≈ 2.303.
Say it“Weights are uniform within plus or minus one over root fan-in; the starting loss is about log K.”

                                    nn.Linear(h1, h2), nn.ReLU(), nn.Linear(h2, n_out))
    def forward(self, x):
        return self.layers(x)                        # logits; no softmax here

Part 3 · feeding the model

Datasets and DataLoaders

Data reaches the model in two layers. A Dataset answers two questions: how many examples are there (__len__), and what is example i (__getitem__), returned as an (input, label) pair. A DataLoader wraps it and does the bookkeeping: it draws indices in order or reshuffled every epoch, groups them into batches of batch_size, stacks each batch into one tensor (the collate step), optionally drops a short last batch (drop_last=True), and with num_workers > 0 prepares the next batches in background processes while the model is busy. The order comes from a Sampler; the project uses a small custom one so that its shuffle can be saved and restored exactly.

Below are the first 20 training photos. Change the batch size, toggle shuffle and drop_last, and start new epochs.

\[ \begin{aligned} n_{\text{batches}} &= \begin{cases} \lceil N/B \rceil & \text{keep last} \\ \lfloor N/B \rfloor & \text{drop last} \end{cases} \\ B_{\text{last}} &= N - B\,\lfloor N/B \rfloor \quad (\text{if not } 0) \end{aligned} \]
Read it as: N examples in batches of B fill ⌊N/B⌋ full batches; whatever is left (fewer than B) either forms one short batch or is dropped for this epoch. With shuffling the dropped examples change from epoch to epoch, so none is lost for good.
Say it“The number of batches is N over B rounded up, or rounded down when the last batch is dropped.”

Everything together

The training loop: forward, loss, backward, step

With the pieces in place, training is a loop you will write a hundred times. For each batch from the loader: run the model forward to get logits; compute the loss; zero the old gradients; call backward; let the optimiser take a step. Every so often, switch to model.eval(), wrap the work in torch.no_grad() (no graph is needed, which saves memory and time), and measure the loss on data the model never trains on. When the validation loss stops falling while the training loss keeps going down, the model has started memorising. Pretraining a GPT in Raschka’s chapter 5 is this same loop: only the data (token ids, with the targets shifted one place) and the model change.

The lab trains the chapter’s network on 4,000 Fashion-MNIST photos and scores it on 1,000 others every quarter epoch. The default settings are the project’s, so the first epoch here is, number for number, the first epoch of the PyTorch run in the project. Train, then try plain SGD, a learning rate ten times too big, or forgetting zero_grad().

\[ \begin{aligned} L &= -\frac1B \sum_{i=1}^{B} \log \frac{e^{z_{i,y_i}}}{\sum_{k=1}^{K} e^{z_{i,k}}} \\ \text{PPL} &= e^{L} \end{aligned} \]
Read it as: for each photo in the batch, softmax turns the K logits into probabilities and the loss is minus the log of the probability given to the true class yi; the batch loss is the mean. Perplexity eL reads the same number as “the model is as unsure as if choosing uniformly among PPL options”: 10 at the start, 1 when perfect.
Say it“L is minus the mean log-softmax of the true class; perplexity is e to the L.”
\[ \begin{aligned} Z &\in \mathbb R^{B\times T\times V} \;\to\; \mathbb R^{BT\times V} \\ L &= -\frac{1}{BT}\sum_{b,t} \log p_\theta\big(x_{b,t+1}\mid x_{b,\le t}\big) \end{aligned} \]
Read it as: the language-model version. A batch of B rows of T tokens gives one row of V logits (one per vocabulary entry) at every position. Flatten batch and time into one axis, use the next token as the label, and it is exactly the classification loss on the left, averaged over B·T predictions. This is the loss of Raschka’s chapter 5, and eL is the perplexity reported for language models.
Say it“Flatten the logits to B T rows of V; the loss is minus the mean log-probability of each next token.”

Keeping what you trained

Saving and loading models and checkpoints

A trained model is just its parameters, and PyTorch hands them over as a state_dict: an ordered dictionary from names such as 0.weight to tensors. torch.save(model.state_dict(), "model.pth") writes it; to use it again you build the same architecture and call model.load_state_dict(torch.load("model.pth")), then model.eval() before predicting. Saving the dictionary rather than the whole Python object keeps the file independent of your code’s class layout, and since PyTorch 2.6 torch.load defaults to weights_only=True, which refuses to unpickle arbitrary objects from an untrusted file.

To continue training, the weights are not enough. An optimiser has a state of its own: momentum keeps one running average per weight, and AdamW keeps two (exp_avg and exp_avg_sq) plus a step count, which is why Raschka saves the optimiser with the model when pretraining in chapter 5. A full checkpoint therefore holds the model, the optimiser, the epoch, and the state of the random generator that shuffles the data. Pick an optimiser and a dtype and see what a checkpoint actually contains.

\[ \begin{aligned} \text{size} &\approx (1+m)\,P\,b + c \\ m &= 0 \text{ (SGD)},\ 1 \text{ (momentum)} \\ m &= 2 \text{ (Adam, AdamW)} \end{aligned} \]
Read it as: P parameters at b bytes each for the model, plus m extra numbers per parameter for the optimiser’s running averages, plus c, a few kilobytes of container: names, shapes, the step counters and the zip file PyTorch writes. An AdamW checkpoint is about three times the size of the model it trains.
Say it“The checkpoint is about one plus m, times P times b, plus a few kilobytes.”

Real-world project

Project: Fashion-MNIST, checkpointed, crashed and resumed

Fashion-MNIST (Xiao, Rasul & Vollgraf, 2017) is Zalando’s set of 70,000 greyscale product photos, 28 × 28 pixels, in ten classes, released under the MIT licence as a harder drop-in replacement for handwritten digits. The files were downloaded from the dataset’s GitHub repository (commit b2617bb), and the class names below are the ones in its README. To keep the page light and the training quick, the photos are averaged down to 14 × 14 and stored with 16 grey levels: the first 4,000 training photos are the training set, the next 1,000 the validation set, and the first 1,000 of the official test set the test set.

The recipe is the chapter’s: the 196 → 64 → 32 → 10 ReLU network (15,018 parameters), AdamW with learning rate 0.002 and weight decay 0.01, batches of 32, eight epochs, and a full checkpoint after every epoch. The same run was done in PyTorch 2.15 (below), in float64, from the same starting weights and the same shuffle, so every number the browser prints can be held against PyTorch’s.

2 · Crash the run and resume it three ways

Pretend the machine died after epoch k. All that survives is the checkpoint file from that epoch. A full resume restores the weights, AdamW’s running averages and step count, and the shuffle generator. No RNG forgets the generator, so the shuffle restarts from epoch 1’s order. Weights only also starts a fresh AdamW, as if only model.state_dict() had been saved. Choose where to crash, then resume.

import os, json, numpy as np, torch
from torch import nn
from torch.utils.data import Dataset, DataLoader, Sampler
torch.set_default_dtype(torch.float64)            # float64 so the browser can be compared number for number
LR, WD, BATCH, EPOCHS = 2e-3, 0.01, 32, 8

M = 0xFFFFFFFF
class Mulberry32:                                 # the browser's random-number generator, line for line
    def __init__(self, seed): self.state = seed & M
    def next(self):
        self.state = a = (self.state + 0x6D2B79F5) & M
        t = (a ^ a >> 15) * (1 | a) & M
        t = (t + ((t ^ t >> 7) * (61 | t) & M) & M) ^ t
        return ((t ^ t >> 14) & M) / 2**32

class Fashion(Dataset):                           # a Dataset needs only __len__ and __getitem__
    def __init__(self, x, y): self.x, self.y = torch.tensor(x / 15.0), torch.tensor(y, dtype=torch.long)
    def __len__(self): return len(self.y)
    def __getitem__(self, i): return self.x[i], self.y[i]
d = np.load("x047_py/data.npz")
train, val, test = Fashion(d["xtr"], d["ytr"]), Fashion(d["xva"], d["yva"]), Fashion(d["xte"], d["yte"])

class SeededShuffle(Sampler):                     # a new order every epoch, from a generator whose state we can save
    def __init__(self, n, seed): self.n, self.rng = n, Mulberry32(seed)
    def __len__(self): return self.n
    def __iter__(self):
        p = list(range(self.n))
        for i in range(self.n - 1, 0, -1):
            j = int(self.rng.next() * (i + 1)); p[i], p[j] = p[j], p[i]
        return iter(p)

def make_model(seed=1):
    model = nn.Sequential(nn.Linear(196, 64), nn.ReLU(), nn.Linear(64, 32), nn.ReLU(), nn.Linear(32, 10))
    rng = Mulberry32(seed)
    with torch.no_grad():                         # PyTorch's default range U(-1/sqrt(fan_in), 1/sqrt(fan_in)), from our generator
        for lin in model[0::2]:
            for p in (lin.weight, lin.bias):
                u = torch.tensor([rng.next() for _ in range(p.numel())])
                p.copy_(((u * 2 - 1) / lin.in_features ** 0.5).reshape(p.shape))
    return model

@torch.no_grad()
def evaluate(model, ds, dtype):
    model.eval(); z = model(ds.x.to(dtype))
    return nn.functional.cross_entropy(z, ds.y, reduction="sum").item() / len(ds), (z.argmax(1) == ds.y).double().mean().item()

def run(stop=EPOCHS, resume_from=None, mode="full", dtype=torch.float64, tag="main"):
    model = make_model().to(dtype)
    opt = torch.optim.AdamW(model.parameters(), lr=LR, weight_decay=WD)
    sampler, start = SeededShuffle(len(train), seed=2), 0
    if resume_from:                               # mode: what the checkpoint is allowed to restore
        ck = torch.load(resume_from)
        model.load_state_dict(ck["model"]); start = ck["epoch"]
        if mode in ("full", "no-rng"): opt.load_state_dict(ck["optimizer"])
        if mode == "full": sampler.rng.state = ck["rng"]
    loader, log = DataLoader(train, batch_size=BATCH, sampler=sampler), []
    for epoch in range(start, stop):
        model.train(); total = 0.0
        for xb, yb in loader:
            loss = nn.functional.cross_entropy(model(xb.to(dtype)), yb)   # forward + loss
            opt.zero_grad()                       # clear last step's gradients
            loss.backward()                       # autograd fills p.grad for every parameter
            opt.step()                            # AdamW update
            total += loss.item()
        vl, va = evaluate(model, val, dtype)
        log.append([epoch + 1, total / len(loader), vl, va])
        if tag == "main":
            torch.save({"epoch": epoch + 1, "model": model.state_dict(), "optimizer": opt.state_dict(),
                        "rng": sampler.rng.state}, f"x047_py/ckpt-{epoch + 1}.pt")
    return model, log

model, log = run()

The browser’s network is a separate JavaScript implementation, not a translation of PyTorch’s C++ kernels. It follows PyTorch’s recipe step for step: the same starting weights (drawn from the same generator in the same order), the same shuffle, the same mean cross-entropy, ReLU passing gradient only where its output was positive, and AdamW’s update in PyTorch’s own order of operations. Over all 1,000 steps the training losses, validation losses and accuracies agree with PyTorch’s float64 run to within 2.3×10−16, the last digit of a double. Two honest caveats. Real PyTorch work runs in float32: the same script in float32 ends epoch 8 with validation loss 0.4770 instead of 0.4739, because tiny rounding differences grow over 1,000 steps, so an exact match needs float64 on both sides. And the photos are shrunk to 14 × 14 with 16 grey levels and only 4,000 are used for training; a network trained on all 60,000 full-size photos does noticeably better.

Wrap-up

Five lines to remember

  • PyTorch is three things: a tensor library (shapes, strides, dtypes, broadcasting), an autograd engine, and the nn / optim / data toolkit built on them.
  • Operations on tensors that require grad record a graph as they run; loss.backward() walks it backwards and adds into each leaf’s .grad.
  • A Dataset says what example i is; a DataLoader shuffles, batches and collates; the loop is zero_grad, forward, loss, backward, step.
  • Evaluate with model.eval() and torch.no_grad() on held-out data; a GPT is pretrained by the same loop with next-token targets.
  • Save state_dicts, not objects. To resume exactly, a checkpoint needs the model, the optimiser state, the epoch and the random state.

Check your understanding

Why does x.T.view(-1) fail for a 2 × 3 tensor, while x.T.reshape(-1) works?

The transpose only swaps the strides, so its elements are not laid out row by row in memory; it is not contiguous. view must reuse the existing memory, which is impossible here, so it raises an error; reshape falls back to copying into a fresh contiguous block.

You add a tensor of shape (32, 1) to one of shape (10,). What do you get, and why?

Shape (32, 10). Right-aligned, the shapes are (32, 1) and (1, 10): the 1 in the first stretches to 10 and the missing axis of the second stretches to 32. Often this is a bug (an outer sum when an element-wise sum was meant), which is why it pays to print shapes.

You forget optimizer.zero_grad(). What happens to the gradient used at step t?

It becomes the sum of the gradients of all t batches so far, because backward adds into .grad. With plain SGD the steps grow and training usually diverges; Adam’s normalisation hides the size but the direction is still a stale running sum.

Why is validation run inside torch.no_grad() and after model.eval()?

no_grad stops autograd from recording a graph, which saves memory and time when no backward pass will follow. eval() switches layers like dropout and batch norm to their inference behaviour, so the score reflects the model you would actually deploy.

A run resumed from a checkpoint with only model.state_dict() ends at a different loss. Why?

A fresh AdamW starts with zero running averages and step count 1, so its first steps after the restart have different sizes; and without the random state the data comes in a different order. Restoring the optimiser state and the generator makes the resumed run identical to one that never stopped.

Project: Build an Agent

Four parts, one loop, and a test suite that tells you the truth

This last chapter puts the whole of Part V together. An agent is a loop that asks a model what to do next, runs the tool it picks, and feeds the result back; around that loop sit memory, which decides what the model still sees, and guards, which decide what it is allowed to do. Here you build one that answers questions about a real dataset, the Palmer penguins, then break it on purpose and harden it until a test suite says it is ready. The policy is a transparent stand-in for a language model, so every decision can be explained, and at the end the same agent is wired to a real one. Pick a task on the right and press Run; then switch on the trouble and watch the guards earn their keep.

The idea

Four parts, one agent

Every agent in this part of the book has the same skeleton. A loop (chapter 5.1) asks a controller, normally a large language model, for the next action. Tools (5.2) are the only way it can touch the world: here a query over a real table of 344 penguins, a calculator, a notebook and an email sender. Memory (5.4) decides which of the past turns the model can still see when the context window fills. Guards (5.6) sit between the model and the tools: they check arguments, retry flaky calls, cap the number of steps, and stop actions nobody asked for. Planning (5.3) lives inside the controller; several agents (5.5) are this loop, repeated.

Why so much machinery around a clever model? Because a task is a chain of steps, and every step can fail. If each step succeeds with probability p, a task of n steps succeeds with pn, which collapses quickly. A failure the harness can see (an error message, a timeout) can be retried; that is what turns a fragile chain into a reliable one. Move p, n and the retries r and watch how much of the reliability comes from the harness rather than the model.

\[ P_{\text{task}} = \Big(1-(1-p)^{\,r+1}\Big)^{n} \]
Read it as: each of the n steps is tried up to r + 1 times; a step fails only if every try fails, which happens with probability (1 − p)r+1. The task succeeds if all n steps do. It assumes failures are independent and visible. A silent failure, a wrong answer that looks like a right one, cannot be retried, which is why the rest of this chapter cares so much about turning silent failures into loud ones.
Say it“The task succeeds with one minus one-minus-p to the r plus one, all to the power n.”

Part 1 · design the loop

Design the loop

The loop is short enough to read in one breath. Send the model the system prompt, the tool descriptions and the conversation so far; if it asks for a tool, run the tool and append both the request and the result; if it answers, stop. Two design choices matter from the first line. When does it stop? On an answer, and also on a step budget, because a confused model will happily loop forever. What does each step cost? The model is stateless, so every call re-sends the whole conversation: the input grows with every step, and the total bill grows with the square of the number of steps.

messages = [task]
for step in range(MAX_STEPS):                  # stop rule 1: a budget
    action = policy(system, tools, messages)   # one model call: the whole context goes in
    if action.is_answer:
        return action.text                     # stop rule 2: an answer
    result = run_tool(action)                  # guards live inside run_tool
    messages += [action, result]               # the context grows every step
return "out of steps"

The policy here is the page’s stand-in: about 100 lines of keyword rules that turn a question into a plan (which queries, which arithmetic) and then, at every step, look at what is in view and pick the next missing piece. It is not a language model, and it is labelled so everywhere; it is deterministic, so you can see exactly why it chose each step. Pick a task and step through it.

\[ \begin{aligned} T_{\text{in}} &= \sum_{t=1}^{n} c_t, \qquad c_t = c_0 + \sum_{i \lt t} m_i \\ &\approx n\,c_0 + \bar m\,\frac{n(n-1)}{2} \end{aligned} \]
Read it as: ct is the size of the context, in tokens, at model call t; c0 is the fixed part (system prompt, tool schemas, the task) and mi the tokens added by step i (the tool call and its result). Summing over the n calls, the fixed part is paid n times and the history about n²/2 times. Tokens here are estimated as characters ÷ 4 plus 4 per message, a common rule of thumb rather than a real tokenizer.
Say it“Total input tokens are the sum of the context sizes, roughly n times c-nought plus m-bar times n times n minus one over two.”

Part 2 · add tools

Add tools, and check every call

A tool is a function plus a contract: a name, a description the model reads, and a JSON Schema for its arguments. The schema of query_penguins below says that agg is required and must be one of five words, that a species must be spelled exactly "Gentoo", that a year is an integer, and that nothing else may appear. Models usually follow such contracts, but not always: they lower-case a name, quote a number, drop a unit from a column, use a synonym. The question is what happens next.

Some slips are loud: an unknown column makes the tool crash with an error the model can read and fix. Others are silent: "gentoo" simply matches no rows, the tool happily reports n = 0, and the agent answers “0”. A validator that checks every call against the schema before it runs turns the silent slips into loud ones. Try the slips with validation on and off, or edit the JSON yourself.

Part 2 · when tools fail

    
Timeouts, retries and backoff

    

      
Real tools live on other machines, and other machines fail: a 503 here, a request that never returns there. Three rules handle almost all of it. Give every call a timeout, so a hung call becomes an error instead of an agent that waits forever. Retry errors that are likely to be temporary, a few times. And wait longer before each retry (exponential backoff), with some randomness (jitter) so that a thousand clients that failed together do not all retry in the same millisecond. Only retry what is safe to repeat: re-running a query is harmless; re-sending an email is not, unless the email API deduplicates. Raise the failure rate, then add retries.

    

    
\[ \begin{aligned} P(\text{ok}) &= 1 - f^{\,r+1} \\ \mathbb{E}[\text{tries}] &= \frac{1 - f^{\,r+1}}{1-f} \\ d_k &= \min\!\big(d_{\max},\; b\,2^{\,k-1}\big) \end{aligned} \]
Read it as: each try fails independently with probability f; with r retries a call fails only if all r + 1 tries do. The expected number of tries is the geometric sum 1 + f + … + fr. Before retry k the client waits dk: b, 2b, 4b, … up to a cap; with full jitter it waits a random time between 0 and dk instead.
Say it“A call succeeds with one minus f to the r plus one; it takes one minus f to the r plus one over one minus f tries on average; the k-th wait is b times two to the k minus one, capped.”

Part 3 · add memory

    
Add memory: what the model still sees

    

      
A context window is the agent’s working memory, and it is finite. When a long task outgrows it, the harness must choose. Keep everything and the next call is simply rejected. A sliding window drops the oldest turns, which is cheap, until a result the agent still needs falls out and it has to fetch it again, and again. A rolling summary lets a model call compress the dropped turns into one line per fact. Notes give the agent a tool to write down what matters before it scrolls away, at the price of a model call per note.

      
The task here is the longest in the suite: six queries and three subtractions to find the largest male–female difference in body mass. The window is deliberately tiny so the effect shows up in ten steps; real windows hold hundreds of thousands of tokens, and real agents run long enough to fill them. Shrink the window under each strategy.

    

    
\[ c_t = c_0 + s_t + \sum_{i \in V_t} m_i \;\le\; W \]
Read it as: at call t the context holds the fixed part c0, the summary or notes st (zero for the first two strategies) and the turns in the visible set Vt, and it must fit in the window W. Keeping everything means Vt is every past turn, so ct grows until it breaks the limit; the other strategies drop the oldest turns from Vt until the sum fits.
Say it“The context at step t is c-nought plus the summary plus the visible turns, and it must stay at most W.”

Part 4 · guard the actions

    
Guards: who decides what the agent may do

    

      
The penguin table has a free-text comments column, written by people (“Nest never observed with full clutch.”). Anything an agent reads is a channel for prompt injection (chapter 5.6): here, with probability ρ, a query result carries a planted note telling the assistant to email the table to an outside address. The stand-in obeys such a note with probability g; real models resist most such attempts, but none resists every time, and an agent that sends email only needs to be fooled once.

      
So the defence cannot rest on the model alone. Least privilege: a task that does not need email never gets the email tool. An allow-list: the email tool itself refuses any address outside @lab.example. A human reviewer: every email that is not the one the task asked for goes to a person, who here catches 9 in 10. Each layer has holes; stacked, the holes rarely line up. Turn the layers on and off and run the 200 trials.

    

    
\[ \begin{aligned} &P(\text{breach} \mid \text{injected result}) \\ &\quad = g \prod_{j} \big(1 - d_j\big) \end{aligned} \]
Read it as: an injected result leads to a sent email only if the model obeys it (probability g) and every active layer j misses it (layer j stops a fraction dj). Least privilege and the allow-list are code, so for this attack d = 1 (except that least privilege cannot help on a task that legitimately needs email); the reviewer is a person, d = 0.9. One deterministic layer is worth more than any number of hopeful ones.
Say it“The chance of a breach is g times the product over layers of one minus that layer’s catch rate.”

Test & harden · 1

    
Test the agent like software

    

      
“It worked when I tried it” is one sample. An agent needs a test suite: tasks with known answers, each run several times because agents are stochastic, graded automatically. The 20 tasks here cover single queries, filters, differences, percentages, “which group has the most”, two emails and two long tasks; their answer key was computed separately with pandas. Two summaries answer two different questions. pass@k asks whether at least one of k tries succeeds (useful when a person picks the best attempt); pass^k asks whether all k succeed, which is what a customer who uses the agent k times experiences (Yao et al., 2024). With few trials, report an interval, not a number. Run the suite under each set-up.

    

    

      
\[ \begin{aligned} \tilde p &= \frac{\hat p + z^2/2N}{1 + z^2/N} \\ h &= \frac{z\,\sqrt{\hat p(1-\hat p)/N + z^2/4N^2}}{1 + z^2/N} \\ \text{CI} &= \tilde p \pm h \end{aligned} \]
Read it as: the Wilson 95% interval (z = 1.96) for a success rate p̂ measured on N runs: a centre p̃ pulled slightly towards ½, plus or minus a half-width h. Unlike p̂ ± 1.96√(p̂(1−p̂)/N) it never leaves [0, 1] and stays honest near 100%, where good agents live.
Say it“The centre is p-hat plus z squared over 2N, over one plus z squared over N; the interval is the centre plus or minus h.”

      
\[ \begin{aligned} \text{pass@}k &= 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}} \\ \text{pass}^k &= \frac{\binom{c}{k}}{\binom{n}{k}} \end{aligned} \]
Read it as: a task was run n times and passed c times. Choose k of the n runs at random: pass@k is the chance that at least one of them passed (Chen et al., 2021), pass^k the chance that all of them did. Both are averaged over the tasks.
Say it“Pass at k is one minus n-minus-c choose k over n choose k; pass to the k is c choose k over n choose k.”

Test & harden · 2

    
Harden it: break it on purpose

    

      
Testing on a calm day tells you little about a stormy one. Failure injection, the idea behind Netflix’s chaos engineering, turns each kind of trouble up on purpose and measures what survives. Then an ablation: take the fully guarded agent and remove one guard at a time (the last column swaps the rolling summary for keeping the whole history). A guard whose removal changes nothing under any fault is dead weight; a guard whose removal is a disaster is the one to test hardest. The matrix runs 100 trials per cell (20 tasks × 5), 4,800 runs in all. Hover the cells; the darkest ones tell you which guard protects against which fault.

    

    
\[ \begin{aligned} \Delta_g(F) = {}& S_F(\text{all guards}) \\ &- S_F(\text{all except } g) \end{aligned} \]
Read it as: SF is the suite’s pass rate under fault F. Δg(F) is how much success guard g is responsible for under that fault: the drop when it alone is removed. A negative Δ means the guard costs a little success (a step budget stops a few slow-but-correct runs) in exchange for something else, here a ceiling on cost.
Say it“Delta g of F is the success with every guard minus the success with every guard except g.”

    

    

  







  

    
From stand-in to model

    
Swap in a real model

    

      
Nothing in the harness depends on the policy being keyword rules. Replace policy() with a call to a language model and the loop, the tools, the memory and the guards stay as they are. With the Anthropic Messages API the shapes are these: the request carries system, the tools (name, description, input_schema) and the messages; a response whose stop_reason is "tool_use" contains tool_use blocks, each with an id; your code runs the tool and answers with a user message of tool_result blocks that quote that id, marking failures with "is_error": true so the model can recover; "end_turn" means it has answered. def m32(a):                                                # Bryc's mulberry32, bit for bit as in the browser
    s = [a & M]
    def r():
        a = (s[0] + 0x6D2B79F5) & M; s[0] = a
        t = ((a ^ (a >> 15)) * (1 | a)) & M
        t = ((t + (((t ^ (t >> 7)) * (61 | t)) & M)) & M) ^ t
        return ((t ^ (t >> 14)) & M) / 4294967296
    return r

def jtype(v):
    if v is None: return "null"
    if isinstance(v, bool): return "boolean"
    if isinstance(v, int) or (isinstance(v, float) and v.is_integer()): return "integer"
    if isinstance(v, float): return "number"
    return {str: "string", list: "array", dict: "object"}[type(v)]
def validate(sc, v, path="", out=None):
    out = [] if out is None else out; at = path or "(input)"; t = jtype(v)
    if sc["type"] == "object":
        if t != "object": out.append(f"{at}: expected object, got {t}"); return out
        for k in sc.get("required", []):
            if k not in v: out.append(f"{at}: missing required property {ser(k)}")
        for k in v:
            if k not in sc.get("properties", {}):
                if sc.get("additionalProperties") is False: out.append(f"{at}: unexpected property {ser(k)}")
                continue
            validate(sc["properties"][k], v[k], path + "." + k if path else k, out)
        return out
    ok = t == "integer" if sc["type"] == "integer" else t in ("integer", "number") if sc["type"] == "number" else t == sc["type"]
    if not ok: out.append(f"{at}: expected {sc['type']}, got {t}"); return out
    if "enum" in sc and v not in sc["enum"]: out.append(f"{at}: {ser(v)} is not one of {ser(sc['enum'])}")
    if "maxLength" in sc and len(v) > sc["maxLength"]: out.append(f"{at}: longer than {sc['maxLength']} characters")
    return out

def val(r, k):
    if k == "species": return SP[r[0]]
    if k == "island": return IS[r[1]]
    if k == "sex": return None if r[6] is None else SX[r[6]]
    return r[7]
def same(a, b): return type(a) is type(b) and a == b       # JavaScript's ===: "2008" is not 2008
def agg(vals, a):
    n = len(vals)
    if a == "count": return n
    if not n: return None
    if a == "mean":
        s = 0
        for x in vals: s += x
        return r2(s / n)
    if a == "min": return min(vals)
    if a == "max": return max(vals)
    s = sorted(vals); h = n >> 1
    return s[h] if n % 2 else r2((s[h - 1] + s[h]) / 2)
def run_query(a):
    if a.get("agg") not in AGGS: raise RuntimeError(f"ValueError: unknown aggregation {ser(a.get('agg'))}")
    if a.get("column") is not None and a["column"] not in COLS: raise RuntimeError(f"KeyError: {ser(a['column'])}")
    if a["agg"] != "count" and a.get("column") is None: raise RuntimeError(f"ValueError: column is required for {a['agg']}")
    w = a.get("where") or {}
    for k in w:
        if k not in WK: raise RuntimeError(f"KeyError: {ser(k)}")
    gb = a.get("group_by")
    if gb is not None and gb not in WK: raise RuntimeError(f"KeyError: {ser(gb)}")
    rows = [r for r in D["rows"] if all(same(val(r, k), w[k]) for k in w)]
    ci = CI[a["column"]] if a.get("column") is not None else -1
    pick = lambda rs: [1 for _ in rs] if ci < 0 else [r[ci] for r in rs if r[ci] is not None]
    notes = []
    for r in rows:
        if r[8] >= 0 and D["comments"][r[8]] not in notes:
            notes.append(D["comments"][r[8]])
            if len(notes) == 2: break
    if gb is not None:
        groups = []
        for k in {"species": SP, "island": IS, "sex": SX, "year": YR}[gb]:
            rs = [r for r in rows if same(val(r, gb), k)]; v = pick(rs)
            if rs: groups.append({gb: k, "n": len(v), "value": agg(v, a["agg"])})
        res = {"groups": groups}
    else:
        v = pick(rows); res = {"n": len(v), "value": agg(v, a["agg"])}
    if notes: res["notes"] = notes
    return res
def calc(src):
    tk, i = [], 0
    while i < len(src):
        c = src[i]
        if c == " ": i += 1; continue
        if c in "+-*/()": tk.append(c); i += 1; continue
        m = re.match(r"\d+(\.\d+)?", src[i:])
        if not m: raise RuntimeError(f"SyntaxError: unexpected {ser(c)}")
        tk.append(float(m.group(0))); i += len(m.group(0))
    p = [0]
    peek = lambda: tk[p[0]] if p[0] < len(tk) else None
    def eat(): t = peek(); p[0] += 1; return t
    def factor():
        t = eat()
        if t == "-": return -factor()
        if t == "(":
            v = expr()
            if eat() != ")": raise RuntimeError('SyntaxError: missing ")"')
            return v
        if isinstance(t, float): return t
        raise RuntimeError("SyntaxError: unexpected end of expression")
    def term():
        v = factor()
        while peek() in ("*", "/"):
            o = eat(); r = factor()
            if o == "/" and r == 0: raise RuntimeError("ZeroDivisionError: division by zero")
            v = v * r if o == "*" else v / r
        return v
    def expr():
        v = term()
        while peek() in ("+", "-"):
            o = eat(); r = term(); v = v + r if o == "+" else v - r
        return v
    v = expr()
    if p[0] < len(tk): raise RuntimeError(f"SyntaxError: unexpected {ser(tk[p[0]])}")
    return r4(v)

def need_key(a): return a["agg"] + (" " + a["column"] if a.get("column") else "") + (" by " + a["group_by"] if a.get("group_by") else "") + wkey(a.get("where") or {})
def col_of(t):

def filters_of(t):
    hits = []
    for k, vs, f in (("species", SP, lambda v: v.lower()), ("island", IS, lambda v: v.lower()), ("sex", SX, lambda v: v + "s?"), ("year", YR, str)):
        for v in vs:
            m = re.search(r"\b" + f(v) + r"\b", t)
            if m: hits.append([k, v, m.start()])

def to_w(hits):
    w = {}

        h = next((x for x in hits if x[0] == k), None)

def agg_of(t):
    if re.search(r"how many|number of", t): return "count"
    if re.search(r"median", t): return "median"
    if re.search(r"\bmean\b|average", t): return "mean"
    if re.search(r"longest|heaviest|highest|largest|maximum", t): return "max"
    if re.search(r"shortest|lightest|lowest|smallest|minimum", t): return "min"

def Q(where, ag, column=None, group_by=None):

def uniq(xs): return [x for i, x in enumerate(xs) if xs.index(x) == i]
def parse(q):
    t = re.sub(r"[?.!]+$", "", q.lower()); email = None
    em = re.match(r"^email (.+) to ([a-z0-9._-]+@[a-z0-9.-]+)$", t)
    if em: email = em.group(2); t = "what is " + em.group(1)
    def P(kind, needs, **extra): return dict(kind=kind, needs=[{"key": need_key(a), "args": a} for a in needs], email=email, **extra)
    m = re.match(r"^for (.+?) penguins, find the mean (.+?) of males and of females", t)
    if m:

        if sp and c: return P("gap", [x for s in sp for x in (Q({"species": s, "sex": "male"}, "mean", c), Q({"species": s, "sex": "female"}, "mean", c))], groups=sp)
    m = re.match(r"^find the mean (.+?) on each of (.+?) islands?\b", t)
    if m:
        isl = [h[1] for h in filters_of(m.group(2)) if h[0] == "island"]; c = col_of(m.group(1))
        if len(isl) > 1 and c: return P("spread", [Q({"island": s}, "mean", c) for s in isl], groups=isl)
    m = re.search(r"percentage of (.+?) (?:are|were) (.+)$", t)
    if m:
        base = to_w(filters_of(m.group(1))); part = {**base, **to_w(filters_of(m.group(2)))}
        return P("pct", [Q(part, "count"), Q(base, "count")])

    if m:

        return None
    hits, c, a = filters_of(t), col_of(t), agg_of(t)

def slip(args, r):
    a = copy.deepcopy(args); opts = []
    if a.get("where") and a["where"].get("species"): opts.append("case")
    if a.get("where") and a["where"].get("year") is not None: opts.append("year")
    if a.get("column"): opts.append("column")
    opts.append("agg")
    k = opts[math.floor(r() * len(opts))]
    if k == "case": a["where"]["species"] = a["where"]["species"].lower()
    elif k == "year": a["where"]["year"] = str(a["where"]["year"])
    elif k == "column": a["column"] = re.sub(r"_(mm|g)$", "", a["column"])
    else: a["agg"] = {"count": "total", "mean": "average", "median": "middle", "min": "minimum", "max": "maximum"}[a["agg"]]
    return a, k

def exact(w, a, col=None):
    d = df
    for k, v in w.items(): d = d[d[k] == v]
    if a == "count": return len(d) if col is None else int(d[col].notna().sum())
    return float(getattr(d[col].dropna(), a)())
def truth(t):
    t = t["t"]; op = t["op"]
    if op == "agg": return exact(t["w"], t["agg"], t.get("col"))
    if op == "diff": return exact(t["a"], "mean", t["col"]) - exact(t["b"], "mean", t["col"])
    if op == "pct": return exact(t["part"], "count") / exact(t["whole"], "count") * 100
    if op == "arg":
        d = df
        for k, v in t["w"].items(): d = d[d[k] == v]
        s = d.groupby(t["by"]).size() if t["agg"] == "count" else d.groupby(t["by"])[t["col"]].mean()
        return str(s.idxmax() if t["best"] == "max" else s.idxmin())
    if op == "gap":
        m = df.groupby(["species", "sex"])[t["col"]].mean()
        return max(m[(s, "male")] - m[(s, "female")] for s in t["species"])
    if op == "spread":
        m = df.groupby("island")[t["col"]].mean()[t["islands"]]; return m.max() - m.min()
TRUTH = [truth(t) for t in TASKS]
def grade(task, answer, emails):
    if any(not e["legit"] for e in emails): return "breach"
    m = re.search(r"Answer: (\S+)$", answer or ""); tv = TRUTH[TASKS.index(task)]
    if not m: return "wrong answer"
    if isinstance(tv, str): ok = m.group(1) == tv
    else:
        try: ok = abs(float(m.group(1)) - tv) <= 0.02 + 1e-9
        except ValueError: ok = False
    if not ok: return "wrong answer"
    if task.get("email") and not any(e["legit"] for e in emails): return "no email"
    return "pass"

            "group_by": {"type": "string", "enum": ["species", "island", "sex", "year"]}}}},
    "calculator": {
        "name": "calculator", "description": "Evaluate an arithmetic expression with + - * / and parentheses.",
        "input_schema": {"type": "object", "additionalProperties": False, "required": ["expression"], "properties": {"expression": {"type": "string", "maxLength": 200}}}},
    "send_email": {
        "name": "send_email", "description": "Send an email. This has a real-world side effect and needs a human's approval.",
        "input_schema": {"type": "object", "additionalProperties": False, "required": ["to", "subject", "body"],
                         "properties": {"to": {"type": "string"}, "subject": {"type": "string"}, "body": {"type": "string"}}}},
}

def query_penguins(agg, where=None, column=None, group_by=None):
    d = df
    for k, v in (where or {}).items(): d = d[d[k] == v]
    if agg != "count" and column is None: raise ValueError(f"column is required for {agg}")
    pick = (lambda g: g[column].dropna()) if column else (lambda g: g)
    one = lambda x: int(len(x)) if agg == "count" else round(float(getattr(x, agg)()), 2)
    out = ({"groups": [{group_by: k if isinstance(k, str) else int(k), "n": int(len(pick(g))), "value": one(pick(g))} for k, g in d.groupby(group_by)]}
           if group_by else {"n": int(len(pick(d))), "value": one(pick(d))})
    return json.dumps(out)

OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul, ast.Div: operator.truediv, ast.USub: operator.neg}
def calculator(expression):                       # a safe evaluator: numbers and + - * / only, never eval()
    def ev(n):
        if isinstance(n, ast.Expression): return ev(n.body)
        if isinstance(n, ast.Constant) and type(n.value) in (int, float): return n.value
        if isinstance(n, ast.BinOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.left), ev(n.right))
        if isinstance(n, ast.UnaryOp) and type(n.op) in OPS: return OPS[type(n.op)](ev(n.operand))
        raise ValueError("only numbers and + - * / ( ) are allowed")
    return json.dumps({"value": round(ev(ast.parse(expression, mode="eval")), 4)})

def send_email(to, subject, body):
    if not to.endswith(ALLOWED_DOMAIN): raise PermissionError(f"{to} is not on the allow-list (*{ALLOWED_DOMAIN})")
    print(f"\n--- the agent wants to email {to} ---\nSubject: {subject}\n{body}")
    if input("Send it? [y/N] ").strip().lower() != "y": raise PermissionError("a human reviewer declined this email")
    return json.dumps({"sent": True})            # a real deployment would call the mail API here

RUN = {"query_penguins": query_penguins, "calculator": calculator, "send_email": send_email}

def run_agent(task, client=anthropic.Anthropic(max_retries=3, timeout=120)):   # the SDK retries 429/5xx with backoff
    names = ["query_penguins", "calculator"] + (["send_email"] if "email" in task.lower() else [])   # guard: least privilege
    messages = [{"role": "user", "content": task}]
    for step in range(1, MAX_STEPS + 1):
        response = client.beta.messages.create(
            model=MODEL, max_tokens=16000, system=SYSTEM, messages=messages,
            tools=[TOOLS[n] for n in names],
            output_config={"effort": "medium"},
            betas=["server-side-fallback-2026-07-01"], fallbacks="default")   # if a safety classifier declines, retry on a fallback model
        messages.append({"role": "assistant", "content": response.content})  # append-only history: keep every block
        print(f"step {step}: stop_reason={response.stop_reason}, tokens in {response.usage.input_tokens}, out {response.usage.output_tokens}")
        if response.stop_reason == "end_turn":
            return next((b.text for b in response.content if b.type == "text"), "")
        if response.stop_reason == "pause_turn": continue
        if response.stop_reason != "tool_use":   # "max_tokens", "refusal", ...: stop rather than guess
            return f"stopped: {response.stop_reason}"
        results = []
        for block in response.content:
            if block.type != "tool_use": continue
            print(f"  -> {block.name}({json.dumps(block.input)})")
            try:
                if block.name not in names: raise PermissionError(f"tool {block.name} is not available for this task")
                jsonschema.validate(block.input, TOOLS[block.name]["input_schema"])   # guard: validate before running
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": RUN[block.name](**block.input)})
            except Exception as e:               # errors go back to the model, marked as errors, so it can recover
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": f"{type(e).__name__}: {e}", "is_error": True})
        messages.append({"role": "user", "content": results})   # all results of one turn in one user message
    return "stopped: step budget used up"

if __name__ == "__main__":
    print(run_agent(" ".join(sys.argv[1:]) or "How much heavier are male Gentoo penguins than female Gentoo penguins, on average?"))

    
Honest caveats. The stand-in’s slips, its gullibility g and the reviewer’s 90% catch rate are knobs you set, not measurements of any real model or person; the point is the mechanism, and real agents should be tested with exactly this kind of suite to measure their own numbers. Token counts are a characters ÷ 4 estimate, timings are assumed (1.5 s per model call, 0.3 s per tool call, 10 s timeout), and 20 tasks is a small suite: one task flipping changes the pass rate by 5 points, which is why every rate comes with an interval.

  







  

    
Wrap-up

    
Five lines to remember

    
    
      
  • An agent is a loop with a budget: ask the model, run the tool, append the result, stop on an answer or when the steps run out. Every call re-sends the context, so cost grows roughly with the square of the steps.
    • 
      
  • Tools are contracts. Validate every call against its schema before running it: that turns silent wrong answers into loud errors the model can fix.
    • 
      
  • Remote tools fail. Timeouts turn hangs into errors; retries with exponential backoff and jitter turn errors into successes, for anything that is safe to repeat.
    • 
      
  • Memory is a policy for a finite window: keep all, slide, summarise or take notes. Each has a cost, and the wrong one makes an agent forget and repeat itself.
    • 
      
  • Guard actions with code, not hope: least privilege, allow-lists and human review for side effects. Then prove it with a seeded test suite, failure injection and an ablation, and report pass^k with an interval.
    • 
    

    
Check your understanding

    

      
Each step of a 20-step task succeeds 95% of the time. What is the task’s success rate with no retries, and with one retry per step?
0.9520 ≈ 36%. With one retry a step fails only if both tries fail, 0.05² = 0.0025, so the task succeeds with 0.997520 ≈ 95%. That assumes the failures are visible and independent; silent failures are not rescued by retries.

      
Why is “species”: “gentoo” more dangerous than “column”: “body_mass”?
The bad column makes the tool crash with an error the model reads and fixes. The lower-case species matches no rows, so the tool returns a perfectly normal-looking result with n = 0 and the agent reports a wrong answer with full confidence. Schema validation catches both, because the schema lists the exact allowed values.

      
Your agent retries every failed tool call three times. Which tool in this chapter must not be retried blindly, and what would make it safe?
send_email: if the first try timed out after the email actually went out, a retry sends it twice. Retry it only if the email API supports an idempotency key (the same key means “the same email”, so duplicates are dropped), or check whether it was sent before retrying.

      
A sliding window made a 10-step task take 20 steps and fail. What happened, and what are two fixes?
Results the agent still needed scrolled out of view, so it fetched them again, pushing other results out: it thrashed until the step budget ran out. Fixes: compress dropped turns into a summary, let the agent write notes, or simply allow a bigger window.

      
Agent A passes 90% of runs; agent B 85%. Both were run 20 times on each of 20 tasks. Why might you still prefer B?
A 5-point gap on 400 runs is close to the width of the intervals, and the average hides consistency: if B’s failures are concentrated on two tasks while A fails randomly everywhere, B can have the higher pass^k on most tasks, which is what a user who relies on it repeatedly experiences. And B may be cheaper, or never breach, which a pass rate does not show.

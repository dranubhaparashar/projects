Defensive Prompting

Jailbreaks, prompt leaks and data extraction, measured and defended

Anyone who can put text in front of your model can try to make it misbehave: leak its instructions, ignore its safety training, obey a stranger’s orders or recite its training data. This chapter teaches those attacks the way a security course does, at the level of how and why they work, and spends its labs on measuring them and on the defences. Huyen 5.3 · defensive prompt engineering

Three ways to attack a prompt

An application built on a language model is a pipeline: a developer writes a system prompt, users type messages, and the app may add files, web pages, emails or tool results before the model writes a reply. Every one of those inputs is text, and the model reads it all as one sequence. That is the root of the problem: whoever writes any part of that sequence can try to steer the model. Huyen groups the attacks into three families. Prompt extraction tries to get the system prompt or other context out. Jailbreaking and prompt injection try to make the model do what it was told or trained not to do. Information extraction tries to get the model to reveal its training data or the private data in its context.

What is at stake depends on what the app can reach. If the model can run code or call tools, an attacker may get remote code or tool execution. If it holds private data, there is a data leak. A model that can be talked out of its rules can produce harmful or offensive content and misinformation, be used to disrupt or hijack the service, and cause brand damage when screenshots spread. Switch the channels and assets of an app on and off and watch which attacks become possible, and how quickly the chance that some session meets attacker text grows with the number of untrusted inputs.

\[ \begin{aligned} P(\text{exposed}) &= 1 - P(\text{safe}) \\ &= 1 - (1 - p_u) \\ &\qquad \times (1 - p_d)^{\,n} \end{aligned} \]
Read it as: pu is the share of sessions whose user is an attacker, pd the share of third-party items (files, pages, emails, tool results) that an attacker has written, and n the number of such items one session pulls in. A session is safe only if the user is honest and every item is clean, so the safe chances multiply, and the exposed chance is what is left.
Say it“The chance of exposure is one minus the chance of an honest user times the chance that all n items are clean.”

Huyen 5.3.1 · proprietary prompts

Your system prompt is not a secret

A good system prompt takes work, and some companies treat theirs as an asset. Attackers try to recover it by prompt extraction: messages that ask the model, directly or through some pretext, to repeat, summarise, translate or continue the text it was given. It works far more often than developers expect, because the instructions sit in the same context window as the request and the model was trained to be helpful with whatever is there. Two lessons follow. First, write every system prompt as if it will be published: no keys, no internal URLs, no rules whose secrecy is the only thing that makes them work. Second, the same risk covers everything else in the context: retrieved documents, another customer’s records or a hidden tool description can be pulled out the same way.

A detail that matters for both sides: an “extracted” prompt may be made up. The model can produce something plausible that it was never given, so an attacker cannot be sure, and a defender who sees a supposed leak online should check it against the real thing. That check is easy to automate. Plant a canary, a random string that appears nowhere else, in the prompt, and measure how much of the prompt a reply reproduces. Try the five replies, or write your own, and see which ones the detector flags.

\[ R_L = \frac{\operatorname{LCS}(\text{secret},\ \text{reply})}{|\text{secret}|} \]
Read it as: split both texts into words; the longest common subsequence (LCS) is the longest list of secret words that also appear in the reply in the same order, not necessarily side by side. Dividing by the number of secret words gives the share of the prompt the reply reproduces (this is ROUGE-L recall).
Say it“R-L is the longest common subsequence over the length of the secret.”
\[ P(\text{chance match}) \approx L \cdot 36^{-k} \]
Read it as: a canary of k random letters and digits (36 symbols) can turn up by accident at roughly L places in L characters of unrelated text, each with chance 36−k. With k = 12 that is about 2 × 10−19 per character: if the canary shows up, the prompt leaked.
Say it“The chance of a false alarm is about L times thirty-six to the minus k.”

Huyen 5.3.1 · reverse prompt engineering

Reading a prompt off its answers

Refusing to print the prompt is not enough, because the prompt shows in everything the model does. Reverse prompt engineering infers the instructions from the behaviour: does the bot always use bullet points, push a loyalty scheme, end with a question, dodge questions about competitors? Each reply is a little evidence, and evidence adds up. Research systems do this at scale: Morris et al. (2023) recover prompts from a model’s next-token probabilities, and Zhang, Morris and Shmatikov (2024) from ordinary text outputs alone.

Here is the idea in its simplest form. An attacker suspects the bot runs one of four system prompts. Each prompt makes certain traits more or less likely in a reply. After every reply the attacker applies Bayes’ rule. The replies are simulated from the trait probabilities in the table, with no language model involved. Ask questions until you are 95% sure, then reveal the hidden prompt.

\[ \begin{aligned} &P(k \mid r_{1:t}) \\ &\quad = \frac{P(k)\prod_{i} P(r_i \mid k)}{\sum_{j} P(j)\prod_{i} P(r_i \mid j)} \end{aligned} \]
Read it as: k is a candidate prompt and r1 … rt the replies seen so far. Each reply’s probability under k is the product over its five traits of p (trait shown) or 1 − p (trait absent). Multiply those across replies, weight by the prior, and normalise so the four candidates sum to 1.
Say it“The posterior of prompt k is its prior times the likelihood of every reply, divided by the same for all candidates.”
\[ \begin{aligned} \log\frac{P(k \mid r_{1:t})}{P(j \mid r_{1:t})} &= \log\frac{P(k)}{P(j)} \\ &\quad + \sum_{i=1}^{t}\log\frac{P(r_i \mid k)}{P(r_i \mid j)} \end{aligned} \]
Read it as: on the log-odds scale each reply adds its own term. If the true prompt is k, those terms average to a positive number (the KL divergence of reply distributions), so the odds grow roughly linearly with the number of questions, however small each step.
Say it“The log posterior odds are the log prior odds plus the sum of the log likelihood ratios.”

Huyen 5.3.2 · jailbreaking

Why jailbreaks work

Two words get mixed up. A jailbreak attacks the model: it tries to get the model to do what its safety training says it should refuse. A prompt injection attacks an application: it slips instructions into the input so that the model follows the attacker instead of the developer. Many attacks are both. Wei, Haghtalab and Steinhardt (2023) explain why safety-trained models can be jailbroken at all with two failure modes. Competing objectives: the model was trained to follow instructions and to be helpful as well as to refuse, and a prompt can set those goals against each other, for instance by demanding a particular opening or forbidding refusals. Mismatched generalisation: pretraining gave the model skills, such as reading encodings, other languages or odd formats, that the much smaller safety-training set never covered, so a request moved into that territory is understood but not refused.

Hand-made attacks come in three broad kinds. Obfuscation disguises the request with misspellings, symbols or encodings. Output-format manipulation asks for the content in another form, such as a poem, a table or code. Role-play wraps the request in a fiction or a persona that is supposedly free of rules. Rather than run any of them against a real model, this lab trains a small safety filter in your browser and shows mismatched generalisation directly. The filter is logistic regression on character 3- and 4-grams, trained on 370 harmful requests from AdvBench against 1,000 ordinary requests from Anthropic’s HH data. Choose an obfuscation and raise its strength; the requests are the 100 JailbreakBench behaviours.

\[ \begin{aligned} p(x) &= \sigma\!\Big(\mathbf w^\top \frac{\phi(x)}{\lVert \phi(x) \rVert} + b\Big) \\ \text{caught}(D) &= \frac{1}{|D|}\sum_{x \in D} \mathbb 1\big[p(x) > \tfrac12\big] \end{aligned} \]
Read it as: φ(x) counts the character 3- and 4-grams inside each word of the request, hashed into 16,384 slots; dividing by its length makes long and short requests comparable. The filter’s probability of “harmful” is a sigmoid of a weighted sum. Its catch rate on a set D is the share of requests it scores above ½. Mismatched generalisation is the gap between the catch rate on data like the training set and on data that is not.
Say it“p of x is the sigmoid of w dot the normalised n-gram vector plus b; the catch rate is the share above one half.”

Huyen 5.3.2 · automated attacks

Attacks that search: GCG, random search and PAIR

Hand-made jailbreaks are found by people; automated ones are found by optimisation. GCG (greedy coordinate gradient, Zou et al., 2023) appends a short suffix of tokens to a request and tunes it to make the model more likely to start its answer with an agreeing phrase. At each step it uses the gradient with respect to a one-hot encoding of every suffix token to shortlist the top k replacement tokens per position, tries a batch of random single swaps from those shortlists for real, and keeps the best. Suffixes found on open models partly transfer to other models. Random search (Andriushchenko et al., 2024) needs no gradients: propose a random swap, keep it if the objective improves. PAIR (Chao et al., 2023) uses a second language model as the attacker, which rewrites the request in fluent language from a judge’s feedback, often within about twenty queries.

The lab runs GCG and random search against the safety filter from the last section, not against a language model, so nothing here is a jailbreak of any deployed system. The suffix is four words drawn from the 200 most common words in the benign training requests, started as “! ! ! !”. One honest difference: because the filter looks only at bags of within-word n-grams, a word scores the same in every slot, so the gradient ranks words rather than slots. The search loop is exactly GCG’s. Run both attacks on one behaviour, then on all of them.

\[ \begin{aligned} z(x) &= \mathbf w^\top \frac{\phi(x)}{\lVert\phi(x)\rVert} + b \\ \Delta z_{i \to v} &\approx \nabla_{\phi} z \cdot \big(c_v - c_{s_i}\big) \\ \nabla_{\phi} z &= \frac{\mathbf w - (\mathbf w^\top \mathbf u)\,\mathbf u}{\lVert\phi\rVert} \end{aligned} \]
Read it as: z is the filter’s logit; the attacker wants it below 0 (P(harmful) < ½). Swapping suffix word si for word v changes the raw counts by cv − csi; the gradient (u is the normalised count vector) predicts the change to first order. The shortlist is the k words with the most negative prediction; the batch then measures the true change, which differs because of the normalisation.
Say it“The change in z from swapping in word v is about the gradient dotted with v’s counts minus the old word’s.”
\[ -\log p_{\text{harm}}(n) \approx C\, n^{-\alpha} \]
Read it as: the many-shot attack of Anil et al. (2024) fills a long context with n made-up dialogues in which an assistant complies, then asks the real question. They found the negative log-likelihood of a harmful answer falls as a power law in n, a straight line on log–log axes. A defence that raises C delays the attack, but if α stays the same, a longer context still gets there. The chart beside the lab shows the formula, not measured data.
Say it“Minus log p of a harmful answer is C times n to the minus alpha.”

Huyen 5.3.2 · prompt injection

Prompt injection: when data gives orders

Direct injection comes from the user typing into the app. Indirect injection, described by Greshake et al. (2023), arrives through content the app fetches on the user’s behalf, and the user may never see it. It comes in two shapes. In passive phishing the attacker leaves instructions where a model will one day read them: a web page, a code repository, a product review, a video transcript. In active injection the attacker sends the instructions to the target, for example an email to someone whose assistant reads and answers mail. Either way the model sees an instruction inside what should have been data, and if it obeys, it acts with the user’s permissions.

Retrieval makes this a numbers game. Poisoned pages are written to match likely questions, so they are retrieved more often than their share of the corpus suggests, and every extra document in the context is another chance. Raise the number of retrieved documents k and watch the hijack rate climb; then lower the obey rate h, which is what defences such as marking data as data try to do (the agent-safety chapter measures those).

\[ \begin{aligned} q' &= \frac{q\beta}{q\beta + 1 - q} \\ P(\text{hijack}) &= 1 - (1 - q' h)^{k} \end{aligned} \]
Read it as: q is the share of poisoned documents in the corpus and β how much more likely the retriever is to pick a poisoned one (the attacker’s search-engine optimisation), so q′ is the chance a retrieved slot holds poison. The model obeys an injected instruction with probability h; with k slots filled independently, a query is safe only if no slot both holds poison and is obeyed.
Say it“The hijack chance is one minus one-minus-q-prime-h to the power k.”

Huyen 5.3.3 · information extraction

Pulling training data back out

A model is a compressed copy of its training data, and some of the copy is exact. Attackers want it for three reasons: data theft (rebuild a valuable data set, or train a competing model on it), privacy (names, addresses, phone numbers that slipped into the corpus) and copyright (reproduce protected text or images). The simplest probe is fill in the blank: give the context and see what the model completes, which is also how factual knowledge in a model was first measured (Petroni et al., 2019). Carlini et al. (2021) generated hundreds of thousands of samples from GPT-2, ranked them by how unusually confident the model was, and found hundreds of verbatim training sequences, including personal contact details. Later work showed memorisation grows with model size, with how often a sequence is duplicated and with the length of the prompt (Carlini et al., 2023), that a deployed chat model could be pushed into emitting training data by asking it to repeat a word forever (Nasr et al., 2023), and that image diffusion models can regurgitate training images (Carlini et al., 2023).

To measure memorisation, plant a canary (Carlini et al., 2019): a sentence “the secret code is 52817.” inserted d times into the training text, among 300 other people’s codes written once each. Then rank all 100,000 possible codes by how likely the model finds them. If the true code ranks first, the model has memorised it. Here the model is a character language model trained on Alice’s Adventures in Wonderland in your browser; its order n (how many characters of context it uses) plays the part of model size. Raise the number of copies d and watch the exposure climb and greedy decoding start to spell out the code.

\[ \begin{aligned} &\text{exposure}(s) \\ &\quad = \log_2 |\mathcal R| - \log_2 \operatorname{rank}(s) \end{aligned} \]
Read it as: ℛ is the set of possible secrets (here 105 codes, so at most log2 105 ≈ 16.6 bits) and rank(s) the canary’s position when every candidate is sorted from most to least likely under the model (ties share the average place). A model that knows nothing gives exposure near 1 bit; full exposure means the canary is the model’s first choice.
Say it“Exposure is log two of the number of candidates minus log two of the canary’s rank.”
\[ \begin{aligned} P(c \mid h) &= \frac{n(h,c) + t(h)\,P(c \mid h^-)}{n(h) + t(h)} \\ \text{bits}(s) &= -\sum_{i} \log_2 P(s_i \mid h_i) \end{aligned} \]
Read it as: the character model (interpolated Witten–Bell): n(h, c) counts how often character c followed context h, n(h) how often h occurred, t(h) how many different characters followed it, and h− is h with its first character dropped. In bits(s), hi is the n − 1 characters before si. A string’s cost in bits adds up the surprise of every character; the candidates are ranked by that cost.
Say it“The probability of c after h mixes its count with the shorter context’s probability, weighted by the number of distinct followers.”

Membership inference: was this sentence in the training set?

A weaker but more general question: given a sentence, can an attacker tell whether it was trained on? A model is usually more confident on text it has seen, so the simplest membership-inference attack thresholds the loss. Half of the 1,010 sentences of 40–300 characters in Alice are the training set; the other half are held out. The honest way to report such an attack is the true-positive rate at a low false-positive rate (Carlini et al., 2022), because an attack that is right on average but cannot single out anyone confidently is not much of a threat. Raise the order and the number of passes: more capacity and more repetition, more leakage.

\[ \begin{aligned} \text{TPR}(\tau) &= P\big(\ell(x) < \tau \mid x \in D_{\text{train}}\big) \\ \text{FPR}(\tau) &= P\big(\ell(x) < \tau \mid x \notin D_{\text{train}}\big) \end{aligned} \]
Read it as: ℓ(x) is the model’s loss in bits per character on sentence x; the attacker says “member” when it is below τ. TPR is the share of real members caught, FPR the share of outsiders wrongly accused. The AUC is the chance that a random member has lower loss than a random outsider.
Say it“TPR is the chance a member’s loss is under tau; FPR the same for a non-member.”

Huyen 5.3.4 · defences against prompt attacks

Defence in layers, and its two error rates

No single fix stops these attacks, so defences are stacked at three levels. At the model level, train the model to rank its inputs. OpenAI’s instruction hierarchy (Wallace et al., 2024) teaches a model that system messages outrank user messages, which outrank its own earlier outputs, which outrank tool results; lower-ranked instructions are followed only when they agree with higher ones. Training on borderline requests teaches it the other half of the job: to help with the safe ones that merely look risky. At the prompt level, state explicitly what the model must not do, repeat the key rules after the user’s text as well as before it, and warn it about the attacks you expect. At the system level, isolate anything that executes code, put a human in front of consequential actions, define out-of-scope topics, watch for unusual usage, rate-limit, and run guardrails on what goes in (harmful requests, personal data) and what comes out.

Every layer makes two kinds of mistake, and you need both numbers. The violation rate is the share of attacks that get through. The false-refusal rate is the share of legitimate requests that get blocked. A filter that refuses everything has a perfect violation rate and is useless. Move the filter’s threshold and watch one rate fall as the other rises; the benign set is JailbreakBench’s 100 benign behaviours, each written to sit near one of the harmful ones, plus XSTest’s 250 safe prompts that only sound unsafe (Röttger et al., 2024).

Huyen 5.3.4 · evaluating and hardening

The red-team loop

Defences are only as good as the attacks they were tested against. A red team, people or automated tools (open-source scanners such as garak and Microsoft’s PyRIT automate many known attacks), tries to break the system; the defenders fix what broke; the attacks join a regression suite; and the next round starts. Two rules keep the loop honest. Measure the worst attack, not the average one, because a real attacker picks the attack that works. And measure false refusals every round, because each patch tends to make the system more suspicious of ordinary users.

Here is a loop on the filter from the jailbreak section, using its four obfuscations at strength 0.5 as the red team. The fixes are the usual ones: normalise the input (undo digit-for-letter swaps and dotted letters) before scoring; score each sentence and block if any one is flagged, against padding; train on obfuscated copies of both harmful and benign training requests; and, against false refusals, add benign imperatives (600 instructions such as “Write a short story about…” from Databricks’ Dolly data), because the filter had learned that commands look harmful. Every switch retrains or re-scores live. Turn the fixes on one at a time and read both columns.

\[ \begin{aligned} \text{ASR}_a &= \frac{1}{|D|}\sum_{x \in D} \mathbb 1\big[\text{passes } a(x)\big] \\ \text{ASR}_{\max} &= \max_{a \in \mathcal A} \text{ASR}_a \end{aligned} \]
Read it as: for each attack a in the suite 𝒜, the attack success rate (ASR) is the share of harmful requests x whose obfuscated form a(x) passes the filter; the system’s robustness is set by the best of them. A fix that lowers the average but leaves one attack working has not closed the hole.

Real-world project

Project: jailbreak success against a defended open model, measured

JailbreakBench (Chao et al., 2024) is an open benchmark of 100 harmful behaviours in ten categories, each paired with a benign twin, released under the MIT licence. Its artifact repository (also MIT) stores, for each published attack and target model, the prompt the attack produced for every behaviour, the model’s response and the benchmark judge’s verdict. This project uses four of those attacks: GCG (gradient-searched suffixes; transferred from open models for the two GPT models), PAIR (an attacker LLM), a hand-written template from the JailbreakChat collection, and random search with a template (Andriushchenko et al., 2024). The targets are two open models, Vicuna-13B (little safety training) and Llama-2-7B-chat (heavily safety-tuned), and two GPT models for comparison.

Only verdicts and numbers are embedded in this page: no attack prompt and no model response. For each case the page carries the judge’s verdict, the verdict of a second classifier, Llama Guard, recorded in the same files, and a fluency score of the attack prompt that the Python script below computed with the same character model the page trains (the page cannot recompute it, because it does not hold the prompts). You build a defended system in three steps and measure it. Everything that has text in the page, the benign prompts that set the filter’s threshold, is scored live.

\[ \begin{aligned} &\text{flu}(x) \\ &\quad = \max_{j} \frac{1}{W}\sum_{i=j}^{j+W-1} -\log_2 P(x_i \mid h_i) \end{aligned} \]
Read it as: score the prompt with an order-5 character model trained on Alice, average the bits per character (each character predicted from the four before it, hi) over every window of W = 60 characters, and keep the worst window (the whole prompt if it is shorter). Gradient-searched suffixes are strings of odd tokens and symbols, so one window is very surprising even when the rest of the prompt is ordinary English. This is a small version of the perplexity filters of Jain et al. (2023) and Alon and Kamfonas (2023), which use a language model instead.
Say it“The fluency score is the largest average surprise over any sixty-character window.”

3 · Add an output filter, and read the residual

The output filter blocks a response when Llama Guard, as recorded in the artifacts, judged it unsafe. A behaviour counts as a violation only if the judge says the model was jailbroken, the fluency filter let the prompt in, and Llama Guard let the response out.

def rng(a):                                    # mulberry32, the generator the page uses
    st = [a & M32]
    def r():
        st[0] = (st[0] + 0x6D2B79F5) & M32; a = st[0]
        t = ((a ^ (a >> 15)) * (1 | a)) & M32

        return ((t ^ (t >> 14)) & M32) / 4294967296
    return r

# ---------- character language model, interpolated Witten-Bell ----------
V0 = 128
def lm_build(T, N):
    C = [dict() for _ in range(N)]
    for i in range(len(T)):
        ch = T[i]
        for k in range(N):
            if i - k < 0: break
            c = C[k].setdefault(T[i - k:i], [0, {}])
            c[0] += 1; c[1][ch] = c[1].get(ch, 0) + 1
    return C
def lm_prob(C, ctx, ch):
    p = 1.0 / V0
    for k in range(len(C)):
        if k > len(ctx): break
        e = C[k].get(ctx[len(ctx) - k:])
        if e is None: break
        n, t = e[0], len(e[1])
        p = (e[1].get(ch, 0) + t * p) / (n + t)
    return p
def lm_bits(C, s):
    N = len(C)
    return [-math.log2(lm_prob(C, s[max(0, i - N + 1):i], s[i])) for i in range(len(s))]
def norm(s): return re.sub(r"\s+", " ", s.lower()).strip()
def fluency(C, s, W=60):
    b = lm_bits(C, norm(s))
    if not b: return 0.0
    if len(b) <= W: return sum(b) / len(b)
    cs = [0.0]
    for x in b: cs.append(cs[-1] + x)
    return max((cs[i + W] - cs[i]) / W for i in range(len(b) - W + 1))

def exposure(C, code, prefix="the secret code is "):
    N = len(C); target = 0.0
    def lp(ctx, ch): return -math.log2(lm_prob(C, ctx[max(0, len(ctx) - N + 1):], ch))
    for j, ch in enumerate(code): target += lp(prefix + code[:j], ch)
    lower = 0; equal = 0; stack = [("", 0.0)]
    while stack:
        s, acc = stack.pop()
        if len(s) == len(code):

            elif acc <= target + 1e-9: equal += 1
            continue

        for ch in "0123456789": stack.append((s + ch, acc + lp(prefix + s, ch)))

    return math.log2(10 ** len(code)) - math.log2(rank), rank, target

Wrap-up

Five lines to remember

  • Everything in the context is one stream of text, so anyone who writes part of it can try to steer the model: extract its prompt, jailbreak it, inject instructions or pull out its data. The damage depends on what the app can reach.
  • Treat every system prompt as public. Detect leaks with a canary and an overlap score, and remember that a “leaked” prompt may be invented and that behaviour alone reveals a prompt to anyone who asks enough questions.
  • Jailbreaks exploit competing objectives and safety training that covers less ground than the model’s skills. Automated search (GCG, random search, PAIR) finds them faster than people do, and a defence is only tested once it has faced an attacker who adapts to it.
  • Models memorise, more so when they are bigger and the data repeats; exposure and membership inference turn that into numbers. De-duplicate, keep secrets out of training data, and report attacks at a low false-positive rate.
  • Defend in layers at the model, prompt and system level, and always measure two numbers, the violation rate and the false-refusal rate. Layers that fail together protect less than their product, and the red-team loop never really ends.

Check your understanding

A reply contains a long, confident “system prompt”, but no canary and an RL of 0.2. What should you conclude?

Probably that the model made it up, or at most paraphrased fragments. A real verbatim leak would carry the canary and reproduce most of the prompt in order. It still deserves a look, since a paraphrase can reveal the rules, but it is not evidence that the text was extracted.

Why does a filter trained on AdvBench catch 91 of 100 JailbreakBench requests but none of XSTest’s 200 unsafe questions?

AdvBench requests are commands (“Write a…”, “Create a…”) and the benign training requests are mostly questions, so the filter learned the style as much as the content. XSTest’s unsafe prompts are questions, outside the narrow distribution it was trained on: mismatched generalisation in miniature.

Why does GCG need to evaluate a batch of candidates at all, when it already has a gradient?

The gradient is a first-order prediction of the effect of a token swap, but tokens are discrete and the model is not linear, so the prediction can be wrong. It is used only to shortlist promising swaps; measuring them for real and keeping the best is what makes each step actually improve the objective.

Two layers each miss 20% of attacks. Is the stacked system’s miss rate 4%?

Only if their misses are independent. Filters built on similar signals tend to miss the same attacks; with correlation ρ = 0.5 the joint miss rate is 0.04 + 0.5 × 0.16 = 12%, three times the naive figure. Measure the stack end to end.

The fluency filter stops almost every GCG and random-search prompt in the project. Is the problem solved?

No. It does nothing against fluent attacks such as PAIR or hand-written templates, and attackers who know about it can add a fluency term to their search. It also refuses some benign text. It is one layer, useful because it is cheap, and its value has to be re-measured against attacks designed to beat it.

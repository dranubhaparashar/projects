GPUs, Accelerators & Distributed Training

Six FLOPs per parameter per token, and the machines that deliver them

A language model is, for the hardware, almost nothing but matrix multiplication: about six floating-point operations per parameter for every token it trains on. Multiply that by billions of parameters and trillions of tokens and no single chip can finish in a lifetime, so training is spread across thousands of accelerators whose memories, links and failures all have to be budgeted. This chapter builds that budget from the bottom up: what one GPU can do and why, how much memory a training step needs, how the work is split across devices in three directions, and how to estimate the days and dollars before buying any of them. The figure is the roofline: for a chosen accelerator, how fast a piece of work can possibly run depends only on how many operations it does per byte it moves. The count

Where the FLOPs go: six per parameter per token

Open up a transformer (chapter 4.3, inside an LLM) and almost every parameter sits in a matrix that multiplies the token’s vector: the query, key, value and output projections of attention, the two matrices of the feed-forward block, and the final matrix that turns the last hidden vector into vocabulary logits. The embedding table is the one exception, and looking a row up costs nothing. So the arithmetic of a forward pass is, to a very good approximation, the arithmetic of multiplying one token vector through every weight matrix once.

Count what that costs. A weight matrix with K inputs and M outputs, applied to one token, performs M·K multiplications and M·K additions: two floating-point operations (FLOPs) per weight. The forward pass therefore costs about 2N FLOPs per token, where N is the number of parameters in matrices. The backward pass runs two matrix multiplications for every one in the forward pass: one to get the gradient with respect to the layer’s input (needed to keep going backwards) and one to get the gradient with respect to the weights (what the optimiser wants). That is another 4N. Training on one token costs 6N; inference, which has no backward pass, costs 2N. This is the accounting Kaplan et al. (2020) used for their scaling laws, and it is the reason the previous chapter could write total training compute as C ≈ 6ND for D tokens.

One term is left out: the attention scores. Comparing a query with T keys and blending T values costs about 4·T·d FLOPs per layer per token in the forward pass for the full square (half of that if the kernel skips the masked future), with no parameters involved at all. It matters when the context T is comparable to 12d, the number of weights per layer divided by d. For a model with d = 4096 that is a context of about 49,000 tokens: long-context training is where the “6N” slogan starts to under-count.

Everything else is noise in the count. The embedding look-up is a memory read. Layer norms, the softmax over the attention scores, the GELU and the residual additions each cost a few FLOPs per element of an s×h activation, against 24h FLOPs per element for the layer’s matmuls: well under one per cent of the arithmetic. They are not negligible in time, as the next section explains, because they are bound by memory traffic rather than by arithmetic; but as FLOPs they vanish, and the 6N rule is good to a few per cent for any model whose context is short compared with 12d.

\[ \begin{aligned} \text{forward} &\approx 2N + 4\,L\,T\,d \\ \text{training (forward + backward)} &\approx 6N + 12\,L\,T\,d \\ \text{inference} &\approx 2N \end{aligned} \qquad N \approx 12\,L\,d^{2} + V d \]
Read it as: all counts are per token. N is the parameter count; L the number of layers; d the hidden width; T the context length; V the vocabulary. 2N is one multiply and one add per weight. The backward pass doubles the matrix work (input gradient and weight gradient), so training is three forward passes’ worth. The 12LTd term is the attention scores for the full T×T square, three passes again; causal kernels do about half of it. Of the 12d² weights per layer, 4d² are the attention projections and 8d² the feed-forward block (two matrices of d×4d, or three of d×8d/3 in a gated SwiGLU block, the same total).

Fast implementations: why nobody writes the loops

Those 6N FLOPs have to be executed by something, and how they are executed changes the speed by factors of thousands. The listing below multiplies two matrices three ways on an ordinary laptop CPU. Pure Python loops perform one multiply-add per interpreter step. NumPy hands the same product to a BLAS library (OpenBLAS here) that is written for the processor: it keeps small tiles of the matrices in registers and cache, uses vector instructions that do eight or sixteen multiplications at once, and runs on every core. The third case is the same 4096×4096 matrix multiplied by a vector: the FLOP count per byte collapses, and so does the speed, for a reason the next section makes exact.

cpu_matmul.py · run on this page’s author machine, Python 3.14, NumPy 2.5
import time, numpy as np

def pure_python_matmul(A, B):                 # three nested loops, one FLOP at a time
    n, k, m = len(A), len(B), len(B[0])
    C = [[0.0] * m for _ in range(n)]
    for i in range(n):
        for j in range(m):
            s = 0.0
            for t in range(k):
                s += A[i][t] * B[t][j]
            C[i][j] = s
    return C

rng = np.random.default_rng(0)
for n in (64, 128):                           # the slow way, small sizes only
    A, B = rng.standard_normal((n, n)), rng.standard_normal((n, n))
    t0 = time.perf_counter(); pure_python_matmul(A.tolist(), B.tolist()); dt = time.perf_counter() - t0
    print(f"python loops  n={n:5d}  {2*n**3/dt/1e9:8.4f} GFLOP/s  ({dt*1e3:8.1f} ms)")

for n in (256, 1024, 4096):                   # numpy -> BLAS: vectorised, blocked, multi-threaded
    A, B = rng.standard_normal((n, n), dtype=np.float32), rng.standard_normal((n, n), dtype=np.float32)
    A @ B                                     # warm up
    reps = 3
    t0 = time.perf_counter()
    for _ in range(reps): A @ B
    dt = (time.perf_counter() - t0) / reps    # 2n^3 FLOPs over 3n^2 fp32 numbers of 4 bytes

n = 4096                                      # the same matrix times a vector: a memory-bound shape
A, x = rng.standard_normal((n, n), dtype=np.float32), rng.standard_normal((n, 1), dtype=np.float32)

The machine

Inside an accelerator: the roofline

A CPU is built to run one thread very fast: deep pipelines, branch prediction, large caches, a handful of cores. A GPU is built to run tens of thousands of threads at once on the same instruction, which is exactly what a matrix multiplication wants. An NVIDIA H100 contains 132 streaming multiprocessors (SMs). Each SM holds thousands of simple arithmetic units, four tensor cores, a 256 KB register file and a 256 KB block that is shared between a programmer-managed scratchpad (shared memory) and an L1 cache. A tensor core is a unit that multiplies a small matrix tile (a handful of rows and columns of bf16 numbers at a time) and accumulates the result in fp32 in a few clock cycles, which is why the dense bf16 peak of the chip, 989 trillion FLOP/s, is about fifteen times its ordinary fp32 peak of 67. Below the SMs sits a 50 MB L2 cache shared by all of them, and below that 80 GB of high-bandwidth memory (HBM3) stacked next to the die and connected by a 5,120-bit bus: 3.35 TB/s. Other accelerators differ in the details and agree in the shape: Google’s TPU v4 replaces the SMs with a few large 128×128 systolic arrays (eight per chip, in two cores) through which data flows in lock-step; AMD’s MI300X has 304 compute units, a 256 MB last-level cache and 192 GB of HBM3. All of them are a huge matrix engine next to a memory that is fast but, relative to the engine, not fast enough.

That relation is captured by one picture. Every kernel (one GPU program, such as a matrix multiplication or a layer norm) reads some bytes from HBM, does some FLOPs on them and writes some bytes back. Its arithmetic intensity I is FLOPs per byte moved. The kernel cannot run faster than the peak P of the arithmetic units, and it cannot run faster than the memory can feed it, which is I FLOPs for every byte of the bandwidth BW. The attainable speed is the smaller of the two: Williams, Waterman and Patterson’s (2009) roofline model. On a log–log plot it is a sloped line that meets a flat roof at the knee I* = P/BW, which for an H100 in bf16 is 989/3.35 ≈ 295 FLOP/byte. Left of the knee the kernel is memory-bound: adding compute would not help, only moving fewer bytes would. Right of it the kernel is compute-bound, and the only way forward is more or faster arithmetic units.

\[ \text{attainable FLOP/s} \;=\; \min\!\big(P,\; I \cdot BW\big), \qquad I = \frac{\text{FLOPs}}{\text{bytes moved}}, \qquad I^{*} = \frac{P}{BW} \]
Read it as: P is the peak arithmetic rate of the device (FLOP/s), BW the bandwidth of the memory the kernel streams from (bytes/s), I the kernel’s arithmetic intensity. Below the knee I* the memory is the bottleneck and the attainable rate grows in proportion to I; above it the compute units are. Time for a kernel is then max(FLOPs/P, bytes/BW).
Say it“You get the smaller of peak compute and intensity times bandwidth.”

Where kernels land

The lab below lets you place real kernels on the roofline. A square bf16 matrix multiplication of size n has intensity n/3 (2n³ FLOPs over three n² matrices of 2 bytes each); for n = 4096 that is about 1,365 FLOP/byte, well right of every knee, which is why big matmuls reach 70–80% of peak in practice. Make the matrix thin, as happens when a batch of one token multiplies the weights during decoding, and the intensity falls towards 1. A layer norm touches each element a few times and has an intensity near 2 whatever its size: hopelessly memory-bound, so its speed is just bandwidth. Attention is the interesting case. Written naively, the T×T score matrix is written to HBM, read back for the softmax, written again and read again for the value product; its intensity tends to a constant about half the head dimension, 64 for 128-dimensional heads, which is memory-bound on every modern chip. The fused kernels of Dao et al. (2022), FlashAttention, keep the scores in shared memory and never write them, so the intensity grows like T/2 and long-context attention becomes compute-bound. Same FLOPs, same result, several times faster: the roofline tells you why.

Bandwidth against compute: why batching helps

The decode kernel above is the whole story of inference efficiency in one number. Generating one token for one sequence multiplies every weight by one vector: 2N FLOPs for 2N bytes (in bf16), intensity 1, so an H100 spends 3.35 TB/s worth of time reading 14 GB of 7B-model weights, about 4 ms, and does arithmetic for a few microseconds of it. Put B sequences in the batch and the weights are read once but used B times: intensity B, time unchanged until B reaches the knee I* ≈ 295, after which the arithmetic finally takes over and the time per step starts growing in proportion. Throughput in tokens per second is therefore almost linear in the batch up to the knee and flat after it. The same reasoning drives training: a micro-batch of 4,096 tokens gives every weight matrix a 4,096-row multiplication, far right of the knee, which is why training is compute-bound and inference, unless batched hard, is not. Running PyTorch on a GPU

From Python the whole machine is reached through a few habits. Tensors and modules live on a device; everything that touches them must be on the same one. Mixed precision (next section) is a context manager. The expensive mistakes are the ones that break the roofline logic: launching thousands of tiny kernels (each launch costs a few microseconds whatever it does), synchronising the host with the device every step by calling .item() on a loss, or copying data from pageable host memory. The listing is a complete training step as it is written in practice; it is shown as code only, because this page is built on a machine without a GPU and the book shows no output it did not produce.

train_step.py · shown, not run
import torch, torch.nn as nn
from torch.nn.parallel import DistributedDataParallel as DDP

torch.backends.cuda.matmul.allow_tf32 = True        # fp32 matmuls on tensor cores (10-bit mantissa)
model = build_transformer().to(device)              # weights move once; stay resident in HBM
model = DDP(model, device_ids=[local_rank])         # data parallel: all-reduce of grads, bucketed, overlapped
model = torch.compile(model)                        # fuse small ops into fewer, larger kernels
opt = torch.optim.AdamW(model.parameters(), lr=3e-4, fused=True)
loader = DataLoader(ds, batch_size=8, pin_memory=True, num_workers=4)

for step, (x, y) in enumerate(loader):
    x = x.to(device, non_blocking=True)             # pinned host memory -> async copy over PCIe
    y = y.to(device, non_blocking=True)
    with torch.autocast("cuda", dtype=torch.bfloat16):   # matmuls in bf16, master weights stay fp32
        logits = model(x)
        loss = nn.functional.cross_entropy(logits.flatten(0, 1), y.flatten())
    loss.backward()                                 # DDP starts all-reducing buckets as they finish
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step(); opt.zero_grad(set_to_none=True)
    if step % 100 == 0:                              # .item() forces a host-device sync: do it rarely
        print(step, loss.item())

# measure on the device clock, not the host clock
start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
start.record(); logits = model(x); end.record(); torch.cuda.synchronize()
print("forward ms:", start.elapsed_time(end))

  • Avoid synchronisingAnything that needs a value on the host (.item(), print(tensor), Python if on a tensor) stalls the queue of kernels. Log every hundred steps, not every step.
  • Use the right dtypebf16 for matmuls and activations, fp32 for the loss reduction, the optimiser states and the master weights. Chapter 4.4c (precision & quantisation) is about the numbers themselves.

The budget

The memory budget of training

Compute decides how long training takes; memory decides whether it runs at all. Four things have to fit on each device during a training step. The weights, one number per parameter. The gradients, another number per parameter, produced by the backward pass and consumed by the optimiser. The optimiser states: Adam keeps two running moments per parameter, and mixed-precision training keeps a third, a full-precision master copy of the weights so that tiny updates are not rounded away. And the activations: every intermediate tensor the forward pass produced has to be kept until the backward pass has used it, and there are dozens per layer.

With the standard mixed-precision recipe (Micikevicius et al., 2018), weights and gradients are stored in bf16 (2 bytes each) for speed, while the master weights and Adam’s two moments are fp32 (4 bytes each). That is 2 + 2 + 4 + 4 + 4 = 16 bytes per parameter before a single activation is counted, the figure Rajbhandari et al. (2020) start the ZeRO paper from. A 7-billion-parameter model therefore needs 112 GB of state: it does not fit on an 80 GB device, and that is with nothing to train on. Whether you store moments in 8 bits, drop the master copy, or use an optimiser without moments changes the 16; chapter 4.4c works through the data types, so here the choices are switches.

Activations are the part that scales with the batch. Korthikanti et al. (2022) count them for one transformer layer with sequence length s, micro-batch b, hidden width h and a attention heads, stored in 16-bit: s·b·h·(34 + 5·a·s/h) bytes. The 34 collects every tensor of size s×b×h that the layer saves (inputs to each matmul, the normalisation inputs, the dropout masks, the gated activations); the 5as/h term is the attention score and probability matrices, which are s×s per head and so grow quadratically with the sequence. For a Llama-7B-shaped layer at s = 4,096 and b = 1 that is 16.8 M × 194 = 3.25 GB per layer, 104 GB for 32 layers. The training step of a 7B model wants over 200 GB per device at a micro-batch of one. Something has to give, and the two ways out are the subject of this section and the next two: recompute activations instead of storing them, and shard the states across devices.

Inference has a different and smaller budget, worth stating for contrast: only the weights (2N bytes in bf16, or less after quantisation) plus the KV cache, the keys and values of every past token of every active sequence, 2 × L × h × 2 bytes per token for a model without grouped-query attention. A 7B model serving 64 sequences of 4,096 tokens holds 14 GB of weights and 64 × 4,096 × 2 × 32 × 4,096 × 2 bytes = 137 GB of cache, which is why serving systems spend their ingenuity on the cache (chapter 4.5a) and their quantisation on both (chapter 4.4c). The rest of this chapter stays with training.

\[ \begin{aligned} M_{\text{states}} &= N\,\big(\underbrace{b_w}_{\text{weights}} + \underbrace{b_g}_{\text{grads}} + \underbrace{b_m}_{\text{master}} + \underbrace{b_o}_{\text{optimiser}}\big) \;=\; 16N \text{ bytes for bf16 + fp32 Adam} \\ M_{\text{act}} &\approx L \cdot s\,b\,h\left(34 + 5\,\frac{a\,s}{h}\right) \text{ bytes, or } L\cdot 34\,sbh \text{ (selective recompute), or } L \cdot 2\,sbh \text{ (full recompute)} \end{aligned} \]
Read it as: bw, bg, bm, bo are bytes per parameter for the weights (2 in bf16), the gradients (2), the fp32 master copy (4) and the optimiser moments (8 for Adam’s two). For activations, s is the sequence length, b the micro-batch, h the hidden width, a the number of heads, L the layers; 34 sbh is every saved tensor of the layer except attention’s score matrices, and 5 as·sb is those matrices. Selective recomputation (Korthikanti et al., 2022) throws away just the score matrices and recomputes them in the backward pass; full checkpointing (Chen et al., 2016) keeps only each layer’s input, 2sbh bytes, and re-runs the whole layer forward when its gradient is needed.

Activation checkpointing: memory for time

Full checkpointing is a straight trade. Keep only the input of each layer and re-run its forward pass when the backward pass arrives, and activation memory falls from 34sbh + 5as·sb per layer to 2sbh, while compute rises by one extra forward pass: 6N becomes 8N per token, one third more. That is a steep price for a resource you may have plenty of, which is why the selective variant is now the default in large runs. The score matrices are the one part of the layer that is both huge (quadratic in s) and cheap to recompute (no parameters, so roughly 4·T·d FLOPs per layer per token against the layer’s 24d²); dropping only them removes most of the memory for a few per cent of the time. Split the data

Data parallelism and ring all-reduce

The first way to use p devices is the obvious one. Copy the whole model to each of them, give each a different slice of the batch, let each compute the gradient on its slice, then average the p gradients and apply the same update everywhere. Because the update is identical on every replica, the replicas stay identical; mathematically it is one training step on a batch p times larger, and the loss curve against tokens is the same as it would be on one giant device. The global batch is the per-device micro-batch times p (times any gradient accumulation steps), and the only new ingredient is the averaging, an all-reduce: every device ends up with the sum of what every device started with.

How much traffic does that take? Call the gradient S bytes (2N in bf16). The naive scheme, every device sending its full gradient to every other, moves (p−1)S per device, which grows without bound. The ring all-reduce (Patarasuk & Yuan, 2009; made standard for deep learning by Baidu’s 2017 implementation, and the core of NVIDIA’s NCCL) arranges the devices in a ring and cuts the gradient into p chunks. In the first phase, reduce-scatter, each device passes one chunk to its right neighbour, which adds its own contribution and passes the running sum on; after p−1 steps each device holds the complete sum of one chunk. In the second phase, all-gather, the complete chunks travel round the ring once more and everyone has everything. Each step moves S/p bytes per device, there are 2(p−1) steps, so each device sends and receives 2(p−1)/p · S bytes in total, less than 2S whatever p is. The scheme is bandwidth-optimal: the cost per device does not grow with the number of devices. What does grow is latency, 2(p−1) hops of a few microseconds each, which is why libraries switch to tree-shaped algorithms for very large rings.

Two practical points make data parallelism almost free when the model fits. First, the gradient of the last layers is ready while the backward pass is still computing the first layers, so the all-reduce can start early: PyTorch’s DistributedDataParallel (Li et al., 2020) groups parameters into buckets of about 25 MB and launches the all-reduce of each bucket as soon as its gradients are complete, hiding most of the communication behind computation. Second, the per-device traffic 2S is fixed per step, so a larger micro-batch amortises it over more tokens. The one hard limit is memory: every replica carries the full 16N bytes of state. For a 7B model that is 112 GB on an 80 GB device, and plain data parallelism cannot start.

The all-reduce is one of a small family of collective operations that every distributed training system is built from, and it pays to know the others by name, because the next sections take the all-reduce apart into them. All are implemented by communication libraries (NVIDIA’s NCCL, AMD’s RCCL, Google’s XLA collectives) that pick ring, tree or hierarchical algorithms according to the message size and the topology, and are called from PyTorch through torch.distributed.

  • broadcastOne device sends the same tensor to all others: how the initial weights are made identical on every replica. Cost S per device.
  • reduce-scatterEvery device starts with a full tensor; afterwards device j holds the sum of the j-th slice from everyone. (p−1)/p · S per device. The first half of the ring all-reduce, and the whole of what ZeRO needs for gradients.
  • all-gatherEvery device starts with one slice; afterwards everyone holds all slices. (p−1)/p · S per device. The second half of the ring, and how sharded weights are reassembled before a layer runs.
  • all-reduceEvery device ends with the full sum: reduce-scatter followed by all-gather, 2(p−1)/p · S. Gradient averaging in data parallelism, partial-sum merging in tensor parallelism.
  • all-to-allDevice i sends its j-th slice to device j for every j: a transpose across the group. The routing step of mixture-of-experts models, and the most demanding pattern for a network.
  • point-to-point send / recvOne device to one other: the activation hand-off between pipeline stages. No group, no algorithm, just bandwidth and latency.
\[ \text{bytes per device} = 2\,\frac{p-1}{p}\,S \;\xrightarrow{\,p\to\infty\,}\; 2S, \qquad t_{\text{all-reduce}} \approx 2\,\frac{p-1}{p}\,\frac{S}{BW} + 2(p-1)\,\alpha \]
Read it as: S is the size of the tensor being reduced (2N bytes for a bf16 gradient), p the number of devices in the ring, BW the bandwidth of one link in one direction, α the latency of one hop. The reduce-scatter and all-gather phases each take p−1 steps of S/p bytes. Compare the naive (p−1)S: for p = 256 the ring moves 2S instead of 255S.

ZeRO and FSDP: sharding the states

Look again at what p data-parallel replicas hold: p identical copies of 16N bytes. Of those 16 bytes per parameter, 12 (the master weights and the two Adam moments) are touched exactly once per step, in the optimiser update, and the update of parameter k depends only on the gradient and states of parameter k. Rajbhandari et al. (2020) noticed that nothing requires all replicas to hold all of it. Their Zero Redundancy Optimizer (ZeRO) partitions the state across the data-parallel group in three stages of increasing ambition.

Stage 1 shards the optimiser states: device j owns the master copy and moments of the j-th slice of the parameters. After the backward pass the gradient is reduce-scattered rather than all-reduced, so device j receives the summed gradient for exactly its slice, updates its slice, and the fresh bf16 weights are all-gathered so that every device has the full model for the next forward pass. Reduce-scatter plus all-gather is exactly what a ring all-reduce was anyway, so the communication is unchanged at 2S per device, and the memory drops from 16N to 4N + 12N/p. Stage 2 also shards the gradients: once the reduce-scatter has delivered device j’s slice, it discards the rest, and bf16 gradients need only 2N/p. Memory 2N + 14N/p, communication still 2S. Stage 3 shards the weights themselves. Each device holds only its 1/p slice permanently; just before a layer runs, forward or backward, its weights are all-gathered from the group, used, and freed. That adds one all-gather of the weights (S bytes per device) on top of the reduce-scatter and all-gather of the gradient and update: 3S, half as much again, for a memory of 16N/p that shrinks with the group. PyTorch’s Fully Sharded Data Parallel (Zhao et al., 2023) is stage 3 with the layer as the unit of sharding; the DeepSpeed library implements all three stages, with options to offload the shards to host memory.

The consequence is that “does the model fit?” stops being a question about one device. With stage 3 across 64 devices, a 70B model’s 1.12 TB of state is 17.5 GB each. The price is the extra all-gather traffic and, more subtly, that stage 3 makes the weights arrive just in time: if the all-gather of the next layer is not fully overlapped with the compute of the current one, the device waits. Sharding is a memory tool with a communication bill, and the next two sections introduce splits that address compute and memory together.

Three refinements are standard in practice. Prefetching: FSDP issues the all-gather for layer k+1 while layer k computes, so the just-in-time weights arrive early as long as the link keeps up with the compute. Offloading: the sharded optimiser states, which are touched once per step, can live in host memory and cross PCIe at the step boundary (ZeRO-Offload), trading HBM for a slower optimiser step. Hybrid sharding: shard the states only within a node, where the all-gathers run on NVLink, and replicate across nodes with an ordinary all-reduce (hybrid-sharded data parallel, HSDP), which keeps stage-3 traffic off the network. Each is a knob on the same trade: bytes of memory against bytes on a link.

\[ \begin{aligned} \text{stage 0 (DDP)}:&\; 16N & \text{stage 1}:&\; 4N + \tfrac{12N}{p} \\ \text{stage 2}:&\; 2N + \tfrac{14N}{p} & \text{stage 3 (FSDP)}:&\; \tfrac{16N}{p} \end{aligned} \qquad \text{traffic per device: } 2S,\; 2S,\; 2S,\; 3S \]
Read it as: bytes of state per device for N parameters sharded over a data-parallel group of p, with the bf16 + fp32 Adam recipe (2 + 2 + 12). Each stage shards one more of the three: optimiser states (12), gradients (2), weights (2). S = 2N is the bf16 gradient; stages 1 and 2 keep the ring all-reduce’s 2S by splitting it into its two halves, stage 3 adds an all-gather of weights.

Split the matrices

Tensor parallelism: one layer across several devices

Sharding spreads the storage of a layer; the computation of each layer still happens on one device. Tensor parallelism (also called model parallelism within a layer) splits the matrix multiplications themselves, so that t devices each do 1/t of every layer’s arithmetic on 1/t of its weights. The trick, due to Shoeybi et al. (2019) in Megatron-LM, is to choose the direction of the split so that the non-linearity in between needs no communication.

Take the feed-forward block, Y = GELU(XA)·B with A of shape h×4h and B of shape 4h×h. Split A by columns into t pieces A1…At. Device i computes GELU(XAi), a slice of the 4h-wide hidden activation, and because GELU acts on each element separately it can be applied to the slice without seeing the others. (Splitting A by rows would give partial sums that must be added before the GELU, forcing a synchronisation in the middle.) Now split B by rows to match: device i multiplies its slice by Bi and obtains a partial result Yi of the full shape h, and Y = Σi Yi. One all-reduce of an s×b×h activation finishes the block. Attention splits even more naturally: heads are independent, so give each device a/t heads (column slices of the Q, K and V projections), let it run its heads’ attention locally, and split the output projection by rows so that again a single all-reduce sums the partial outputs. Each layer therefore needs two all-reduces in the forward pass, and two in the backward pass (the backward of a column-split layer must sum the input gradients from all devices: the forward and backward operators are each other’s conjugates).

What does it cost? Weights, gradients and optimiser states all divide by t: a 70B model on t = 8 is 8.75B parameters per device. The s×b×h activations at the block boundaries are replicated on every device unless sequence parallelism (Korthikanti et al., 2022) splits them along s between the blocks, which also turns the all-reduces into reduce-scatter and all-gather pairs at the same total traffic. The communication is the problem: four all-reduces per layer per micro-batch, each moving 2(t−1)/t · 2sbh bytes per device, and every one of them sits on the critical path, because the next matmul cannot start until the sum is in. For a 4,096-wide model with s·b = 4,096 tokens that is 32 MB per all-reduce, 128 MB per layer, repeated for every layer and every micro-batch. Only NVLink-class bandwidth inside a node (450 GB/s per direction on an H100, against 50 GB/s for a 400 Gb/s network port) makes that cheap enough, which is why tensor parallelism in practice stops at t = 8, the number of GPUs in a node. The lab shows the ratio of that communication time to the layer’s own compute as t and the shape change.

\[ Y = \sum_{i=1}^{t} \operatorname{GELU}(X A_i)\, B_i, \qquad \text{bytes per layer per device} = 4 \times 2\,\frac{t-1}{t} \times 2\,s\,b\,h \]
Read it as: Ai is the i-th column block of the first matrix, Bi the matching row block of the second. Each device computes one term of the sum with no communication; the sum itself is one all-reduce. Per layer there are four such all-reduces (two forward, two backward), each over an activation of s tokens × b sequences × h width in bf16 (2 bytes), moved round a ring of t devices.

Split the layers

Pipeline parallelism and the bubble

The third way to split a model is along its depth: give the first L/p layers to device 1, the next L/p to device 2, and so on. Activations flow forward from stage to stage and gradients flow back. Only the activation at each boundary is communicated, 2sbh bytes per micro-batch in each direction, between two devices rather than round a ring: a tiny fraction of tensor parallelism’s traffic, and insensitive to latency, so pipeline stages can sit in different nodes connected by the ordinary network.

The catch is idleness. If one batch goes through the pipeline, stage 2 waits while stage 1 works, and so on: only one of p devices is busy at any moment. GPipe (Huang et al., 2019) fixes most of this by cutting the batch into m micro-batches and feeding them in one after another, so that while micro-batch 2 is in stage 1, micro-batch 1 is already in stage 2. The pipeline still has to fill at the start and drain at the end, and during those phases some stages have nothing to do. With tf and tb the forward and backward time of one micro-batch on one stage, the step takes (m + p − 1)(tf + tb) instead of the ideal m(tf + tb), and the idle share, the pipeline bubble, is (p − 1)/(m + p − 1). Eight stages and four micro-batches waste 64% of the devices; eight stages and 64 micro-batches waste 10%. Many micro-batches help, but each micro-batch must still be large enough to keep the matmuls on the right of the roofline, so the global batch has to be large, which is one reason large models train with batches of millions of tokens.

GPipe’s schedule runs all m forward passes, then all m backward passes, so a stage holds the activations of all m micro-batches at once and memory grows with m. The 1F1B schedule (Narayanan et al., 2019 in PipeDream, and the flush variant used by Megatron, Narayanan et al., 2021) starts each micro-batch’s backward pass as soon as possible: after a short warm-up a stage alternates one forward and one backward, so at most p micro-batches are in flight, and activation memory is bounded by p whatever m is. The bubble is exactly the same. Interleaving (giving each device several non-adjacent chunks of layers, so that there are effectively more stages in a shorter pipeline) cuts the bubble by the number of chunks at the price of more communication. Put it together

3-D parallelism across a cluster

A training cluster is built in layers, and each layer is slower than the one inside it. Eight GPUs share a chassis, a node, and are wired together by NVLink through NVSwitch chips: on an H100 system each GPU has 900 GB/s of NVLink bandwidth (450 GB/s in each direction) to any other GPU in the node. Nodes are joined by a network, InfiniBand or Ethernet, usually with one 400 Gb/s port per GPU: 50 GB/s per direction, nine times less than NVLink and 67 times less than the GPU’s own HBM. At the top, hundreds or thousands of nodes hang off a multi-level switch fabric (a fat tree, often one network “rail” per GPU position) in which traffic between distant nodes shares the spine links. TPU pods make the same ladder differently, with a 3-D torus of direct chip-to-chip links across up to 4,096 chips in a v4 pod, but the rule is identical: bandwidth is plentiful locally and scarce globally.

The three parallelisms have three communication profiles, and the trick of large-scale training (Narayanan et al., 2021, for Megatron; Smith et al., 2022, for Megatron-Turing NLG) is to map them onto the ladder. Tensor parallelism moves the most bytes and cannot be overlapped, so it stays inside the node: t ≤ 8. Pipeline parallelism moves a few megabytes point to point per micro-batch and tolerates latency, so stages are spread across nodes: a pipeline of p stages is p nodes (or p groups of nodes). Data parallelism moves the whole gradient once per step but can hide behind the backward pass, so it takes whatever dimension is left: d = G/(t·p) replicas, each one a full pipeline, all-reducing across the network. The devices are numbered so that the tensor-parallel index changes fastest, then the pipeline index, then the data-parallel index, which is why the picture below looks like a grid of nodes with one colour per node when you look at tensor groups. Mixture-of-experts models add a fourth axis, expert parallelism, which routes tokens to experts on other devices with all-to-all traffic; it follows the same logic and is outside this chapter.

The lab assigns a cluster to a 3-D split and counts the bytes each device must move per step, by type, for a 7B-shaped model with 4,096-token micro-batches. Notice three things as you move the sliders. Tensor-parallel traffic is enormous per step but goes over NVLink; put it on the network (t·p > 8 with tensor groups spanning nodes is never done, so the lab keeps t within a node) and it would dominate everything. Pipeline traffic is tiny. Data-parallel traffic shrinks as t·p grows, because each replica holds fewer parameters, but it crosses the network and has to be hidden behind computation; the time it would take, uncovered, is shown next to it.

Honest accounting

Failures, checkpoints, MFU and the time estimate

Everything so far assumed the machines work. At the scale of a frontier run they do not, continuously. Meta’s report on Llama 3 (Llama Team, 2024) counts 466 job interruptions over the 54 days of pre-training the 405B model on 16,384 H100s, 419 of them unexpected, and about three quarters of those traced to hardware: failing GPUs, HBM errors, broken links. The arithmetic is simple and unforgiving. If one device has a mean time between failures of M (ten years is a generous figure for a GPU under constant load), a job spanning n devices sees a failure every M/n on average: 16,384 devices and ten years give 5.3 hours. Any failure stops the synchronous step everywhere.

The defence is checkpointing: write the full training state (the 16N bytes of weights, master copy and moments: 112 GB for a 7B model, 6.5 TB for 405B) to shared storage every τ seconds, and on failure restart from the last one. Too rarely and each failure loses hours of work; too often and the writing itself eats the run. If a checkpoint takes δ seconds to write and the system fails every Msys seconds, the time lost per unit time is about δ/τ for writing plus τ/(2Msys) for the half-interval of work a typical failure destroys. Young (1974) minimised that: τ* = √(2δMsys), with a total overhead of about √(2δ/Msys). Modern systems write checkpoints asynchronously from a copy in host memory, which shrinks δ and lets τ shrink with it; the lab below shows the trade-off.

MFU: the honest efficiency metric

How well is a run using its hardware? Counting FLOPs executed per second and dividing by the peak is tempting but gameable: recomputing activations executes more FLOPs and raises that number while making training slower. Chowdhery et al. (2022) defined model FLOP utilisation (MFU) to close that loophole: take the FLOPs the mathematics requires per token (6N plus the attention term), multiply by the tokens actually processed per second, and divide by the peak FLOP/s of all devices. Recomputation, pipeline bubbles, exposed communication, optimiser steps, data loading and kernel inefficiency all push MFU down, which is the point. The companion hardware FLOP utilisation (HFU) counts the recomputed FLOPs too and is always higher. Published MFU figures are sobering: PaLM 540B reached 46.2% on 6,144 TPU v4 chips, Megatron-Turing NLG 530B about 30%, GPT-3’s run was estimated at 21%, and Llama 3 405B ran at 38–43% on 16,384 H100s. Forty per cent is a good number; sixty is exceptional and only seen on small models with short contexts. Everything in the time estimate hangs on it.

  • Kernel efficiencyEven a well-shaped matmul reaches 70–80% of peak; attention, normalisation and element-wise kernels far less. The product over a step is the κ of the project’s calculator, typically 0.5–0.7.
  • Pipeline bubble(p−1)/(m+p−1) of device-time, directly off the top; interleaving and zero-bubble schedules claw some of it back.
  • Exposed communicationTensor-parallel all-reduces on the critical path, and whatever part of the data-parallel all-reduce or the ZeRO-3 all-gathers is not hidden behind compute.
  • Everything that is not a layerThe optimiser step over all states, gradient clipping, data loading and tokenisation, logging, and the host-side synchronisations of the training loop. Small per step, never zero.
  • Stragglers and failuresA synchronous step runs at the pace of the slowest device; thermal throttling, a slow link or a flaky node drags the whole job. Restarts from checkpoints cost the lost interval plus a cold start.
\[ \text{MFU} = \frac{\text{tokens/s} \times (6N + 12\,L\,h\,s)}{n_{\text{dev}} \times P}, \qquad T_{\text{train}} \approx \frac{6\,N\,D}{n_{\text{dev}} \times P \times \text{MFU}} \]
Read it as: N parameters, D training tokens, ndev devices of peak P FLOP/s each. The numerator of MFU is the compute the model needs per second at the observed throughput; the denominator is what the hardware could do. Turned round, the training time is the required compute 6ND divided by the delivered rate. Divide T by 86,400 for days; multiply by ndev and the hourly price for the bill.

The project in the next section does the same calculation with every assumption as a control.

A word on D before the arithmetic. Two trillion tokens for seven billion parameters is about 290 tokens per parameter, far more than the roughly 20 per parameter that Hoffmann et al. (2022) found to be compute-optimal for a fixed training budget (the Chinchilla rule of the previous chapter). The choice is deliberate: a small model trained for longer is cheaper to serve, because inference costs 2N per token for every token it will ever generate, and for a model that will answer billions of requests the training budget is the smaller bill. Plans like this one therefore start from a target size and a token count chosen for the model’s whole life, not from the Chinchilla optimum alone.

The same plan in Python

The listing is complete and runnable as pasted; it needs only NumPy. It computes the default plan above line by line, then uses two small NumPy sweeps to ask the questions a planner actually asks: how much does each ZeRO stage save on this cluster, and which TP × PP split is fastest. The output is the real output of running it with Python 3.14 and NumPy 2.5; the browser version of the plan agrees with it to the printed digits (checked in Node against the same code).

plan_run.py
import numpy as np

# ---------------- the run (the page's default setting) ----------------
N, D      = 7.0e9, 2.0e12          # parameters, training tokens
G         = 256                    # devices
TP, PP    = 1, 1                   # tensor- and pipeline-parallel degrees; DP = G / (TP*PP)
seq, mb   = 4096, 1                # sequence length, micro-batch (sequences per device)
B_tok     = 4 * 1024**2            # global batch, tokens per optimiser step
vocab     = 32000
zero      = 1                      # ZeRO stage 0..3 (1 = shard optimiser states)
recompute = "selective"            # "none" | "selective" | "full" activation recomputation
w_b, g_b, master_b, opt_b = 2, 2, 4, 8   # bytes/param: bf16 weights, bf16 grads, fp32 master, Adam m+v
# device: NVIDIA H100 SXM, vendor peak figures (dense BF16), one 8-GPU node per 8 devices
peak, hbm, bw_intra, bw_inter = 989e12, 80e9, 450e9, 50e9   # FLOP/s, bytes, NVLink per direction, 400 Gb/s IB
tdp_w, price, pue, kg_per_kwh = 700, 2.50, 1.1, 0.4
kappa     = 0.55                   # fraction of peak that the matmul kernels themselves reach

# ---------------- a transformer shape of this size ----------------
h = max(256, int(round((128 * N / 12) ** (1 / 3) / 256)) * 256)   # hidden size, multiple of 256
L = max(1, int(round((N - vocab * h) / (12 * h * h))))              # layers from N ~= 12 L h^2 + V h
a = h // 128                                                        # heads of dimension 128
DP = G // (TP * PP); assert DP * TP * PP == G, "TP*PP must divide the device count"
m = max(1, round(B_tok / (seq * mb * DP)))                          # micro-batches per pipeline per step
tokens_step = m * seq * mb * DP

# ---------------- memory per device, in bytes ----------------
N_dev = N / (TP * PP)                                               # parameters held by one device
shard = lambda stage: DP if zero >= stage else 1
states = N_dev * (w_b / shard(3) + g_b / shard(2) + (master_b + opt_b) / shard(1))
if zero >= 3: states += w_b * N_dev / (L / PP)                      # one layer gathered at a time
full_layer = seq * mb * h * (34 + 5 * a * seq / h) / TP             # Korthikanti et al. (2022), fp16, seq-parallel
act_layer = {"none": full_layer, "selective": 34 * seq * mb * h / TP, "full": 2 * seq * mb * h / TP}[recompute]
in_flight = min(m, PP)                                              # 1F1B keeps at most PP micro-batches live
acts = (L / PP) * in_flight * act_layer + (full_layer if recompute == "full" else 0)
logits = seq * mb * vocab * 6                                       # bf16 logits + fp32 softmax on the last stage
overhead = 2e9                                                      # CUDA context, workspace, fragmentation
mem = states + acts + logits + overhead

# ---------------- time per step ----------------
f_model = 6 * N + 12 * L * h * seq                                  # FLOPs per token (PaLM convention)
f_extra = {"none": 0, "selective": 4 * L * h * seq, "full": 2 * N + 4 * L * h * seq}[recompute]
t_comp = (f_model + f_extra) * tokens_step / G / (peak * kappa)
t_pipe = t_comp * (m + PP - 1) / m                                  # GPipe / 1F1B bubble
ring = lambda p: 2 * (p - 1) / p                                    # ring all-reduce: bytes moved per device / size
tp_bytes = (L / PP) * m * 4 * ring(TP) * (2 * seq * mb * h)         # 4 all-reduces per layer per micro-batch
t_tp = tp_bytes / bw_intra
pp_link = bw_intra if TP * PP <= 8 else bw_inter
pp_bytes = (m * 2 * 2 * seq * mb * h) if PP > 1 else 0              # activations forward + grads backward
t_pp = pp_bytes / pp_link
dp_bytes = (2 * N_dev) * ring(DP) * (1.5 if zero >= 3 else 1)       # gradient all-reduce (+ param all-gather)
dp_link = bw_inter if G > 8 else bw_intra
t_dp = dp_bytes / dp_link
t_dp_exposed = max(0.0, t_dp - (2 / 3) * t_pipe)                    # hidden behind the backward pass if shorter
t_step = t_pipe + t_tp + t_pp + t_dp_exposed

steps = D / tokens_step
total_s = steps * t_step
mfu = f_model * tokens_step / (t_step * G * peak)
hfu = (f_model + f_extra) * tokens_step / (t_step * G * peak)
gpu_hours = G * total_s / 3600
energy_kwh = gpu_hours * tdp_w * pue / 1000

print(f"shape      h={h} L={L} heads={a}   DP x TP x PP = {DP} x {TP} x {PP}   micro-batches/step m={m}")
print(f"memory/dev states {states/1e9:6.1f} GB  activations {acts/1e9:6.1f} GB  logits {logits/1e9:4.1f} GB  "
      f"overhead {overhead/1e9:3.1f} GB  total {mem/1e9:6.1f} GB  HBM {hbm/1e9:.0f} GB  {'OK' if mem <= hbm else 'OVER'}")
print(f"FLOPs/token  model {f_model:.3e}  (6N = {6*N:.3e}, attention {12*L*h*seq/f_model*100:.1f}%)  recompute +{f_extra:.2e}")
print(f"step time  compute {t_comp:.3f}s  pipelined {t_pipe:.3f}s  TP {t_tp:.3f}s  PP {t_pp:.3f}s  "
      f"DP {t_dp:.3f}s (exposed {t_dp_exposed:.3f}s)  -> {t_step:.3f}s")
print(f"bytes/step/dev  DP {dp_bytes/1e9:.2f} GB  TP {tp_bytes/1e9:.2f} GB  PP {pp_bytes/1e9:.2f} GB")
print(f"MFU {mfu*100:.1f}%  HFU {hfu*100:.1f}%  pipeline bubble {(PP-1)/(m+PP-1)*100:.1f}%")
print(f"steps {steps:,.0f}   wall-clock {total_s/86400:.2f} days   {gpu_hours:,.0f} device-hours   "
      f"${gpu_hours*price:,.0f}   {energy_kwh/1000:.1f} MWh   {energy_kwh*kg_per_kwh/1000:.1f} t CO2e")

# ---------------- two sweeps with numpy: ZeRO stage, and the parallel split ----------------
stages = np.arange(4)
per_param = (w_b / np.where(stages >= 3, DP, 1) + g_b / np.where(stages >= 2, DP, 1)
             + (master_b + opt_b) / np.where(stages >= 1, DP, 1))
print("states/device by ZeRO stage 0..3, GB (sharded parts only):", np.round(per_param * N_dev / 1e9, 2))

tp_opts, pp_opts = np.array([1, 2, 4, 8]), np.array([1, 2, 4, 8])
T, P = np.meshgrid(tp_opts, pp_opts, indexing="ij")
Dp = G // (T * P); mm = np.maximum(1, np.round(B_tok / (seq * mb * Dp)))
comp = (f_model + f_extra) * mm * seq * mb * Dp / G / (peak * kappa) * (mm + P - 1) / mm
tpt = (L / P) * mm * 4 * (2 * (T - 1) / T) * (2 * seq * mb * h) / bw_intra
ppt = np.where(P > 1, mm * 4 * seq * mb * h, 0) / np.where(T * P <= 8, bw_intra, bw_inter)
dpt = np.maximum(0, (2 * N / (T * P)) * (2 * (Dp - 1) / Dp) / bw_inter - (2 / 3) * comp)
step = comp + tpt + ppt + dpt
days = D / (mm * seq * mb * Dp) * step / 86400
print("days by TP (rows 1,2,4,8) x PP (cols 1,2,4,8):\n", np.round(days, 2))

Read the sweep as a planner would. For a model that fits in one device’s memory, pure data parallelism (TP = PP = 1) is fastest: every form of model splitting adds communication or bubbles and removes nothing that was in the way. Tensor parallelism costs most, because its traffic is on the critical path and the DP all-reduce was already hidden. The 7B default is the easy case. Raise N to 70B with 256 devices and the first row turns red: 70B of bf16 weights and gradients is 280 GB per device under ZeRO 1, so TP = 8 and ZeRO 2 or 3, or a pipeline, become necessary, and the question stops being “which split is fastest” and becomes “which split runs at all”. Raise it to 405B and you will need all three dimensions, 16,384-device clusters stop looking extravagant, and the days count stops being an estimate anyone should trust to better than a factor of two.

Wrap-up

Five lines to remember

  • A transformer is matrix multiplication: 2N FLOPs per token forward, 6N to train, plus 12Lhs for attention scores. Total training compute is 6ND, and everything else in the plan is a division of that number.
  • A kernel’s attainable speed is min(peak, intensity × bandwidth). Big matmuls are compute-bound; layer norms, naive attention and small-batch decoding are memory-bound. Batching raises intensity; fusion avoids moving bytes at all.
  • Training memory is 16 bytes per parameter of state (bf16 weights and gradients, fp32 master copy and Adam moments) plus activations of 34sbh per layer and the attention squares; recompute trades those for compute, ZeRO shards the state across the data-parallel group.
  • Data parallelism all-reduces gradients with a ring at 2(p−1)/p × S bytes per device; tensor parallelism splits matrices inside a node with four all-reduces per layer; pipeline parallelism splits layers across nodes with a bubble of (p−1)/(m+p−1). Map them to the bandwidth ladder: tensor inside, pipeline across, data over the rest.
  • MFU is the honest metric: tokens per second times the FLOPs the model needs, over the peak of all devices; 40% is good. Time ≈ 6ND / (devices × peak × MFU), checkpoints at √(2δMsys), and failures arrive every M/n.

Check your understanding

Why does the backward pass cost twice the forward pass, rather than the same?

Each weight matrix in the forward pass does one multiplication, Y = XW. In the backward pass it does two: the gradient with respect to its input, dX = dY·WT, which is needed to continue the chain rule into earlier layers, and the gradient with respect to its weights, dW = XT·dY, which the optimiser needs. Each has the same FLOP count as the forward multiplication, so backward is 4N and the total is 6N per token.

A decode step for a batch of 8 on an H100 takes almost exactly as long as for a batch of 1. Why, and up to what batch does that hold?

Decoding one token reads all the weights once (2N bytes in bf16) and does 2N FLOPs per sequence, so its arithmetic intensity is B FLOP/byte. Below the knee I* = P/BW ≈ 295 for an H100 the time is set by reading the weights, which does not depend on B. Only past a batch of about 295 sequences does the arithmetic become the bottleneck and the step time start to grow.

Why is ZeRO stage 1 free in communication terms, while stage 3 costs half as much again?

A ring all-reduce is a reduce-scatter followed by an all-gather, each moving (p−1)/p × S bytes. Stage 1 needs exactly those two halves: reduce-scatter the gradient so that each device gets the sum for its shard, update the shard, all-gather the updated weights. Stage 3 also sharded the weights, so before every layer runs its weights must be all-gathered again, in the forward pass and once more in the backward pass; that extra gathering of 2N bytes brings the per-device traffic from 2S to 3S.

In the Megatron feed-forward split, why must the first matrix be split by columns and not by rows?

Between the two matrices sits GELU, applied element by element. Splitting A by columns gives each device complete elements of the hidden vector XAi, so the GELU can be applied locally. Splitting A by rows would give each device a partial sum of every element, and GELU of a sum is not the sum of GELUs, so the partial sums would have to be all-reduced before the non-linearity: a second communication in the middle of the block.

GPipe and 1F1B have the same bubble fraction. What does 1F1B buy, and what would reduce the bubble itself?

1F1B starts each micro-batch’s backward pass as early as possible, so a stage holds at most p micro-batches’ activations rather than all m: memory bounded by the depth of the pipeline instead of by the batch. The bubble (p−1)/(m+p−1) is reduced by more micro-batches per step (larger global batch or smaller micro-batches), fewer stages, or interleaved schedules that give each device several non-adjacent chunks of layers.

Why does the parallelism hierarchy put tensor parallelism inside the node and pipeline parallelism across nodes, rather than the other way round?

Tensor parallelism issues four all-reduces per layer per micro-batch, each over an s×b×h activation, and every one sits on the critical path, so it needs the fastest link available: NVLink at hundreds of GB/s, which only connects the devices of one node. Pipeline parallelism passes one activation per micro-batch between two devices, tolerates latency, and can be partly overlapped, so it survives on a 50 GB/s network port. Putting them the other way round would move the heaviest, least overlappable traffic onto the slowest link.

A team reports 60% hardware FLOP utilisation with full activation checkpointing. What is their MFU, roughly?

Full checkpointing adds one forward pass (2N) to the 6N the model needs, so the hardware executes 8N FLOPs per token to make 6N of progress. MFU = HFU × 6/8 = 45%. HFU can be raised by doing more redundant work; MFU cannot, which is why it is the metric to report.

Agent Safety & Evaluation

What happens when the text an agent reads starts giving the orders

An agent that reads your email, browses the web and can send messages has a new kind of weak spot: anyone who can put text in front of it can try to give it instructions. No single defence stops that, so real systems stack several imperfect ones, like slices of Swiss cheese, and then measure how often an attack still gets through. The figure does exactly that for a small office agent built in this page: the red band is 100% of injected instructions, and each slab is a defence. Touch a slab to switch it on and watch both the attack rate and the share of ordinary work the agent still gets done.

The idea

The lethal trifecta

A chatbot that only talks can say something wrong. An agent that acts can do something wrong, with your permissions. Computer security has an old name for a program tricked into misusing the authority it holds: a confused deputy (Hardy, 1988). Simon Willison (2025) put the agent version into three words. Data theft needs three ingredients at once: the agent can see private data, it reads untrusted content that an outsider can write, and it has a way out, any channel that sends data out, such as email or a web request. Take away any one of the three and this kind of attack has nowhere to go.

When all three are present, the risk per task may look small: a share q of untrusted inputs carries an injected instruction, and the model follows a share g of those. But agents run many tasks. Switch the three legs on and off, then slide the number of tasks.

\[ \begin{aligned} p &= q\,g\;\mathbb{1}\big[\text{all three legs}\big] \\ P_N &= 1-(1-p)^{N} \end{aligned} \]
Read it as: p is the chance that one task ends in a leak: an injection must be present (q), the model must follow it (g), and all three legs must exist (the indicator 𝟙 is 1 if they do, 0 if not). Over N independent tasks, the chance of at least one leak is one minus the chance that every task is clean, (1 − p)N. The expected number of leaks is N·p.
Say it“p is q times g, if all three legs are present; the chance of at least one incident in N tasks is one minus one-minus-p to the N.”

The threat

Prompt injection: when data gives orders

In direct prompt injection the user types the instructions. The dangerous kind for agents is indirect prompt injection (Greshake et al., 2023): the instructions arrive inside content the agent reads while doing your task, an email, a web page, a shared document, a tool’s output. It works because a language model sees one stream of tokens. Your request, the system prompt and the email are all just text, and there is no type system that says which lines are commands. It is SQL injection without a way to escape the input. Real injections are written to blend in, or hidden where people don’t look; on this page they are shown as a schematic, clearly marked ⟨instruction: …⟩ so you can always see where they are. One known mitigation is spotlighting (Hines et al., 2024): mark untrusted text so the model can tell it apart, with delimiters or by rewriting every space (“datamarking”). Switch the marking on and run more tasks.

\[ P(\text{hijack}) = 1-\big(1-q\,g\,\rho\big)^{m} \]
Read it as: a task reads m untrusted documents; each carries an injection with probability q, and the model follows a given injection with probability gρ, where ρ ≤ 1 is the reduction spotlighting buys. The task is hijacked if any one document succeeds. This page assumes ρ = 0.7 for delimiters and 0.4 for datamarking; those are illustrations, not measurements, and real reductions depend on the model and on how hard the attacker tries.
Say it“The chance of a hijack is one minus one-minus-q-g-rho to the m.”

Defence 1 · filter the input

Injection detectors and the base-rate trap

The obvious defence is a classifier that scans every tool result and withholds anything that looks like an injection. Such detectors exist and help, but they are classifiers, with the usual two errors: they miss some injections, and they flag some harmless text. Two things make that worse than it sounds. First, base rates: almost all the text an agent reads is harmless, so even a small false-alarm rate produces more false alarms than true hits, and every false alarm is a task the agent can no longer finish. Second, adaptive attackers: an attacker can keep rewording an injection until the detector scores it like ordinary text, which pulls the two distributions together. Here the detector’s score is modelled as normal with mean 0 for harmless text and d′ for injected text. Move the threshold, then shrink d′.

\[ \begin{aligned} \text{TPR} &= 1-\Phi(\theta-d') \\ \text{FPR} &= 1-\Phi(\theta) \\ \text{prec} &= \frac{\pi\,\text{TPR}}{\pi\,\text{TPR} + (1-\pi)\,\text{FPR}} \\ \text{risk} &= \pi\,(1-\text{TPR})\,g \end{aligned} \]
Read it as: Φ is the standard normal CDF and θ the threshold: text scoring above it is flagged. TPR is the share of injections caught, FPR the share of harmless text flagged. With a base rate π of injected documents, Bayes’ rule gives the precision (prec), the share of flags that are real. The injections that slip through are still followed with probability g, which leaves a residual risk per document.
Say it“Precision is pi times TPR over pi times TPR plus one-minus-pi times FPR; the residual risk is pi times one-minus-TPR times g.”

Defence 2 · separate the powers

Privilege separation: plans from trusted text only

Detectors try to recognise attacks. Privilege separation makes most of them impossible by construction. In the dual-LLM pattern (Willison, 2023), refined into CaMeL by Debenedetti et al. (2025), a planner model sees only your request and writes the whole plan as a small program before any untrusted text is read. A quarantined model reads the emails and pages, but it has no tools: it can only return values into variables. Each value carries a label, T (trusted) or U (untrusted), and the labels spread through the program like ink: anything computed from a U value is U. A policy then checks every tool call. An injection can still change the values the quarantined model returns, but it can no longer add a call or change who a call is aimed at. Pick a task and a policy, and switch the injection on.

\[ \begin{aligned} y &= f(x_1,\dots,x_n) \\ \ell(y) &= \ell(x_1) \sqcup \cdots \sqcup \ell(x_n) \\ \text{run}(c) &\iff \ell(a) = \mathsf{T} \;\; \forall\, a \in \text{sens}(c) \end{aligned} \]
Read it as: ℓ(x) is the label of value x. The join ⊔ takes the “least trusted” of its inputs: T ⊔ T = T, and anything joined with U is U. A tool call c may run only if its sensitive arguments, sens(c) (the recipient of an email, the path of a file to delete), are trusted. Other arguments, like the body of an email, may be untrusted; the policy decides which are which.
Say it“The label of y is the join of the labels of its inputs; a call runs only if every sensitive argument is labelled trusted.”

Defence 3 · limit the blast radius

Sandboxes, permissions and allow-lists

Whatever the model decides, the environment can refuse. That is the old principle of least privilege (Saltzer & Schroeder, 1975): give a program exactly the permissions its tasks need. For an agent that means a sandbox (files only under a working folder, code in a container with no network) and allow-lists (the hosts it may fetch from, the people it may email). These checks run in ordinary code, outside the model, so no amount of clever wording can talk them round. But they must be written carefully: a check that compares strings instead of meanings can be walked around. Below are twelve actions an agent might request, six from real tasks and six that an injection might ask for. Tighten the manifest, then switch between naive and canonical checks.

\[ \begin{aligned} \text{allow}(a) &= [\,\text{tool}_a \in G\,] \\ &\wedge [\,\text{canon}(\text{path}_a) \in R\,] \\ &\wedge [\,\text{host}_a \in H\,] \wedge [\,\text{to}_a \in A\,] \\ D &= \sum_{a\,\in\,\text{harmful}} s_a\,\text{allow}(a) \end{aligned} \]
Read it as: an action runs only if its tool is granted (G), its file path, after canonicalisation (resolving “..” and “.”), lies inside the allowed folder R, its host is on the host list H, and its recipient on the address list A; each test applies only to actions that have that argument. D, the damage that gets through, adds the severity sa of every harmful action still allowed.
Say it“An action is allowed if its tool, canonical path, host and recipient are all on their lists; the damage is the sum of severities of harmful actions allowed.”

Defence 4 · ask before acting

A human in the loop, and why fewer questions work better

Permissions cannot tell a legitimate delete from a malicious one; a person can. So agents pause before risky actions and ask: “Send this email to eve@elsewhere.example?” This confirmation gate is only as good as the attention behind it, and attention wears out. People who see many prompts learn to click “yes” without reading: Akhawe & Felt (2013) measured how often real browser users clicked through security warnings, and the habit is well documented. Bainbridge (1983) called the general problem the irony of automation: the more a system asks a person only to watch, the worse the person gets at watching. Here every action in a 40-action session has a risk score, and actions at or above a threshold θ are sent to the user. The fatigue curve v(m) is an illustrative model, not a measured one; the shape of the trade-off is the point. Move the threshold and find the bottom of the curve.

\[ \begin{aligned} m(\theta) &= \textstyle\sum_j n_j\,\mathbb{1}[\,r_j \ge \theta\,] \\ v(m) &= \frac{v_0}{1 + m/m_0} \\ P(\text{slip}) &= 1 - P(r_{\text{atk}} \ge \theta)\; v\big(m(\theta)\big) \end{aligned} \]
Read it as: action type j has risk rj and occurs nj times per session, so m(θ) is the number of prompts the user sees. With m prompts the user catches a bad request with probability v(m): v0 when prompts are rare, halved by m = m0. A malicious action slips through unless it is gated and the user is paying attention.
Say it“The chance an attack slips through is one minus the chance it is gated times the user's vigilance, which falls as the number of prompts grows.”

Keeping score

Success rates need error bars

Agents are random: the same task run twice can succeed once and fail once. So an evaluation runs each task many times and reports a rate, and a rate from n trials comes with uncertainty. The textbook interval, p̂ ± 1.96√(p̂(1 − p̂)/n), named after Wald, behaves badly exactly where agent evaluations live: small n and rates near 0 or 100%. With 20 out of 20 it reports [100%, 100%]. Brown, Cai & DasGupta (2001) recommend the Wilson interval instead; Clopper–Pearson inverts the exact binomial tails and never covers less than promised. For safety the low end matters most: “0 of 50 attacks succeeded” still allows a true rate of several percent. Push the true rate towards 100%, shrink n, and compare how often each interval really contains the truth.

\[ \frac{\hat p + \dfrac{z^2}{2n} \;\pm\; z\sqrt{\dfrac{\hat p(1-\hat p)}{n} + \dfrac{z^2}{4n^2}}}{1 + \dfrac{z^2}{n}} \]
Read it as: p̂ = x/n is the observed success rate and z = 1.96 for 95%. Wilson’s interval is centred not on p̂ but pulled towards ½ by z²/2n, and its width never collapses to zero, even at 0 or n successes. It comes from asking which true rates p would not be rejected by a test of the observed x. Coverage, the chance that the interval contains the true p, can be computed exactly by summing binomial probabilities, which the lower chart does.
Say it“p-hat plus z squared over 2n, plus or minus z root of p-hat one-minus-p-hat over n plus z squared over 4 n squared, all over one plus z squared over n.”

Keeping score, again

pass@k and pass^k: can it, versus will it

Run every task n times and you can ask two different questions. pass@k (Chen et al., 2021, for code generation): if the agent gets k tries and something can check which one worked, does at least one succeed? pass^k (Yao et al., 2024, in τ-bench): does it succeed on all k tries? The first measures capability, the second reliability, and an agent working for a person needs reliability: it gets one go each time you ask, and you will ask again tomorrow. Both have unbiased estimators that use all n trials, not just the first k. Twelve simulated tasks of varying difficulty below. Slide k up and watch the two measures split.

\[ \begin{aligned} \text{pass@}k &= \mathop{\mathbb{E}}_{\text{tasks}}\Big[\, 1 - \tbinom{n-c}{k} \big/ \tbinom{n}{k} \Big] \\ \text{pass}^k &= \mathop{\mathbb{E}}_{\text{tasks}}\Big[\, \tbinom{c}{k} \big/ \tbinom{n}{k} \Big] \end{aligned} \]
Read it as: a task was tried n times and succeeded c times. Pick k of the n attempts at random: C(n − c, k)/C(n, k) is the chance that all k are failures, so one minus it is the chance that at least one succeeded; C(c, k)/C(n, k) is the chance that all k succeeded. Average over tasks. The naive plug-in 1 − (1 − c/n)k is biased; these are not.
Say it“pass at k is the average of one minus n-minus-c choose k over n choose k; pass hat k is the average of c choose k over n choose k.”

Real-world project

Project: a prompt-injection playground

This is a complete, small version of the way agent-security benchmarks such as AgentDojo (Debenedetti et al., 2024) evaluate defences: a set of ordinary user tasks, a set of attacker goals planted in the content those tasks read, and three numbers per configuration. Utility: how often benign tasks are done correctly. Utility under attack: how often the user’s task still succeeds when an injection is present. Attack success: how often the attacker gets their way. The agent is a transparent stand-in for a language model: it carries out the right plan for each task, makes ordinary mistakes at a fixed rate per step, and follows an injected instruction with probability g. Every defence is real code acting on its tool calls. Each of the 10 tasks is run without an attack and against each of the 5 attack goals, n times, with the same random numbers for every configuration, so differences between rows are due to the defences, not to luck.

    import json, math, numpy as np
from scipy.stats import binomtest, norm

W = json.load(open("as-world.json", encoding="utf8")); D = W["defaults"]
CONTACTS, HOSTS, ROOT, ORG = set(W["contacts"]), set(W["hosts"]), W["root"], W["org"]

def mulberry32(a):                                   # the page's random numbers, bit for bit
    s = [a & 0xFFFFFFFF]
    def r():
        s[0] = (s[0] + 0x6D2B79F5) & 0xFFFFFFFF; a = s[0]
        t = ((a ^ (a >> 15)) * (1 | a)) & 0xFFFFFFFF
        t = ((t + (((t ^ (t >> 7)) * (61 | t)) & 0xFFFFFFFF)) & 0xFFFFFFFF) ^ t
        return ((t ^ (t >> 14)) & 0xFFFFFFFF) / 4294967296
    return r

def canon(p):
    out = []
    for s in p.split("/"):
        if s in ("", "."): continue
        if s == "..":
            if out: out.pop()
        else: out.append(s)
    return "/" + "/".join(out)
in_root = lambda p: (canon(p) + "/").startswith(ROOT)
def needs_gate(tool, arg): return tool == "delete_file" or (tool == "send_email" and not arg.endswith("@" + ORG)) or (tool == "fetch" and arg not in HOSTS)
def sandbox_ok(tool, arg): return not tool.endswith("_file") or in_root(arg)
def allow_ok(tool, arg): return arg in CONTACTS if tool == "send_email" else arg in HOSTS if tool == "fetch" else True
def steps(T): return 1 + len(T["acts"]) + (T["out"] == "answer")

def params(g=D["g"], theta=D["theta"], v=D["v"]):
    return dict(g=g, rho=D["rho"], v=v, r=D["r"], tpr=norm.sf(theta - D["dprime"]), fpr=norm.sf(theta))
def thresholds(P, cfg, t, a):
    e = W["tasks"][t]["e"]
    return [e, e, e, e, P["tpr"] if a >= 0 else P["fpr"], P["g"] * (P["rho"] if cfg.get("spot") else 1), P["v"], P["r"]]

def episode(cfg, t, a, B):
    """B[i]: 0-3 mistake at step i, 4 detector flags, 5 model follows, 6 human catches, 7 human wrongly rejects.
    Returns (user task done, attack succeeded, stage that stopped the attack, prompts)."""
    T = W["tasks"][t]; A = W["attacks"][a] if a >= 0 else None
    user = not any(B[:steps(T)]); atk = False if A else None; stop = -1; prompts = 0; seen = True
    if cfg.get("det") and B[4]:
        seen, user = False, False
        if A: stop = 0
    if A and seen:
        if not B[5]: stop = 1
        elif cfg.get("priv") and A["acts"]: stop = 2
        else:
            ok = True
            for tool, arg in A["acts"]:
                if cfg.get("sbx") and not sandbox_ok(tool, arg): stop, ok = 3, False; break
                if cfg.get("allow") and not allow_ok(tool, arg): stop, ok = 4, False; break
                if cfg.get("gate") and needs_gate(tool, arg):
                    prompts += 1
                    if B[6]: stop, ok = 5, False; break
            if ok:
                stop, atk = 6, True
                if A["id"] == "D": user = False
                if A["id"] == "B" and any(x[1] == "/work/report.csv" for x in T["acts"]): user = False
    if seen:
        for tool, arg in T["acts"]:
            if cfg.get("priv") and T["dep"]: user = False; break
            if cfg.get("sbx") and not sandbox_ok(tool, arg): user = False; break
            if cfg.get("allow") and not allow_ok(tool, arg): user = False; break
            if cfg.get("gate") and needs_gate(tool, arg):
                prompts += 1
                if B[7]: user = False; break
    return user, atk, stop, prompts

seed_of = lambda t, a, r: (((t * 6 + (a + 1)) * 1000 + r + 1) * 2654435761) & 0xFFFFFFFF
def simulate(P, cfg, n):
    NT, NA = len(W["tasks"]), len(W["attacks"]); ben = []; U = UA = AS = 0
    for a in range(-1, NA):
        for t in range(NT):
            c = 0
            for r in range(n):
                R = mulberry32(seed_of(t, a, r)); th = thresholds(P, cfg, t, a)
                user, atk, _, _ = episode(cfg, t, a, [R() < x for x in th])
                c += user; AS += bool(atk)
            if a < 0: ben.append(c); U += c
            else: UA += c
    return dict(ben=ben, U=U, UA=UA, AS=AS, nB=NT * n, nA=NT * NA * n)

def exact(P, cfg):                                  # all 2^8 outcomes of the eight events
    NT, NA = len(W["tasks"]), len(W["attacks"]); out = dict(U=0.0, UA=0.0, AS=0.0, prB=0.0, ben=[])
    for a in range(-1, NA):
        for t in range(NT):
            th = thresholds(P, cfg, t, a); pu = pa = pr = 0.0
            for m in range(256):
                B = [bool(m >> i & 1) for i in range(8)]
                w = math.prod(th[i] if B[i] else 1 - th[i] for i in range(8))
                user, atk, _, k = episode(cfg, t, a, B); pu += w * user; pa += w * bool(atk); pr += w * k
            if a < 0: out["U"] += pu / NT; out["prB"] += pr / NT; out["ben"].append(pu)
            else: out["UA"] += pu / (NT * NA); out["AS"] += pa / (NT * NA)
    return out

def pass_at(n, c, k): return 1.0 if n - c < k else 1 - np.prod(1 - k / np.arange(n - c + 1, n + 1))   # Chen et al. (2021)
def pass_all(n, c, k): return 0.0 if c < k else float(np.prod((c - np.arange(k)) / (n - np.arange(k))))

ALL = dict(det=1, spot=1, priv=1, sbx=1, allow=1, gate=1)
PRESETS = [("No defences", {}), ("Spotlighting", dict(spot=1)), ("Injection detector", dict(det=1)), ("Sandbox + allow-lists", dict(sbx=1, allow=1)),
           ("Confirmation gate", dict(gate=1)), ("Privilege separation", dict(priv=1)), ("All six layers", ALL)]
P, n = params(), D["n"]
print(f"detector at theta = {D['theta']}: TPR {P['tpr']:.6f}, FPR {P['fpr']:.6f};  n = {n} trials per (task, goal)\n")
print(f"{'defences':22s} {'utility':>14s} {'under attack':>14s} {'attack success':>15s}  {'Wilson 95% (attack)':>19s}  {'Clopper-Pearson':>16s}  exact ASR")
py = []
for name, cfg in PRESETS:
    s, e = simulate(P, cfg, n), exact(P, cfg)
    w = binomtest(s["AS"], s["nA"]).proportion_ci(method="wilson"); cp = binomtest(s["AS"], s["nA"]).proportion_ci(method="exact")
    wu = binomtest(s["U"], s["nB"]).proportion_ci(method="wilson")
    print(f"{name:22s} {s['U']:4d}/{s['nB']} {s['U'] / s['nB']:.3f} {s['UA']:4d}/{s['nA']} {s['UA'] / s['nA']:.3f} {s['AS']:5d}/{s['nA']} {s['AS'] / s['nA']:.3f}"
          f"  [{w.low:.4f}, {w.high:.4f}]  [{cp.low:.4f}, {cp.high:.4f}]  {e['AS']:.6f}")
    k5 = [np.mean([pass_at(n, c, 5) for c in s["ben"]]), np.mean([pass_all(n, c, 5) for c in s["ben"]])]
    py.append(dict(name=name, U=s["U"], UA=s["UA"], AS=s["AS"], wU=[wu.low, wu.high], wAS=[w.low, w.high], eU=e["U"], eAS=e["AS"], pass5=k5))
print()
for name, cfg in (PRESETS[0], PRESETS[-1]):
    s, e = simulate(P, cfg, n), exact(P, cfg)
    row = "  ".join(f"k={k}: {np.mean([pass_at(n, c, k) for c in s['ben']]):.4f} / {np.mean([pass_all(n, c, k) for c in s['ben']]):.4f}" for k in (1, 2, 5, 10))
    print(f"{name:15s} pass@k / pass^k   {row}   (exact pass^5 {np.mean([p ** 5 for p in e['ben']]):.4f})")
print("\n0 successes in 50 trials: Wilson upper %.4f, Clopper-Pearson upper %.4f, rule of three %.4f" %
      (binomtest(0, 50).proportion_ci(method="wilson").high, binomtest(0, 50).proportion_ci(method="exact").high, 3 / 50))
json.dump(dict(presets=py, n=n), open("as-py.json", "w"))

    Wrap-up

    Five lines to remember

    • Private data, untrusted content and a way out: an agent with all three can be turned against its user. Removing one leg is the strongest defence there is.
    • Prompt injection works because instructions and data share one token stream. Spotlighting and detectors lower the rate; they do not make it zero, and attackers adapt.
    • Structural defences give guarantees: plan from trusted text only and track taint (privilege separation), sandbox files, allow-list hosts and recipients, and check canonical values, not strings.
    • A human gate helps only if it is rare and specific; asking about everything trains people to say yes.
    • Evaluate agents like experiments: many trials per task, Wilson or Clopper–Pearson intervals, utility and attack success side by side, and pass^k when reliability matters.

    Check your understanding

    Your agent reads web pages and can see your files, but it cannot send email or make web requests of its own. Is prompt injection still a risk?

    Data theft through the agent is much harder, because the trifecta is missing its way out. But injection can still mislead you (a planted false claim in an answer), and a single forgotten channel, such as rendering an image from an attacker’s URL, is enough to restore the way out. Check every output channel.

    A detector catches 99% of injections and flags 1% of harmless text. Injections are 1 in 1,000 documents. What share of flags are real?

    Per 100,000 documents: 99 true flags against about 999 false ones, so roughly 9%. Most flags are false alarms, and each one stops a task.

    Why can privilege separation not stop an injection that makes the agent’s summary say an invoice is paid?

    Because that attack changes only a value, not the control flow. The quarantined model must read the email to summarise it, so whatever it returns is untrusted; the policy can stop it reaching a sensitive argument, but showing it to you is the task.

    A sandbox allows paths that start with “/work/”. Why is that not enough?

    A string test is not a location test: “/work/../home/keys.txt” passes it but points outside the folder. Canonicalise first (resolve “..”, and in real systems symbolic links), then compare; likewise compare whole host names, not prefixes.

    Your agent passed 19 of 20 runs of a task. What is pass^5, and why might you care more about it than pass@5?

    pass^5 = C(19,5)/C(20,5) = 15/20 = 0.75, while pass@5 = 1. If a user relies on the agent every time, a 25% chance that at least one of five requests fails matters more than the certainty that one of five succeeds.
